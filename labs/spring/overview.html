@Async · CompletableFuture · @Retryable — 프록시가 해 주는 일과 그 함정

주문 확인 메일 후처리를 예로 @Async와 ExecutorService를 비교하고, 같은 빈 안에서 호출하면 왜 비동기가 안 되는지(self-invocation) 테스트로 확인합니다. 독립 작업 3개를 순차/병렬로 돌려 시간 차이를 보고, README에는 없지만 코드에 있는 @Retryable 결제 재시도 실험까지 담겨 있습니다.

Java 21Spring Boot 3.4.1spring-retryJUnit 5 · MockitoDB 없음

01한눈에

30초 요약

문제

메일 같은 부가 작업이 요청 스레드를 붙잡고, 서로 무관한 작업 3개(결제 250ms·재고 200ms·배송 220ms)를 줄줄이 기다리면 시간이 합산됩니다. 외부 결제 API는 가끔 일시적으로 실패합니다.

접근

① @Async와 ExecutorService로 같은 작업을 넘겨 실행 스레드 이름을 비교 ② 같은 빈 내부 호출 ③ 순차 vs 병렬 시간 ④ @Retryable에서 예외 종류별로 재시도할지, 복구(@Recover)할지 나누기.

결론

@Async·@Retryable은 프록시를 거쳐야만 동작합니다. 병렬화는 “먼저 전부 시작하고 마지막에 join()”해야 효과가 있습니다. 재시도는 예외를 재시도 / 즉시 거절 / 복구 금지로 나누는 것이 핵심입니다.

02흐름

단계를 클릭하면 상세 설명이 나옵니다. 위는 @Async 호출 경로, 아래는 결제 재시도 경로입니다.

@Async 호출 경로

→ → →

테스트가 asyncWorkService.sendOrderConfirmationEmailWithAsync(order)를 호출합니다. 주입받은 asyncWorkService는 실제 객체가 아니라 Spring이 만든 프록시입니다(@EnableAsync가 켜져 있어서).

프록시는 @Async("springAsyncExecutor")를 보고 메서드 본문을 실행하지 않고 springAsyncExecutor(core=max=3, queue 10)에 작업을 제출합니다. 호출자는 즉시 CompletableFuture를 받습니다.

풀의 워커 스레드(spring-async-1 등)가 본문을 실행해 EmailReceipt를 만들고 future를 완료합니다. 테스트는 get(1, SECONDS)로 기다린 뒤 threadName()이 spring-async-로 시작하는지 확인합니다.

callAsyncMethodFromSameBean() 안에서 sendOrderConfirmationEmailWithAsync()를 부르면 this. 호출이라 프록시를 다시 거치지 않습니다. @Async가 무시되어 호출자 스레드에서 동기 실행되고, 이미 완료된 future가 반환됩니다. 테스트는 threadName == 호출자 스레드명으로 이를 증명합니다.

결제 재시도 경로 (@Retryable)

→ → →

PaymentRetryService.requestPayment()도 프록시를 거칩니다(@EnableRetry). 첫 호출의 RetryContext.getRetryCount()는 0. 성공하면 바로 끝나고 대기(backoff)도 없습니다.

TemporaryPaymentException(PaymentException 하위)이 나면 재시도합니다. 테스트 설정(initial-delay 10, multiplier 2.0, random false)에서 대기는 10ms → 20ms로 늘어납니다. 세 번째 시도(retryCount 2)에서 성공하면 COMPLETED. 세 번 모두 같은 idempotencyKey로 호출됩니다.

max-attempts 3을 다 써도 실패하면 @Recover recover(TemporaryPaymentException, ...)가 호출되어 예외 대신 REVIEW_REQUIRED(수동 확인 필요)를 반환합니다.

InvalidPaymentRequestException: noRetryFor → 재시도 없이 1회만 호출, 그러나 @Recover로 REJECTED 반환.
UnknownPaymentStateException: 재시도는 3회 하지만 notRecoverable → @Recover를 건너뛰고 원래 예외를 그대로 던집니다. “결제가 됐는지 모르는 상태”를 조용히 덮지 않기 위함입니다.

03비교·핵심 구현

탭을 눌러 케이스별로 봅니다.

@Async — 서비스 코드는 단순, 실행은 프록시가 비동기

메서드에 어노테이션만 붙이면 Spring이 지정한 풀로 넘겨 줍니다.

// AsyncWorkService
@Async("springAsyncExecutor")
public CompletableFuture<EmailReceipt> sendOrderConfirmationEmailWithAsync(Order order) {
    return CompletableFuture.completedFuture(emailSender.send(order, "@Async"));
}

// ExecutorConfig
executor.setCorePoolSize(3);
executor.setMaxPoolSize(3);
executor.setQueueCapacity(10);
executor.setThreadNamePrefix("spring-async-");
어떻게
프록시가 메서드 호출을 가로채 ThreadPoolTaskExecutor에 제출. 본문 안의 completedFuture는 워커 스레드에서 만들어지고, 프록시가 돌려준 future가 그 결과로 완료됩니다.
결과
테스트: threadName이 spring-async-로 시작하고 호출자 스레드와 다름. 메일 제목 [deep-dive] 주문 확인: order-1.
트레이드오프
호출부가 평범한 메서드 호출처럼 보여 간단하지만, 프록시를 안 거치면 조용히 동기 실행됩니다.
코드
src/main/java/dev/deepdive/spring/async/AsyncWorkService.java, src/main/java/dev/deepdive/spring/config/ExecutorConfig.java

ExecutorService — 제출이 코드에 드러남 비동기

순수 Java 방식. 어떤 풀에 무엇을 제출하는지 호출부에서 바로 보입니다.

// AsyncWorkService
return CompletableFuture.supplyAsync(
        () -> emailSender.send(order, "ExecutorService"),
        javaExecutorService
);

// ExecutorConfig
@Bean(destroyMethod = "shutdown")
public ExecutorService javaExecutorService() {
    return Executors.newFixedThreadPool(3, Thread.ofPlatform().name("java-executor-", 1).factory());
}
어떻게
프록시와 무관. supplyAsync(..., executor)가 직접 작업을 넘깁니다. 종료(shutdown)는 빈 destroyMethod로 관리.
결과
테스트: threadName이 java-executor-로 시작.
트레이드오프
흐름이 명확하고 같은 클래스 안에서도 동작하지만, 풀 생성·종료·제출을 직접 관리해야 합니다.
언제
README “언제 쓰나” 표: 여러 작업의 제출·완료·조합을 직접 제어할 때, Spring 프록시 밖 순수 Java 코드, 같은 클래스 내부에서 비동기가 필요할 때.

self-invocation — @Async가 무시됨 동기 실행

같은 객체 안에서 this로 부르면 프록시를 우회합니다.

public CompletableFuture<EmailReceipt> callAsyncMethodFromSameBean(Order order) {
    return sendOrderConfirmationEmailWithAsync(order); // this. 호출 → 프록시 미경유
}

// AsyncVsExecutorServiceTest
assertThat(receipt.threadName()).isEqualTo(callerThreadName); // 내부 호출이라 테스트 스레드명 표출
assertThat(receipt.threadName()).doesNotStartWith("spring-async-");
왜
Spring AOP는 빈을 감싼 프록시 객체에 부가 기능을 넣습니다. 프록시 내부에서 실제 객체로 들어간 뒤의 this는 프록시가 아닙니다.
해결
비동기 메서드를 별도 빈으로 분리 — 이 모듈은 병렬 예제에서 실제로 OrderPreparationAsyncService를 따로 둡니다. 또는 ExecutorService 사용.
같은 원리
@Transactional, @Retryable, @Cacheable도 프록시 기반이라 같은 함정이 있습니다(일반 지식).

CompletableFuture — 순차 vs 병렬 시간 비교

결제 확인 250ms, 재고 확인 200ms, 배송 예정일 220ms (모두 Thread.sleep으로 흉내). 서로 의존하지 않습니다.

// before: 하나 끝나야 다음 시작 → 합에 가까움
String paymentStatus = confirmPayment(order);
String inventoryStatus = checkInventory(order);
String deliveryEstimate = estimateDelivery(order);

// after: 셋을 먼저 다 시작 → 가장 느린 작업에 가까움
CompletableFuture<String> paymentStatus = CompletableFuture.supplyAsync(() -> confirmPayment(order), javaExecutorService);
CompletableFuture<String> inventoryStatus = CompletableFuture.supplyAsync(() -> checkInventory(order), javaExecutorService);
CompletableFuture<String> deliveryEstimate = CompletableFuture.supplyAsync(() -> estimateDelivery(order), javaExecutorService);
// ...
paymentStatus.join(), inventoryStatus.join(), deliveryEstimate.join()
결과
테스트 임계값: 순차 ≥ 600ms, 병렬 < 500ms. 두 방식 모두 같은 메일 본문을 반환.
전제
풀 크기 3 = 작업 3개가 동시에 돌 수 있어야 함. 풀이 1이면 병렬 이점이 사라집니다.

@Async로 병렬 — join 위치가 전부 함정 주의

@Async 작업을 호출하자마자 join()하면 비동기여도 사실상 순차입니다.

// before: 제출 → 즉시 대기 → 다음 제출 (순차와 같음)
String paymentStatus = orderPreparationAsyncService.confirmPayment(order).join();
String inventoryStatus = orderPreparationAsyncService.checkInventory(order).join();
String deliveryEstimate = orderPreparationAsyncService.estimateDelivery(order).join();

// after: 셋 다 시작한 뒤 마지막에 join
CompletableFuture<String> paymentStatus = orderPreparationAsyncService.confirmPayment(order);
CompletableFuture<String> inventoryStatus = orderPreparationAsyncService.checkInventory(order);
CompletableFuture<String> deliveryEstimate = orderPreparationAsyncService.estimateDelivery(order);
왜 별도 빈
결제/재고/배송 메서드를 AsyncWorkService 안에 두면 self-invocation이 되어 비동기가 안 됩니다. 그래서 OrderPreparationAsyncService로 분리.
결과
테스트 임계값: before ≥ 600ms, after < 500ms.

@Retryable — 예외를 3갈래로 분류 README에 없음

외부 결제 API의 일시 오류는 재시도하되, 고쳐지지 않을 오류와 “결과를 모르는” 오류는 다르게 다룹니다.

@Retryable(
        retryFor = PaymentException.class,
        noRetryFor = InvalidPaymentRequestException.class,
        notRecoverable = UnknownPaymentStateException.class,
        maxAttemptsExpression = "${payment.retry.max-attempts:3}",
        backoff = @Backoff(
                delayExpression = "${payment.retry.initial-delay:50}",
                maxDelayExpression = "${payment.retry.max-delay:500}",
                multiplierExpression = "${payment.retry.multiplier:2.0}",
                randomExpression = "${payment.retry.random:true}"
        )
)
public PaymentResult requestPayment(PaymentRequest request) { ... }

@Recover
public PaymentResult recover(TemporaryPaymentException exception, PaymentRequest request) {
    return PaymentResult.reviewRequired(request.orderId());
}
예외재시도@Recover최종 결과 (RetryableTest)
TemporaryPaymentExceptionO (최대 3회)O3번째 성공 → COMPLETED / 3회 실패 → REVIEW_REQUIRED
InvalidPaymentRequestExceptionX (noRetryFor)O1회 호출 → REJECTED
UnknownPaymentStateExceptionO (3회)X (notRecoverable)같은 예외 인스턴스가 그대로 던져짐
설정
application.yml의 payment.retry.*(3회, 50ms, 최대 500ms, ×2.0, random true). 테스트는 @SpringBootTest(properties=...)로 10ms·random false로 바꿔 대기값을 결정적으로 만듭니다.
테스트 기법
RecordingSleeper(Sleeper 빈)로 실제로 자지 않고 대기 시간만 기록, RetrySynchronizationManager.getContext()로 시도 번호 확인, @MockitoBean PaymentGatewayClient로 실패 주입.

05한계·약점

README가 스스로 밝힌 한계와, 코드에서 확인되는 약점.

README 수정함 README에 @Retryable 실험이 없었음

SpringLabApplication에 @EnableRetry, retry/ 패키지, RetryableTest가 있었지만 README는 @Async만 다뤘습니다. 지금은 README에 “@Retryable로 재시도할 오류와 하지 않을 오류 나누기” 섹션과 시작점 항목을 추가했습니다.

README 수정함 “springAsyncExecutor도 fixed thread pool 크기 3”

README 문장을 실제 설정에 맞게 고쳤습니다. 실제로는 ThreadPoolTaskExecutor(core=max=3, queueCapacity 10)입니다. javaExecutorService만 Executors.newFixedThreadPool(3). 결과적으로 동시 3개는 같지만 큐 동작이 다릅니다.

코드 시간 기반 테스트는 환경에 민감

병렬 < 500ms 단언은 가장 느린 작업 250ms 대비 여유가 250ms뿐입니다. CI가 느리거나 스레드 풀 워밍업이 늦으면 실패할 수 있습니다.

실측 후 그대로 둠: 두 병렬 테스트를 5회 반복 실행한 소요 시간은 모두 255~257ms였습니다(순차는 670ms 이상). 오버헤드가 5ms 남짓이라 250ms 여유는 그 50배이고, 두 스레드 풀 모두 크기 3이라 세 작업이 큐에서 기다리지 않습니다. 기준을 바꿀 근거가 없어 단언은 유지했습니다. 아주 느린 공유 CI에서 문제가 되면 "병렬 < 순차 × 0.7" 같은 상대 비교를 더하는 것이 다음 단계입니다.

코드 풀 포화·예외 전파는 실험하지 않음
  • 작업이 3개뿐이라 큐(10)가 차는 상황, 거절 정책은 다루지 않습니다. 일반 지식: ThreadPoolTaskExecutor는 기본적으로 큐가 차고 max에 도달하면 TaskRejectedException; newFixedThreadPool은 큐가 무제한이라 메모리가 쌓일 수 있음.
  • 비동기 작업에서 예외가 났을 때 future로 전파되는 방식, void 반환 @Async의 예외 처리(AsyncUncaughtExceptionHandler, 일반 지식)도 없습니다.
코드 재시도 설정 일부는 검증되지 않음

운영 설정 random: true(지터)와 max-delay 상한은 테스트에서 끄거나(random false) 도달하지 않습니다(10→20ms, 상한 40). PaymentGatewayClient는 항상 성공하는 스텁이라 실패는 @MockitoBean으로만 재현됩니다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

@Async는 어떻게 동작하고, 같은 클래스 안에서 호출하면 왜 비동기가 안 되나요?

@EnableAsync가 빈을 프록시로 감싸고, 프록시가 호출을 가로채 TaskExecutor에 제출합니다. 같은 객체 안의 this.method()는 프록시를 거치지 않으므로 그냥 호출자 스레드에서 실행됩니다. 이 모듈의 테스트가 스레드 이름이 호출자와 같은 것으로 증명합니다. 해결은 별도 빈 분리(OrderPreparationAsyncService) 또는 ExecutorService 직접 사용.

@Async와 ExecutorService는 언제 각각 쓰나요?
  • @Async: 서비스 메서드 하나를 간단히 백그라운드로 — 메일·알림 같은 분리 가능한 후처리.
  • ExecutorService: 여러 작업의 제출·완료·조합을 직접 제어해야 할 때, 프록시 밖 순수 Java 코드, 같은 클래스 내부 호출.

(README “언제 쓰나” 표 기준)

독립 작업 3개를 병렬화했는데 시간이 안 줄었습니다. 무엇을 의심하나요?
  • 제출 직후 join()/get()으로 기다리고 있는지 — 이 모듈의 “@Async before” 케이스가 정확히 이 실수입니다.
  • self-invocation으로 @Async가 무시됐는지.
  • 풀 크기가 동시 작업 수보다 작은지(여기선 3으로 맞춤).
@Async를 쓸 때 전용 스레드 풀을 직접 정의하는 이유는?

스레드 이름(spring-async-)으로 로그 추적이 쉬워지고, core/max/queue로 동시성과 메모리 상한을 통제할 수 있습니다. 일반 지식 기본 실행기에 의존하면 큐 크기·거절 정책을 통제하기 어렵고, 작업 종류별로 풀을 나눠(bulkhead) 한 작업이 다른 작업을 굶기지 않게 하는 것도 불가능합니다.

어떤 예외는 재시도하고 어떤 예외는 하면 안 되나요?

일시적 오류(타임아웃, 일시 장애)는 재시도. 요청 자체가 잘못된 경우(InvalidPaymentRequestException)는 몇 번 해도 같으므로 noRetryFor로 즉시 거절. 결제 성공 여부를 모르는 경우(UnknownPaymentStateException)는 재시도는 해도 notRecoverable로 @Recover가 “실패”로 덮지 못하게 예외를 그대로 올려 상위에서 상태 조회·보정을 하게 합니다.

결제 API를 재시도할 때 가장 중요한 것은?

멱등성입니다. 첫 요청이 실제로는 처리됐는데 응답만 유실됐다면 재시도가 이중 결제를 만듭니다. 이 모듈의 PaymentRequest는 idempotencyKey를 필수로 하고, 테스트는 3번의 시도가 모두 같은 키(payment-order-2)로 호출됐는지 확인합니다.

지수 백오프와 지터(random)는 왜 쓰나요?

테스트에서 대기는 10ms → 20ms로 배수 증가합니다. 일반 지식 장애 중인 서버에 즉시·동시에 재시도가 몰리면 회복을 방해하므로 간격을 늘리고(backoff), 여러 클라이언트가 같은 박자로 재시도하지 않도록 무작위성(jitter)을 섞습니다. 이 모듈의 운영 설정은 random: true입니다.

@Recover 메서드는 어떻게 선택되나요?

첫 파라미터가 던져진 예외 타입, 이후 파라미터가 원래 메서드 인자와 맞는 @Recover 중 가장 구체적인 타입이 선택됩니다. 그래서 TemporaryPaymentException은 전용 recover, 다른 PaymentException은 범용 recover로 갑니다. 코드 주석: “UnknownPaymentStateException에 notRecoverable이 없다면 이 메서드(범용)가 선택된다.”
