Spring Cache + Redis — @Cacheable과 RedisTemplate 기반 구현, 그리고 핫키 분산 락

로컬 캐시는 서버마다 따로라서, 여러 서버가 같은 캐시를 보려면 Redis 같은 공용 캐시가 필요합니다. 하지만 Redis로 옮기면 직렬화, 없는 키 반복 조회, 동시 만료, 핫키 동시 miss를 직접 고민해야 합니다. 이 모듈은 MySQL/JPA를 원본으로 두고 @Cacheable(RedisCacheManager)과 StringRedisTemplate 기반 구현을 비교하며, Null caching · TTL Jitter · SET NX + Lua 분산 락을 Testcontainers로 검증합니다.

Java 21Spring Boot 3.4.1Spring Data RedisRedis 7.2.5MySQL 8.0.36 · JPATestcontainersJackson JSON

01한눈에

30초 요약

문제

공용 캐시에도 함정이 있습니다. 없는 id는 캐시에 안 남아 매번 DB로 관통, 인기 키가 비어 있는 순간 40개 요청이 동시에 DB 조회, 같은 TTL로 넣으면 동시에 만료.

접근

세 서비스를 비교: SpringCacheBookService(@Cacheable), RedisTemplateBookCacheService(수동 Cache Aside · __NULL__ sentinel · TTL Jitter), RedisHotKeyBookCacheService(락 없음 vs SET NX 락 + double-check). BookOriginService.readCount로 원본 조회 횟수를 셈.

결론

일반 메서드 결과 캐싱은 Spring Cache로 단순하게, SET NX·Lua·sentinel·jitter처럼 Redis 고유 기능이 필요하면 RedisTemplate. 기본 RedisCacheManager는 non-locking이라 @Cacheable이 분산 락을 대신하지 않습니다.

캐시가 있으면 락 없이 바로 역직렬화해 반환. 모든 요청에 락을 거는 게 아니라 miss일 때만 락을 시도합니다.

락 키 hot-book:{id}:lock, 요청마다 UUID 토큰. setIfAbsent(lockKey, token, 3초) = SET NX EX라 Redis가 원자적으로 처리해 한 요청만 true. 3초 TTL은 락 소유 앱이 죽어도 락이 영원히 남지 않게 하는 안전장치.

첫 GET과 락 획득 사이에 다른 요청이 캐시를 채웠을 수 있으니 한 번 더 GET(Double-Checked Locking). 그래도 없을 때만 MySQL 조회, 책이 있으면 10분 TTL로 저장. 없는 책은 저장하지 않음(negative caching 안 함).

if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end return 0 — 토큰 비교와 삭제를 Redis 안에서 원자적으로. 작업이 3초를 넘어 락이 만료되고 다른 요청이 새 락을 잡았다면 토큰이 달라 남의 락을 지우지 않습니다.

락을 못 얻은 요청은 DB를 치지 않고 10ms마다 캐시를 확인(sleep만 합쳐 약 1초). 끝까지 안 채워지면 Optional.empty() — 코드 주석: "책이 없음"뿐 아니라 "대기 시간 안에 캐시가 안 채워짐"일 수도 있다.

RedisTemplateBookCacheService.findBookById — 수동 Cache Aside

String key = "book:" + id;
String cached = redisTemplate.opsForValue().get(key);
if (cached != null) {
    return Optional.of(objectMapper.readValue(cached, Book.class));
}

Optional<Book> loaded = bookOriginService.findById(id);
if (loaded.isPresent()) {
    redisTemplate.opsForValue().set(
            key,
            objectMapper.writeValueAsString(loaded.get()),
            Duration.ofMinutes(10)
    );
}
return loaded;
차이
@Cacheable이 숨기던 GET/SET, JSON 변환(ObjectMapper), TTL을 서비스가 직접 씁니다. 대신 key·value·TTL을 세밀하게 제어 가능.
결과
2회 조회에 readCount 1, book:1에 "id":1, "name":"Effective Java" JSON.

Null caching — 없는 데이터도 30초 캐싱

if ("__NULL__".equals(cached)) {
    return Optional.empty();
}
// ...
} else {
    redisTemplate.opsForValue().set(key, "__NULL__", Duration.ofSeconds(30));
}
왜 짧게
나중에 그 id의 책이 실제로 생기면 sentinel이 새 값을 가립니다. 정상 값(10분)보다 훨씬 짧은 30초.
결과
999L을 20회 조회해도 readCount 1, 값 "__NULL__", TTL 1~30초.
비교
@Cacheable 쪽은 cache-null-values: false + unless라 없는 id는 매번 원본 조회(2회 → 2).
키 공유
수정함 sentinel은 Book JSON과 같은 key(book:{id})에 저장되므로, 일반 조회 findBookById도 sentinel을 먼저 확인해 Optional.empty()(없음 hit)로 돌려줍니다. 예전엔 JSON으로 파싱하려다 예외가 났습니다.

TTL Jitter — cacheBooksWithJitter

for (Book book : books) {
    String key = "book:" + book.id();
    Duration ttl = baseTtl;
    if (!maxJitter.isZero() && !maxJitter.isNegative()) {
        ttl = baseTtl.plusMillis(jitterMillis(key, maxJitter.toMillis()));
    }
    redisTemplate.opsForValue().set(key, objectMapper.writeValueAsString(book), ttl);
}

// hash를 SplitMix64 finalizer로 섞은 뒤 나머지 → 인접 key도 범위 전체로 흩어짐
static long jitterMillis(String key, long maxJitterMillis) {
    return Math.floorMod(mix(key.hashCode()), maxJitterMillis + 1);
}
어떻게
key의 hashCode를 섞어(SplitMix64) 0~maxJitter ms를 결정적으로 더함(같은 key면 항상 같은 jitter). 테스트는 base 60초, jitter 10초.
결과
RedisTemplateBookCacheTest: 5개 키 TTL이 모두 50~70초 범위, 서로 다른 값 2개 이상, 최대-최소 차이 5초 초과. 인접 key 100개의 jitter가 1초 단위 구간 9개 이상에 퍼지는지도 확인.
함정 수정함
예전엔 key.hashCode()를 그대로 나머지 연산해서, 연속 id "book:1"~"book:5"의 jitter가 133~137ms로 1ms씩만 달랐습니다(분산 효과 거의 없음). 테스트도 "값이 2개 이상 다름"만 봐서 드러나지 않았습니다.

RedisHotKeyBookCacheService.findWithDistributedLock (발췌)

String lockKey = "hot-book:" + id + ":lock";
String token = UUID.randomUUID().toString();

if (Boolean.TRUE.equals(
        redisTemplate.opsForValue().setIfAbsent(lockKey, token, Duration.ofSeconds(3)))) {
    try {
        String doubleChecked = redisTemplate.opsForValue().get(key);
        if (doubleChecked != null) {
            return Optional.of(objectMapper.readValue(doubleChecked, Book.class));
        }
        Optional<Book> loaded = bookOriginService.findById(id);
        // ... 있으면 SET key JSON 10분
        return loaded;
    } finally {
        redisTemplate.execute(
                new DefaultRedisScript<>(
                        """
                        if redis.call('GET', KEYS[1]) == ARGV[1] then
                            return redis.call('DEL', KEYS[1])
                        end
                        return 0
                        """,
                        Long.class
                ),
                List.of(lockKey),
                token
        );
    }
}

for (int i = 0; i < 100; i++) {
    Thread.sleep(Duration.ofMillis(10).toMillis());
    String cachedAfterWaiting = redisTemplate.opsForValue().get(key);
    if (cachedAfterWaiting != null) {
        return Optional.of(objectMapper.readValue(cachedAfterWaiting, Book.class));
    }
}
// 주의: 여기서 empty는 "책이 없음"뿐 아니라 "대기 시간 안에 캐시가 안 채워짐"일 수도 있다.
return Optional.empty();

Spring Cache vs RedisTemplate (README 표)

상황주로 선택이유
일반적인 메서드 결과 캐싱Spring Cache@Cacheable, @CachePut, @CacheEvict로 반복 코드 감소
Redis String 직접 GET/SETRedisTemplatekey, value, TTL을 코드에서 세밀하게 제어
Hash, Set, ZSet 사용RedisTemplateSpring Cache는 Redis 자료구조 API를 추상화하지 않음
Null sentinel, TTL JitterRedisTemplate값과 TTL에 별도 정책 필요
SET NX, Lua, 분산 락RedisTemplateRedis의 원자적 명령과 스크립트를 직접 사용

README: 두 방식은 함께 씁니다. 일반 조회는 Spring Cache로 단순화하고, Redis 고유 기능이 필요할 때 RedisTemplate. 학습용으로 RedisTemplateLearningService/RedisBasicCommandTest가 SET/GET/DEL, TTL(getExpire: -1 만료 없음, -2 키 없음), SET NX, Hash, ZSet 랭킹, INFO stats를 다룹니다.

05한계·약점

README 인정 문서·주석이 스스로 밝힌 한계, 코드 확인 코드를 읽어 보면 드러나는 약점.

README 인정 대기 요청의 empty는 "없음"과 "시간 초과"를 구분하지 못한다

대기 루프는 sleep만 약 1초(10ms × 100), 락 TTL은 3초. 원본 조회가 대기보다 오래 걸리면 대기 요청은 캐시가 곧 채워지더라도 먼저 Optional.empty()를 받습니다. 호출자는 "책이 없다"로 오해할 수 있습니다(코드 주석도 인정).

README 인정 락 경로는 없는 책을 캐싱하지 않는다

findWithDistributedLock은 Negative Caching을 하지 않아, 없는 id를 반복 조회하면 매번 락을 잡고 원본을 다시 확인합니다. Null sentinel은 findBookByIdWithNullCaching에만 있습니다.

README 인정 @Cacheable은 분산 락이 아니다

"기본 RedisCacheManager는 non-locking이므로 @Cacheable이 분산 락을 대신하지는 않는다." Spring Cache 경로에는 stampede 방어가 없습니다.

코드 확인 수정함 TTL Jitter가 연속 키에서는 거의 0

예전엔 "book:1"~"book:5"가 마지막 글자만 달라 hashCode가 1씩 차이 → jitter가 133~137ms로 5ms 안에 몰렸고, 테스트 단언("값이 2개 이상 다름")이 약해 드러나지 않았습니다.

수정: hash를 SplitMix64 finalizer로 섞은 뒤 나머지를 취해 결정성은 유지하면서 범위 전체로 퍼지게 했고, 테스트가 TTL 차이 5초 초과와 key 100개의 구간 분포를 단언합니다.

남은 점: jitter는 일괄 적재 헬퍼 cacheBooksWithJitter에만 있고, 실제 조회 경로(findBookById, @Cacheable 10m)는 고정 TTL입니다.

코드 확인 수정함 __NULL__ sentinel이 일반 조회 경로와 키를 공유한다

findBookByIdWithNullCaching과 findBookById는 같은 키 book:{id}를 씁니다. 예전엔 sentinel이 저장된 상태에서 findBookById를 부르면 "__NULL__"을 JSON으로 파싱하려다 IllegalStateException("Book deserialization failed")가 났습니다.

수정: findBookById도 sentinel을 먼저 확인해 Optional.empty()(없음 hit, 원본 조회 없음)로 돌려줍니다. 테스트가 sentinel을 남긴 뒤 일반 조회를 호출해 예외 없이 빈 결과와 원본 조회 1회를 확인합니다. 대안(별도 key namespace)의 장단점은 README에 적었습니다.

코드 확인 쓰기·무효화 경로가 없다

README 표는 @CachePut/@CacheEvict의 장점을 소개하지만, 이 모듈에는 책을 수정하고 캐시를 갱신/삭제하는 메서드가 하나도 없습니다. 캐시 일관성(쓰기 후 무효화, race)은 검증되지 않습니다(→ labs/cache-patterns, labs/spring-cache-local).

코드 확인 분산 락의 운영 이슈는 범위 밖
  • 락 연장(lease renewal) 없음: 원본 조회가 3초를 넘기면 락이 풀려 두 번째 요청도 DB를 칠 수 있음(토큰 덕에 남의 락을 지우진 않음).
  • 대기는 Thread.sleep 폴링이라 대기 요청마다 스레드를 붙잡음.
  • 단일 Redis 컨테이너 기준. Redis 장애·복제 지연 시 동작은 다루지 않음.
코드 확인 수정함 README API 표와 실제 사용 범위의 차이

예전 README의 RedisTemplate API 표에는 List(opsForList), Set(opsForSet)이 있었지만 코드에서는 javadoc 주석으로만 언급되고 호출되지 않았습니다. 실제 사용은 String, Hash, Sorted Set(RedisBasicCommandTest)뿐입니다.

수정: README 표를 실제로 호출하는 API(String·setIfAbsent, Hash, Sorted Set, 삭제)만 남기고, List·Set은 "이 모듈에서는 다루지 않음"으로 한 줄 안내했습니다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요. 일반 지식은 이 레포 밖의 널리 알려진 내용입니다.

Spring Cache(@Cacheable)와 RedisTemplate은 언제 각각 쓰나?
  • 일반 메서드 결과 캐싱 → Spring Cache: 본문엔 원본 조회만 남고 GET/SET·직렬화는 RedisCacheManager가.
  • Redis 자료구조(Hash/ZSet), null sentinel, TTL jitter, SET NX/Lua 락 → RedisTemplate.
  • 둘을 섞어 쓰는 게 README의 결론. 단, 같은 키 공간을 공유하면 값 형식 규칙을 맞춰야 함(sentinel 약점 참고).
Redis 캐시 값은 어떻게 직렬화했고, 왜 @class가 들어가나?
  • GenericJackson2JsonRedisSerializer + defaultTyping(true)를 SerializationPair로 감싸 cacheDefaults().serializeValuesWith에 연결. ObjectMapper는 copy()해서 공용 설정 오염 방지.
  • CacheManager는 값을 Object로 다뤄서 타입 정보 없이는 LinkedHashMap으로 복원됨.
  • 일반 지식 JDK 직렬화 대비 사람이 읽을 수 있고 언어 중립적. 대신 @class에 패키지·클래스명이 박혀 리팩터링(이동·이름 변경) 시 기존 캐시 역직렬화가 깨질 수 있어 배포 시 캐시 버전 prefix를 바꾸기도 함.
@Cacheable에서 Optional.empty()는 왜 캐싱되지 않나?
  • Spring Cache는 Optional을 풀어 내부 값을 다루고, empty의 내부 값은 null. unless = "#result == null" + cache-null-values: false로 저장하지 않음.
  • 결과: 없는 id는 매번 원본 조회(테스트: 2회 → readCount 2). 관통을 막으려면 RedisTemplate의 __NULL__ 30초 sentinel처럼 별도 정책 필요.
Null caching에서 TTL을 짧게(30초) 두는 이유는?
  • 나중에 그 id 데이터가 생성되면 sentinel이 새 값을 가림 → 정상 값(10분)보다 짧게.
  • 테스트: 20회 조회에 원본 1회, TTL 1~30초.
  • 일반 지식 생성 시점에 해당 키를 evict하면 TTL에만 의존하지 않아도 됨. 대량 랜덤 키 공격엔 Bloom filter/입력 검증 병행.
Redis로 분산 락을 어떻게 구현했나? 각 요소의 이유는?
  • SET lockKey token NX EX 3: NX로 한 명만 획득(원자적), EX로 소유자가 죽어도 자동 해제.
  • UUID 토큰 + Lua(GET 비교 후 DEL): 내 락만 해제. Java에서 GET/DEL을 따로 하면 그 사이에 락이 바뀔 수 있음.
  • 락 획득 후 double-check: 첫 GET과 락 사이에 다른 요청이 이미 채웠을 수 있음.
  • 결과: 40 동시 요청에 원본 조회 1회(락 없으면 >1).
(꼬리) 원본 조회가 락 TTL(3초)보다 오래 걸리면?
  • 락이 만료돼 다른 요청이 락을 얻고 DB를 또 조회 → 중복 로드. 토큰 덕분에 먼저 끝난 요청이 새 락을 지우지는 않음.
  • 대기 요청은 약 1초 후 empty 반환 → "없음"으로 오해 가능(README 인정).
  • 일반 지식 대응: 작업 시간보다 넉넉한 TTL, 락 자동 연장(Redisson watchdog), 대기 타임아웃 시 원본 직접 조회 또는 별도 예외/상태 반환, 정합성이 중요한 쓰기 락엔 fencing token.
@Cacheable(sync = true)로 핫키 문제를 해결할 수 있나?
  • README: 기본 RedisCacheManager는 non-locking → @Cacheable이 분산 락을 대신하지 않음.
  • 일반 지식 sync = true는 같은 애플리케이션 인스턴스 안에서 같은 키의 동시 로드를 막는 힌트. 서버가 여러 대면 서버 수만큼 로드는 여전히 발생 → 진짜 1회가 필요하면 Redis 락 같은 분산 조정이 필요.
TTL Jitter는 왜 하고, 이 구현의 문제는?
  • 같은 TTL로 대량 적재하면 같은 순간에 만료 → DB 폭주(Avalanche). TTL을 키마다 다르게.
  • 예전 구현: floorMod(key.hashCode(), maxJitter+1) — 결정적이라 테스트하기 쉽지만, 연속 id는 hashCode가 1씩 달라 jitter가 133~137ms로 몰림.
  • 지금 수정함: 해시를 SplitMix64 finalizer로 섞어 결정성을 유지하며 분산. 테스트가 분포 폭(차이 5초 초과, 구간 9개 이상)까지 단언. 대안은 ThreadLocalRandom 난수(대신 같은 key의 TTL이 매번 달라지고 테스트에 시드 주입 필요).
통합 테스트 환경은 어떻게 구성했나?
  • RedisAndMySqlContainerTest: redis:7.2.5(GenericContainer) + mysql:8.0.36을 띄우고 @DynamicPropertySource로 매핑 포트 주입.
  • 매 테스트 전 flushAll로 Redis 비움, 클래스 끝나면 @DirtiesContext(AFTER_CLASS)로 컨텍스트 폐기.
  • @Testcontainers(disabledWithoutDocker = true): Docker 없으면 skip.
  • 원본 지연은 BookOriginService.resetMetrics(Duration)으로 80ms 주입해 동시 miss 창을 넓힘.
