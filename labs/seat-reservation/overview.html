콘서트 좌석 예약 — Redis로 선점하고, Kafka로 DB 쓰기를 떼어 낸다

같은 좌석을 여러 명이 동시에 누르면 한 좌석이 두 명에게 팔리고(동시성 문제), 예매 오픈처럼 요청이 한꺼번에 몰리면 DB가 버티지 못합니다(부하 문제). 이 모듈은 두 문제를 4단계로 쌓아 갑니다: 제어 없음 → Redis SADD 선점 → Redis + Kafka 비동기 확정 → 느린 DB에서 직접 쓰기 vs Kafka 경유 비교.

01한눈에

30초 요약

문제

지켜야 할 불변식 두 개: 이중 배정 금지(한 좌석 = 한 명), 1인 1좌석(한 명 = 한 좌석). 제어 없이 "있나 확인 → 없으면 INSERT"하면 좌석 50개에 예약이 50건보다 많아집니다(README 실행 예 53건).

접근

Redis Set 두 개(seat:applied-users, seat:held-seats)에 SADD해서 "처음 넣은 요청만 1"을 받는 성질로 선점. 선점 성공분만 DB에 확정하되, 3단계에서는 Kafka에 커맨드만 넣고 즉시 응답, Consumer가 DB에 저장.

결론

정합성은 Redis 원자 연산이, 부하 흡수는 Kafka가 맡는 역할 분리. 풀 2·지연 20ms인 느린 DB에서 직접 쓰기는 100건 중 88건 실패, Kafka 경유는 실패 0건으로 즉시 응답하고 결국 100건 모두 확정(README 예시 출력).

한 줄 암기: "누가 좌석을 가졌나"는 Redis SADD가 원자적으로 결정하고, "그 결과를 DB에 적는 일"은 Kafka 뒤로 미뤄 요청 경로에서 뺀다. 대신 비동기 확정 실패는 FailedEvent로 남긴다(재처리는 아직 미구현).

02흐름

단계를 클릭하면 상세 설명이 나옵니다. 최종 구조(케이스 3: Redis + Kafka) 기준이며 실패 경로를 포함합니다.

정상 경로

→ → →

SeatHoldStore.hold()가 먼저 사용자를 seat:applied-users Set에 넣습니다. SADD는 새로 추가됐을 때만 1을 반환하고 Redis는 명령을 하나씩 실행하므로, 동시에 넣어도 1을 받는 요청은 정확히 하나입니다. 새로 추가되면 키 전체 TTL을 hold-ttl-seconds(기본 300초)로 갱신합니다.

이어서 좌석을 seat:held-seats에 SADD. 1이면 이 요청이 좌석을 처음 잡은 것 → ACCEPTED. 이중 배정 금지 불변식을 지키는 지점.

RedisKafkaSeatReservationService는 DB를 건드리지 않고 commandPublisher.publish(userId, seatNo)만 호출하고 바로 반환합니다. 메시지: 키 = 좌석 번호, 값 = "userId|seatNo", 토픽 seat-reservation.

@KafkaListener(groupId = "seat-reservation-confirm")인 SeatReservationConfirmConsumer가 메시지를 꺼내 SeatReservationWriter.save()로 INSERT. DB가 감당할 속도로 소비하니 스파이크는 토픽이 버퍼처럼 받아 둡니다. 테스트는 Awaitility로 DB 건수가 50이 될 때까지(최대 15초) 기다립니다.

실패·예외 경로

· · ·

SADD seat:applied-users {userId}가 0을 반환 = 이 사용자는 이미 어떤 좌석을 선점함 → USER_ALREADY_HAS_SEAT. 1인 1좌석 불변식을 지키는 지점.

사용자는 넣었는데 SADD seat:held-seats {seatNo}가 0 = 다른 사람이 먼저 잡음. 넣어 둔 사용자를 SREM으로 되돌리고 SEAT_ALREADY_TAKEN. 되돌려야 이 사용자가 다른 좌석을 다시 시도할 수 있습니다.

Kafka는 at-least-once라 같은 메시지가 두 번 올 수 있습니다. SeatReservationWriter.save()가 existsBySeatNo || existsByUserId면 저장하지 않고 false 반환(멱등). 테스트: 같은 메시지 2번 전송 → 2초 동안 계속 1건인지 확인.

Consumer가 save() 중 예외를 만나면 catch에서 로그 + failedEventRepository.save(new FailedEvent(...)). 예외를 삼키므로 리스너는 정상 종료 → 오프셋 커밋 → 무한 재시도 방지. 테스트는 30자 좌석 번호(컬럼 길이 20 초과)로 INSERT를 실패시켜 failedEventRepository.count() == 1을 확인. 재처리 배치는 README에 "향후 구현"으로만 있음.

케이스 2. Redis SADD 선점 + 동기 DB 저장 두 불변식 보장

불변식의 본질이 "유니크 멤버십"이라 Set이 자연스럽다는 설계(README). 분산락 SET NX·INCR은 coupon-issue 주제라 여기선 Set.

public SeatReservationStatus hold(long userId, String seatNo) {
    // 1인 1좌석: 사용자를 집합에 추가, 이미 있으면 좌석 보유 중
    if (!added(APPLIED_USERS_KEY, String.valueOf(userId))) {
        return SeatReservationStatus.USER_ALREADY_HAS_SEAT;
    }
    // 이중 배정 방지: 좌석을 집합에 추가, 이미 있으면 선점됨
    if (!added(HELD_SEATS_KEY, seatNo)) {
        redisTemplate.opsForSet().remove(APPLIED_USERS_KEY, String.valueOf(userId));   // 좌석 밀림 → 사용자 되돌림
        return SeatReservationStatus.SEAT_ALREADY_TAKEN;
    }
    return SeatReservationStatus.ACCEPTED;
}

private boolean added(String setKey, String member) {
    Long addedCount = redisTemplate.opsForSet().add(setKey, member);
    boolean isNew = addedCount != null && addedCount == 1L;
    if (isNew) {
        redisTemplate.expire(setKey, holdTtl);   // 키 레벨 TTL (기본 300초)
    }
    return isNew;
}
// RedisSeatReservationService: 선점 성공 시 요청 스레드가 직접 DB 확정
seatReservationWriter.save(userId, seatNo);
return new SeatReservationRequestResult(userId, seatNo, SeatReservationStatus.ACCEPTED);
결과
250 요청 → acceptedCount == 50, takenCount == 200, DB 50건, 좌석마다 정확히 1건. 같은 사용자(9999)가 50좌석을 동시에 노리면 acceptedCount == 1, userBlockedCount == 49.
TTL
Set은 멤버 단위 TTL이 없어 키 전체에 300초 TTL을 겁니다. 선점 후 앱이 죽어도 집합이 영원히 남지 않게 하려는 장치. 좌석별 정밀 TTL이 필요하면 키 1개 = 좌석 1개인 SET NX EX가 맞다고 클래스 주석에 적혀 있습니다. (README 스니펫에는 이 TTL 코드가 빠져 있음)
한계 (README)
요청 경로에 DB 쓰기가 결합 → 트래픽이 몰리면 DB 지연이 요청으로 전파. Redis 상태는 메모리라 내구성 기준이 아님(선점 후 DB 확정 전 앱이 죽으면 좌석만 잡힘).

케이스 3. Redis + Kafka 비동기 확정 요청 경로에서 DB 제거

// 요청 측: RedisKafkaSeatReservationService
public SeatReservationRequestResult reserve(long userId, String seatNo) {
    SeatReservationStatus status = seatHoldStore.hold(userId, seatNo);
    if (status != SeatReservationStatus.ACCEPTED) {
        return new SeatReservationRequestResult(userId, seatNo, status);
    }
    commandPublisher.publish(userId, seatNo);
    return new SeatReservationRequestResult(userId, seatNo, SeatReservationStatus.ACCEPTED);
}

// 프로듀서: 좌석 번호를 메시지 키로
kafkaTemplate.send(TOPIC, seatNo, new SeatReservationCommand(userId, seatNo).serialize());

// 기록기: 좌석/사용자 단위 멱등
@Transactional
public boolean save(long userId, String seatNo) {
    if (seatReservationRepository.existsBySeatNo(seatNo) || seatReservationRepository.existsByUserId(userId)) {
        return false;
    }
    simulateSlowDb();     // seat.db.write-delay-millis (기본 0)
    seatReservationRepository.save(new SeatReservation(seatNo, userId));
    return true;
}
결과
250 요청 → acceptedCount == 50, Awaitility로 최대 15초 기다려 DB 50건·좌석마다 1건. 중복 메시지 테스트: 같은 메시지 2번 → 1건 유지(2초간 during으로 확인).
왜 Kafka
요청은 Redis 선점 + publish까지만 → DB 대기 없음. Consumer가 DB 속도로 소비 → 스파이크 흡수. Kafka 로그는 내구성이 있어 앱이 죽어도 커맨드가 남음 (README).
설정 게이팅
KafkaTopicConfig, Consumer는 @ConditionalOnProperty(seat.kafka.enabled=true). 토픽은 partitions(1), replicas(1).

05한계·약점

README가 스스로 밝힌 한계와, 코드에서 확인되는 약점. 면접관이 파고들 수 있는 지점입니다.

README 명시

  • FailedEvent 재처리 배치는 향후 구현 — README의 @Scheduled retryFailedEvents()는 예정안이고 코드에 없음.
  • 버스트 테스트는 구조적 인과만 재현. 실제 RDB 장애 재현은 nGrinder·AWS 같은 실부하 환경 필요.
  • 케이스 2: 요청 경로·DB 쓰기 결합, Redis 선점 상태는 내구성 기준이 아님.
  • 예시 수치는 환경에 따라 달라짐.

코드 분석 README에 없거나 다른 점

Kafka 발행 결과를 확인하지 않는다 → 발행 실패 시 Redis 선점만 남음

SeatReservationCommandPublisher.publish()는 kafkaTemplate.send(...)의 반환(future)을 버립니다. 브로커 장애로 발행이 실패해도 요청은 이미 ACCEPTED를 받았고, Redis에는 좌석·사용자가 잡혀 있지만 DB 예약은 영영 생기지 않습니다. 버스트 테스트의 "Kafka 실패 0건"도 동기적으로 던져진 예외만 센 것입니다.

개선 일반 지식: 발행 결과 확인 후 실패 시 Redis 선점 되돌리기, 또는 Transactional Outbox 패턴.

README는 "좌석 키로 같은 파티션에서 순서 처리"라 하지만 토픽은 partitions(1)

KafkaTopicConfig가 .partitions(1)로 토픽을 만듭니다. 파티션이 하나라 모든 메시지가 한 줄로 처리되고, 좌석 키에 따른 파티셔닝 효과는 이 실험에서 관찰되지 않습니다. 반대로 말하면 지금의 멱등 체크가 안전한 이유도 "Consumer 스레드가 하나"이기 때문일 수 있습니다(아래 항목).

DB에 unique 제약이 없다 — 멱등성이 exists 체크에만 의존

SeatReservation의 seat_no, user_id에 unique 제약이 없습니다. SeatReservationWriter.save()의 exists → save는 케이스 1과 같은 check-then-act라, 파티션·Consumer를 늘려 동시에 처리하면 중복 저장이 가능해집니다. 최후 방어선으로 unique 인덱스 + 위반 예외 처리가 필요합니다.

save()의 false(거절) 반환을 호출부가 무시한다

RedisSeatReservationService는 seatReservationWriter.save(...)의 반환값을 보지 않고 무조건 ACCEPTED를 돌려줍니다. 예: Redis 키가 TTL(300초)로 통째로 사라진 뒤 새 요청이 같은 좌석을 선점하면, DB에는 이미 다른 사람 예약이 있어 저장은 거절되는데 응답은 성공입니다. Consumer도 반환값을 기록하지 않습니다.

직접 쓰기 실패 시 Redis 선점을 되돌리지 않는다

케이스 2 경로에서 DB 저장이 예외(예: 커넥션 타임아웃)로 실패하면 SeatHoldStore의 좌석·사용자는 그대로 남습니다. 버스트 테스트의 실패 88건(README 예시)은 TTL이 만료될 때까지 좌석이 "잡혔지만 아무도 없는" 상태가 됩니다.

두 번의 SADD + SREM이 원자적이지 않다

사용자 SADD → 좌석 SADD → (실패 시) SREM이 별도 명령입니다. 그 사이 같은 사용자의 다른 요청은 USER_ALREADY_HAS_SEAT로 거절될 수 있는데, 정작 첫 요청은 좌석 선점에 실패해 사용자가 아무 좌석도 못 가질 수 있습니다(거짓 거절). 불변식 위반(이중 배정)은 아니지만 공정성 문제. Lua 스크립트로 묶으면 해결 일반 지식.

TTL이 README 스니펫에 없고, 키 전체가 한꺼번에 만료된다

코드에는 @Value("${seat.redis.hold-ttl-seconds:300}")와 expire(setKey, holdTtl)가 있지만 README의 선점 코드에는 없습니다. 새 멤버가 추가될 때마다 TTL을 갱신하므로, 마지막 추가 후 300초가 지나면 모든 좌석·사용자 선점이 동시에 사라집니다. 그 뒤엔 DB 확정 여부와 무관하게 Redis가 다시 선점을 허용합니다.

파싱 실패는 FailedEvent로 가지 않는다

SeatReservationCommand.parse(message)는 try 바깥에 있어, 형식이 잘못된 메시지는 catch되지 않고 리스너 밖으로 예외가 나갑니다(spring-kafka 기본 에러 핸들러로 처리). 테스트의 독성 메시지는 형식은 맞고 길이만 넘는 경우입니다.

케이스 1 단언은 비결정적

isGreaterThan(SEATS)는 경합이 실제로 일어나야 통과합니다. Thread.yield()와 인접 인덱스 배치로 확률을 높였을 뿐 보장은 아닙니다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

좌석 선점에 왜 분산락(SET NX)이 아니라 Redis Set(SADD)을 썼나요?
  • 불변식이 "좌석은 한 번만, 사용자도 한 번만" = 유니크 멤버십. SADD는 새로 추가될 때만 1을 반환 → 그 자체가 원자적 선점 판정. 락을 잡고 풀 필요가 없음.
  • 두 불변식을 Set 두 개로 각각 표현: seat:applied-users, seat:held-seats.
  • 트레이드오프: Set은 멤버별 TTL이 없어 키 전체 TTL만 가능. 좌석별 만료가 필요하면 좌석당 키 SET NX EX가 맞음(코드 주석).
Kafka를 넣으면 무엇이 좋아지고, 무엇을 대가로 치르나요?
  • 좋아지는 것: 요청 경로에서 DB 쓰기 제거 → 느린 DB에서도 즉시 응답(README 예시: 직접 쓰기 실패 88건 vs Kafka 0건). 스파이크를 토픽이 버퍼링. 커맨드가 로그에 남아 내구성.
  • 대가: 최종 일관성(응답 시점엔 DB에 아직 없음, 예시에서 확정까지 3,780ms). at-least-once라 멱등 처리 필요. 확정 실패 처리(FailedEvent, 재처리) 필요. 운영 구성요소 증가.
Kafka 메시지가 중복으로 오면 어떻게 하나요? exactly-once는?
  • 이 모듈: Consumer 측 멱등 — existsBySeatNo || existsByUserId면 저장 안 함. 테스트로 중복 2건 → 1건 유지 확인.
  • 약점: unique 제약이 없어 동시 처리 시 깨질 수 있음 → 운영이면 unique 인덱스로 DB가 최종 보장하게.
  • 일반 지식 Kafka의 idempotent producer·트랜잭션은 Kafka 내부 exactly-once이고, 외부 DB 쓰기까지 포함하면 결국 Consumer 멱등이 필요.
Redis에서 선점은 됐는데 Kafka 발행이나 DB 확정이 실패하면?
  • DB 확정 실패: Consumer가 catch → FailedEvent 저장 → 오프셋 커밋(무한 재시도 방지). 재처리 배치는 README상 향후 구현.
  • 발행 실패: 현재 코드는 send() 결과를 확인하지 않아 감지 불가 → 개선 필요. 결과 콜백에서 실패 시 Redis 선점 롤백, 또는 Outbox 패턴 일반 지식.
  • 최후 안전망: 키 TTL 300초로 선점이 영원히 남지는 않음.
FailedEvent 테이블 대신 Kafka의 다른 방법은 없나요?
  • 일반 지식 spring-kafka의 DefaultErrorHandler + 재시도 후 Dead Letter Topic(DLT) 발행, 또는 retry topic 패턴.
  • DB 테이블 방식의 장점: 조회·수동 처리 쉬움. 단점: DB 자체가 장애면 FailedEvent 저장도 실패할 수 있음.
버스트 테스트에서 직접 쓰기는 왜 88건이나 실패했나요?
  • Hikari 풀 2, connection-timeout 250ms, 쓰기마다 20ms 지연인데 100개 스레드가 동시에 커넥션을 요구 → 대부분 250ms 안에 커넥션을 못 받아 예외.
  • Kafka 경유는 요청 스레드가 커넥션을 쓰지 않으므로 풀 고갈과 무관. Consumer 하나가 커넥션을 순서대로 사용.
  • 교훈: 동기 구조에서는 DB 처리량이 곧 요청 처리량의 상한.
Redis가 죽으면 이 구조는 어떻게 되나요?
  • 선점 판정을 할 수 없어 예약이 막힘(현재 코드에 대체 경로 없음). Redis 상태는 메모리라 재시작 시 선점 정보 유실 가능 → README도 "Redis 카운트는 내구성 기준이 아님"이라 명시.
  • 진실의 원천은 DB여야 하고, Redis는 빠른 1차 필터. 그래서 DB unique 제약이 필요.
  • 일반 지식 복제·Sentinel/Cluster, AOF 등으로 가용성·내구성 보완.
좌석 키로 메시지를 보내면 순서가 보장된다고 했는데, 파티션을 늘리면 무엇을 확인해야 하나요?
  • 같은 키는 같은 파티션 → 같은 좌석 커맨드끼리는 순서 유지 일반 지식. 현재는 partitions(1)이라 실험에선 의미가 드러나지 않음.
  • 파티션·Consumer 동시성을 늘리면 다른 좌석이지만 같은 사용자의 커맨드가 다른 파티션에서 동시에 처리될 수 있음 → existsByUserId 체크가 경합. user_id unique 제약 필요.
SADD 두 번과 SREM 롤백을 Lua로 묶어야 할까요?
  • 지금도 이중 배정·1인 1좌석은 깨지지 않음(각 SADD가 원자적). 다만 중간 상태 때문에 같은 사용자의 다른 요청이 잘못 거절될 수 있음.
  • Lua로 "사용자·좌석 둘 다 없을 때만 둘 다 추가"를 원자 실행하면 중간 상태와 롤백 코드가 사라지고 네트워크 왕복도 줄어듦 (coupon-issue의 Lua 케이스와 같은 아이디어).
