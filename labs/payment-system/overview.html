payment-system: 한 트랜잭션으로 묶을 수 없는 결제를 상태·아웃박스·멱등성으로 맞추기

결제(Payment) → 정산(Wallet) → 장부(Ledger)를 서로 다른 DB와 Kafka로 나눈 결제 시스템입니다. 외부 PSP(Toss) 호출이 끼어 있어서 전체를 한 트랜잭션으로 묶을 수 없습니다. 그래서 각 서비스는 로컬 트랜잭션만 쓰고, 그 사이를 트랜잭셔널 아웃박스·재시도·멱등 소비자로 이어 "결국에는 맞는" 상태를 만들려고 합니다.

01한눈에

30초 요약. 아래 그림은 서비스 3개가 Kafka 토픽 3개로 이어지는 전체 구조입니다.

문제

PSP 승인, 결제 DB 커밋, Kafka 발행, 정산, 장부는 서로 다른 시스템에서 일어납니다. 그래서 하나만 실패해도 돈은 빠졌는데 주문은 실패하거나 정산은 됐는데 장부가 비는 어긋남이 생길 수 있습니다.

접근

결제 상태를 5개로 나눕니다(NOT_STARTED·EXECUTING·SUCCESS·FAILURE·UNKNOWN). 성공하면 같은 트랜잭션 안에서 outbox에 이벤트를 쓰고, 커밋된 뒤에 Kafka로 보냅니다. 받는 쪽은 orderId로 중복을 거르고, 지갑은 낙관적 락, 장부는 복식부기로 기록합니다.

결론

핵심 흐름(승인 → 아웃박스 → 정산·장부 → 완료)은 실제로 구현되어 있습니다. 처음 분석에서 찾은 구멍(돌지 않던 복구·릴레이 스케줄러, 상태 전이 경쟁, 완료 판정 레이스, 비어 있던 정산 데이터, check-then-act 멱등성 등)은 수정함 표시처럼 고쳤고, 테스트는 Testcontainers로 CI에서 돕니다. DLQ 재처리·Bulkhead·대사는 아직 없습니다. 면접에서는 "설계 의도 + 찾은 구멍 + 어떻게 고쳤나"를 한 세트로 말하면 됩니다.

서비스 구조: Payment → Kafka → Wallet / Ledger → 다시 Payment

  1. 1 브라우저가 Toss 결제창 인증을 마치면 POST /v1/toss/confirm을 호출합니다.
  2. 2 Payment가 Toss 승인 API를 부릅니다. 이때 Idempotency-Key: orderId 헤더를 붙이고, 실패하면 재시도합니다.
  3. 3 승인에 성공하면 같은 DB 트랜잭션에서 outbox에 행을 쓰고, 커밋한 뒤에 payment 토픽으로 발행합니다.
  4. 4 Wallet과 Ledger는 서로 다른 consumer group이라 같은 메시지를 각자 한 번씩 받습니다.
  5. 5 처리를 마치면 각자 wallet / ledger 토픽에 SUCCESS를 보냅니다.
  6. 6 Payment가 두 메시지를 받아 wallet_updated·ledger_updated를 세우고, 둘 다 서 있으면 is_payment_done을 세웁니다.
근거: payment-service/src/main/resources/application.yml(바인딩 send-out-0/wallet-in-0/ledger-in-0), wallet-service/src/main/resources/application.yml, ledger-service/src/main/resources/application.yml

왜 필요한가: PSP를 부르기 전에 "승인 시도 중"이라는 사실을 DB에 남겨야 합니다. 그래야 호출 도중 서버가 죽어도 복구 작업이 그 건을 찾아낼 수 있습니다.

return lockPaymentOrders(orderId)                 // SELECT ... FOR UPDATE (주문 행 잠금)
        .flatMap(paymentOrders -> {
            if (paymentOrders.isEmpty()) return Mono.error(new PaymentNotFoundException(orderId));
            PaymentStatus blocking = firstStatusOutside(paymentOrders, CONFIRMABLE);  // NOT_STARTED·UNKNOWN 만 허용
            if (blocking != null) return Mono.error(alreadyProcessed(blocking));      // SUCCESS·FAILURE·EXECUTING
            return insertPaymentHistory(paymentOrders, EXECUTING, "PAYMENT_CONFIRMATION_START")
                    .then(updatePaymentOrderStatus(orderId, EXECUTING, CONFIRMABLE))  // WHERE status IN (...)
                    .then(updatePaymentKey(orderId, paymentKey));
        })
        .as(transactionalOperator::transactional)
        .thenReturn(true);

현재 상태가 SUCCESS나 FAILURE이면 PaymentAlreadyProcessedException을 던집니다. 수정함 예전에는 EXECUTING도 통과시켜 같은 건에 대한 동시 confirm이 모두 PSP까지 갔습니다. 지금은 주문 행을 FOR UPDATE로 잠그고 NOT_STARTED·UNKNOWN에서만 넘어가므로, 뒤에 온 요청은 앞 요청이 커밋한 EXECUTING을 보고 PSP를 부르지 않고 EXECUTING("처리 중") 응답을 받습니다. 주문이 없으면 PaymentNotFoundException입니다. 멈춘 EXECUTING은 사용자 재요청이 아니라 복구 스케줄러가 이어받습니다. 확실

왜 필요한가: PSP 호출은 네트워크를 타기 때문에 일시적으로 실패할 수 있습니다. 다시 시도하면 성공할 수도 있지만, 잘못 재시도하면 두 번 결제될 수 있습니다.

TossPaymentExecutor는 POST /v1/payments/confirm을 호출하면서 Basic 인증(secretKey:)과 Idempotency-Key: orderId 헤더를 붙입니다. 응답이 4xx나 5xx이면 code를 TossPaymentError로 바꿔 PSPConfirmationException을 던집니다. 그다음 Retry.backoff(2, 1s).jitter(0.1)가 retryable(=UNKNOWN 계열)이거나 netty TimeoutException인 경우만 최대 2회 다시 시도합니다. 읽기 타임아웃은 ReadTimeoutHandler(30s)입니다. 확실

수정함 응답이 ALREADY_PROCESSED_PAYMENT면 Toss 결제 조회 GET /v1/payments/{paymentKey}(같은 시크릿 키 인증)로 Payment 객체를 받아, orderId·금액·status=DONE이 맞을 때만 승인 상세가 있는 정상 SUCCESS로 바꿉니다. 조회가 실패하거나 맞지 않으면 UNKNOWN으로 남겨 복구에 맡깁니다. 조회 응답이 승인 응답과 같은 Payment 객체라는 점은 Toss 문서에 기댄 추정입니다. 모르는 결제수단·타입은 예외 대신 UNKNOWN으로 매핑하고 경고 로그를 남깁니다.

왜 필요한가: "실패"에도 종류가 있습니다. 카드 한도 초과처럼 확실히 실패한 경우가 있고, 타임아웃처럼 돈이 빠졌는지 알 수 없는 경우가 있습니다. 둘째를 FAILURE로 처리하면 "돈은 빠졌는데 주문은 실패"가 됩니다.

왜 필요한가: UNKNOWN이거나 EXECUTING에서 멈춘 건은 누군가 다시 확인하지 않으면 영원히 그 상태로 남습니다.

PaymentScheduler가 3분마다(fixedDelay PT3M) PaymentRecoveryService.recovery()를 부르고 끝날 때까지 기다립니다. 대상은 UNKNOWN이거나, EXECUTING이면서 updated_at이 3분 넘게 지났고, failed_count < threshold(5)인 결제이며 결제 단위로 10건을 가져옵니다. 건마다 EXECUTING으로 선점(조건부 UPDATE) → 검증 → PSP 재호출(같은 Idempotency-Key) → 상태 갱신 순으로, 동시에 2건씩 처리합니다.

왜 커밋 후인가: 커밋 전에 보냈는데 커밋이 롤백되면 "없는 결제"가 정산됩니다. 그래서 @TransactionalEventListener(AFTER_COMMIT)에서 보냅니다.

A7에서 등록한 이벤트를 커밋 직후 dispatchAfterCommit이 받습니다. 이것을 Sinks.many().unicast()에 넣으면 Supplier send() 바인딩(send-out-0 → 토픽 payment)이 흘려보냅니다. 헤더는 CORRELATION_ID = orderId, KafkaHeaders.PARTITION = abs(orderId.hashCode()) % 6입니다. 확실 리액티브 트랜잭션에서 AFTER_COMMIT 리스너가 호출되는 방식은 Spring 6.1의 TransactionalEventPublisher 동작에 기대는 부분이라 추정입니다. 지금은 Testcontainers Kafka 테스트가 "커밋 → 발행 → outbox SUCCESS"를 실제로 확인합니다.

수정함 예전 설정 키(spring.cloud.stream.function.definition)는 Spring Cloud Stream 4.x가 읽지 않아 바인딩이 하나도 생기지 않았습니다. spring.cloud.function.definition으로 바꿨습니다. 동시에 여러 스레드가 emitNext하면 FAIL_FAST가 FAIL_NON_SERIALIZED로 실패하던 것도 busyLooping으로 바꿨습니다.

왜 필요한가: 커밋은 됐는데 AFTER_COMMIT 발행 직전에 서버가 죽으면 outbox 행은 INIT으로 남습니다. 이것을 주기적으로 다시 보내는 것이 아웃박스 패턴의 핵심 안전망입니다.

WHERE (status = 'INIT' OR status = 'FAILURE')

결제 완료: 두 소비자의 응답을 모아 is_payment_done 수정함

복구·릴레이 스케줄러가 실제로는 한 번도 돌지 않는다 확실 수정함

레포 어디에도 @EnableScheduling이 없어서 @Scheduled가 무시됩니다. 게다가 두 서비스 모두 @Profile("dev")인데 dev 프로필을 켜는 설정이 없어서 빈 자체가 만들어지지 않습니다. 그 결과 UNKNOWN이나 멈춘 EXECUTING은 회복되지 않고, AFTER_COMMIT 발행에 실패한 outbox는 영원히 INIT으로 남습니다.

개선 방향: 설정 클래스에 @EnableScheduling을 추가하고 프로필 조건을 운영에서도 켜지게 바꿉니다. 여러 인스턴스로 띄울 때는 ShedLock 같은 분산 락이나 SELECT … FOR UPDATE SKIP LOCKED로 중복 실행을 막습니다. 마지막 실행 시각과 처리 건수를 메트릭으로 노출해 "안 도는 스케줄러"를 탐지합니다.

수정함 @Profile("dev")를 없애고, 인바운드 어댑터 PaymentScheduler(@EnableScheduling + @ConditionalOnProperty(payment.scheduler.enabled, 기본 true))가 두 유스케이스를 3분마다 부릅니다. 유스케이스는 Mono를 돌려주고 스케줄러가 block으로 기다려 회차가 겹치지 않습니다. 다중 인스턴스 중복은 복구 쪽 선점 UPDATE로 막고, 릴레이는 at-least-once라 소비자 멱등성에 맡깁니다. 실행 메트릭은 아직 없습니다.

Toss가 ALREADY_PROCESSED_PAYMENT를 주면 SUCCESS로 저장하려다 예외가 난다 확실 수정함

TossPaymentError.isSuccess()는 이 코드만 true입니다. 그래서 에러 핸들러가 status = SUCCESS, extraDetails = null로 PaymentStatusUpdateCommand를 만들고, 생성자가 "SUCCESS면 extraDetails 필수" 규칙으로 IllegalArgumentException을 던집니다. 결과적으로 응답은 500이 되고 상태는 EXECUTING이나 UNKNOWN에 머뭅니다. 바로 "응답을 잃어버린 뒤 재시도" 시나리오에서 터지는 구멍입니다.

수정함 TossPaymentExecutor가 이 코드를 받으면 결제 조회(GET /v1/payments/{paymentKey}, 같은 Basic 인증)를 불러, orderId·금액이 같고 status가 DONE일 때만 승인 상세가 있는 정상 SUCCESS로 바꿉니다. 조회 실패나 불일치는 UNKNOWN으로 남겨 복구에 맡깁니다. 조회 응답이 승인 응답과 같은 Payment 객체라는 점은 Toss 문서에 기댄 추정이라 같은 응답 레코드를 재사용합니다. 그래도 상세 없는 성공 신호가 핸들러까지 오면 예외 대신 UNKNOWN으로 기록합니다.

결제수단 enum이 EASY_PAY 하나뿐: 승인 후 매핑 실패로 UNKNOWN 확실 일부 추정 수정함

PaymentMethod.get은 응답의 method 문자열이 "간편결제"일 때만 성공하고, 나머지는 IllegalStateException을 던집니다(PaymentType도 NORMAL만 허용). 이 예외는 Toss가 이미 승인한 뒤 응답을 매핑하다 나므로 "그 외 예외" → UNKNOWN이 됩니다. 이후 재시도하면 Toss가 ALREADY_PROCESSED_PAYMENT를 줄 것이고(추정), 바로 위 버그 때문에 영영 SUCCESS가 되지 못합니다. 카드 결제 응답의 method가 "카드"라는 점은 Toss API에 대한 추정입니다.

수정함 PaymentMethod에 Toss 값 8개(카드·가상계좌·간편결제·휴대폰·계좌이체·문화상품권·도서문화상품권·게임문화상품권), PaymentType에 NORMAL·BILLING·BRANDPAY를 넣고, 모르는 값은 예외 대신 UNKNOWN으로 매핑하고 경고 로그를 남깁니다. CULTURE_GIFT_CERTIFICATE(24자)가 VARCHAR(20)에 안 들어가서 method 컬럼을 VARCHAR(50)으로 넓혔습니다(기존 DB는 멱등 ALTER … MODIFY).

복구 쿼리의 LIMIT 10이 주문 '행' 단위라 결제가 잘려 FAILURE로 오판될 수 있다 확실 수정함

LIMIT 10은 payment_orders 조인 행에 걸리고 ORDER BY도 없습니다. 한 결제의 주문 행이 일부만 들어오면 totalAmount가 작아지고, isValid가 금액 불일치를 던져 FAILURE로 확정됩니다. 실제로는 PSP가 승인했을 수도 있는 건입니다.

수정함 대상 payment_event_id를 파생 테이블에서 ORDER BY … LIMIT 10으로 먼저 뽑고, 그 결제의 주문 전부를 다시 조인합니다. 시각 비교도 DB 시계(NOW())로 바꿨습니다. 복구 경로에서 재승인 대신 PSP 조회를 먼저 하는 것은 아직 아닙니다(ALREADY_PROCESSED 응답일 때만 조회).

근거: payment-service/src/main/java/dev/deepdive/paymentsystem/payment/adapter/out/persistent/repository/R2DBCPaymentRepository.java

최종 상태 전이가 이전 상태를 확인하지 않고, EXECUTING 중 동시 confirm도 통과한다 확실 수정함

updatePaymentStatusToSuccess/Failure/Unknown은 WHERE order_id = ?로 무조건 덮어씁니다. 늦게 끝난 요청이 SUCCESS를 UNKNOWN으로 덮는 것도 가능합니다. 진입 검사도 EXECUTING을 허용하므로, 같은 건에 동시 요청 두 개가 모두 PSP까지 갑니다(이중 승인은 Idempotency-Key로 막힌다는 전제, 추정). 덧붙여 존재하지 않는 orderId는 EXECUTING 전이가 0행으로 "성공"하고, SUM(amount)가 NULL이라 NPE가 나서 UNKNOWN 응답을 받습니다.

수정함 모든 전이가 한 트랜잭션에서 SELECT … FOR UPDATE로 주문 행을 잠그고 이전 상태를 확인한 뒤, WHERE payment_order_status IN (…) 조건부 UPDATE를 합니다. 최종 상태는 EXECUTING·UNKNOWN에서만, confirm 선점은 NOT_STARTED·UNKNOWN에서만 허용합니다. 이미 SUCCESS·FAILURE면 덮어쓰지 않고 no-op, 처리 중(EXECUTING)인 결제의 재요청은 PSP를 부르지 않고 EXECUTING으로 응답합니다. 복구는 UNKNOWN·3분 넘은 EXECUTING만 선점합니다. 없는 orderId는 DB에 쓰지 않고 PAYMENT_NOT_FOUND FAILURE입니다. 동시 confirm 8개 → PSP 1회를 테스트로 확인합니다.

failed_count가 threshold에 닿으면 UNKNOWN인 채 방치된다 확실

조회 조건이 failed_count < threshold뿐이라 한도를 넘긴 건은 조용히 빠지고, 알림이나 다른 처리가 없습니다.

개선 방향: 한도를 넘으면 NEEDS_MANUAL_REVIEW 같은 상태나 별도 테이블로 옮기고 알림을 보냅니다. 대사 작업이 PSP 정산 파일과 대조해 최종 상태를 확정합니다.

메시지·소비자

wallet·ledger가 읽는 로컬 payment_orders를 채우는 코드가 없다 확실 수정함

두 서비스 모두 자기 DB의 payment_orders를 orderId로 조회합니다. 하지만 메시지 payload에는 orderId만 있고, 이 테이블에 INSERT하는 코드는 어디에도 없습니다(wallet은 schema.sql에도 테이블이 없고 ddl-auto: update로만 생깁니다). 그래서 실제로 돌리면 정산·기장이 0건인데 SUCCESS 메시지가 나가고, 결제는 "완료"로 표시됩니다. 테스트는 이 조회를 mock으로 대체해 이 문제를 가립니다.

수정함 Event-carried state transfer로 바꿨습니다. outbox payload에 paymentOrders[{paymentOrderId, sellerId, productId, amount}]와 totalAmount를 싣고(metadata payloadVersion: 2), wallet·ledger는 payload만 읽습니다. 로컬 payment_orders 테이블·엔티티·포트는 지웠습니다. 주문 라인이 없는 예전 형식이나 합계가 맞지 않는 메시지는 예외 → 재시도 → DLQ로 격리됩니다(호환성 메모는 README).

지갑이 없는 판매자는 조용히 건너뛴다 확실 수정함

getUpdatedWallets는 찾은 지갑만 순회합니다. 주문에 판매자가 있어도 지갑 행이 없으면 그 금액은 정산되지 않은 채 SUCCESS가 됩니다.

수정함 지갑이 없는 판매자가 하나라도 있으면 WalletNotFoundException으로 정산 전체를 실패시킵니다. 메시지는 재시도 후 DLQ로 가고(테스트로 확인), 지갑을 만든 뒤 재처리합니다. 대사는 아직 없습니다.

소비자 멱등성이 check-then-act라 동시 재전달에 뚫린다 확실 수정함

existsByOrderId → 처리 → 저장 사이에 원자성이 없고 유니크 제약도 없습니다. 같은 메시지가 리밸런스 등으로 두 컨슈머에 동시에 들어가면 이중 정산이나 이중 기장이 됩니다.

수정함 wallet_transactions·ledger_transactions의 idempotency_key에 UNIQUE를 걸고(schema + JPA), 키를 orderId·참조 종류·참조 id(+wallet은 방향)로 만듭니다. 잔액 갱신·거래 INSERT가 같은 트랜잭션이라, 중복 키 위반이면 통째로 롤백되고 "이미 처리됨" 성공으로 응답합니다. existsByOrderId는 빠른 길로만 남겼습니다. INSERT를 키 순으로 정렬하고 교착 희생은 재시도합니다. 동시 6개 → 1번 반영을 테스트로 확인합니다.

결제 완료 판정에 레이스가 있어 is_payment_done이 영구 0일 수 있다 확실 수정함

③ "결제 완료" 탭의 타임라인처럼, wallet과 ledger 메시지가 같은 스냅샷을 읽으면 둘 다 "아직 아님"으로 판단합니다. 이 판단은 메모리에서 하고, UPDATE는 트랜잭션 없이 나뉘어 나갑니다.

수정함 한 트랜잭션에서 자기 플래그 UPDATE → "모든 주문의 두 플래그가 1"을 조건으로 한 is_payment_done UPDATE를 실행합니다(③ 탭의 SQL). 메모리 판정과 LoadPaymentPort는 지웠습니다. 동시 도착 테스트(15건 × 3회)로 확인합니다.

라이브러리 동작에 기대는 부분들 추정
  • 타임아웃 재시도 필터: WebClient는 요청 단계의 I/O 오류를 WebClientRequestException으로 감쌉니다. 그래서 instanceof TimeoutException이 맞지 않아 즉시 재시도가 안 될 수 있습니다(에러 분류도 "그 외" → UNKNOWN). 개선: Exceptions.unwrap이나 cause 체인을 검사합니다.
  • unicast sink + FAIL_FAST: 여러 스레드가 동시에 emitNext하면 FAIL_NON_SERIALIZED로 발행에 실패할 수 있습니다. 수정함 EmitFailureHandler.busyLooping(2s)로 바꿨습니다.
  • Kafka 트랜잭션과 DB 트랜잭션이 따로: wallet·ledger는 transaction-id-prefix를 설정했지만, JPA 저장(TransactionTemplate, saveAll)과 streamBridge.send가 하나로 묶여 있지 않습니다. 실제로는 "DB 커밋 → 발행"이고, 발행에 실패하면 재전달과 멱등성 검사에 기대게 됩니다.
  • 리액티브 소비자 에러: payment의 wallet()/ledger()는 Flux 전체를 받는 함수라서, 하나의 에러가 스트림을 끝내 이후 메시지를 못 받을 수 있습니다. 이때 max-attempts나 DLQ 같은 바인더 재시도가 적용되지 않을 수 있습니다. 개선: 요소마다 onErrorResume을 두고 실패 메시지를 직접 DLQ로 보냅니다.
  • 파티션 계산: Math.abs(Integer.MIN_VALUE)는 음수라서 해시가 정확히 그 값이면 음수 파티션이 나옵니다(Java 일반 지식, 확률은 극히 낮음). 개선: Math.floorMod를 쓰거나 메시지 key를 orderId로 줘서 Kafka 기본 파티셔너에 맡깁니다.
Kafka 함수 바인딩이 하나도 생기지 않았다 (설정 키 오류) 확실 수정함

payment는 함수 빈이 셋(send, wallet, ledger)이라 함수 정의를 명시해야 하는데, yml이 Spring Cloud Stream 4.x가 읽지 않는 spring.cloud.stream.function.definition을 썼습니다. 그래서 "Multiple functional beans" 경고와 함께 바인딩이 하나도 생기지 않아 발행도, 완료 이벤트 소비도 되지 않았습니다. 테스트가 전부 태그로 빠지거나 sleep만 해서 드러나지 않았습니다. Testcontainers Kafka 테스트를 붙이자 바로 잡혔습니다.

수정함 spring.cloud.function.definition: send;wallet;ledger로 바꿨습니다. 같이 확인한 운영 메모: 바인더는 DLQ에도 원래 레코드와 같은 파티션 번호로 보내므로 payment_*_dlq 토픽은 payment(6)만큼 파티션이 있어야 합니다.

테스트가 CI에서 하나도 돌지 않고, 일부는 assert가 없다 확실 수정함

10개 클래스 전부 ExternalIntegration 태그라 기본 빌드에서 제외됩니다. Recovery, Relay, Confirm의 Kafka 테스트는 Thread.sleep(10000)만 있고 무엇도 검증하지 않습니다. Testcontainers 의존성은 선언만 되어 있습니다.

수정함 서비스마다 Testcontainers 싱글톤 기반 클래스(MySQL 8.0.36 + apache/kafka 3.8.1, @DynamicPropertySource)를 두고 태그를 뗐습니다. sleep 테스트는 결과 assert(Awaitility 포함)로 바꿨고, 동시성 테스트(완료 집계, 중복 confirm, 소비자 중복)와 단위 테스트(PSP 응답 매핑, 결제수단, 미존재 주문, 복식부기 불변식, 백오프, 스케줄러)를 추가했습니다. 실제 Toss를 부르는 테스트만 ExternalIntegration으로 남았습니다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요. 일반 지식 표시는 이 레포 밖의 일반 개념입니다.

결제·정산·장부를 왜 하나의 트랜잭션(또는 2PC)으로 묶지 않았나요?
  • 서비스마다 DB가 다르고(payment_db / wallet_db / ledger_db), 그 사이에 외부 PSP(Toss)가 있습니다. Toss는 우리 트랜잭션 코디네이터에 참여할 수 없으니 2PC는 처음부터 불가능합니다.
  • 2PC는 코디네이터가 장애 나면 참여자가 락을 쥔 채 블로킹되고, 모든 참여자가 XA를 지원해야 하며, 가장 느린 참여자에 맞춰 지연이 늘어납니다. 일반 지식 이 문제는 같은 레포의 distributed-transaction-2pc 실험에서 다룹니다.
  • 그래서 각자 로컬 트랜잭션만 쓰고, 아웃박스 + 멱등 소비자 + 재시도로 최종 일관성을 노렸습니다. 대가는 중간 상태가 보인다는 것(SUCCESS인데 아직 is_payment_done=0)과 대사가 꼭 필요하다는 것입니다.
트랜잭셔널 아웃박스가 뭔가요? 이 프로젝트에선 어떻게 구현했나요?
  • "DB 커밋 + 메시지 발행"이라는 dual write 문제의 해법입니다. 이벤트를 같은 DB의 outbox 테이블에 같은 트랜잭션으로 써서 원자성을 확보하고, 발행은 나중에 합니다.
  • 구현: updatePaymentStatusToSuccess 한 트랜잭션에서 상태 SUCCESS + outbox INSERT + 트랜잭션 이벤트 등록 → @TransactionalEventListener(AFTER_COMMIT)에서 즉시 발행 → 브로커 ack 결과로 outbox를 SUCCESS/FAILURE로 표시 → 릴레이가 1분 넘은 INIT/FAILURE를 재발행합니다.
  • 솔직하게 말할 점: 처음에는 릴레이 스케줄러가 @EnableScheduling 누락과 @Profile("dev")로 돌지 않았고, Kafka 바인딩 설정 키도 틀려 발행 자체가 안 됐습니다. 수정함 스케줄러 어댑터와 설정 키를 고치고 Testcontainers Kafka 테스트로 "커밋 → 발행 → outbox SUCCESS"와 릴레이 재발행을 확인합니다. 지금은 폴링이고, 규모가 커지면 CDC(Debezium)를 고려하겠습니다. 일반 지식
아웃박스는 같은 메시지를 두 번 보낼 수 있잖아요. 중복은 어떻게 처리하나요?
  • 맞습니다. outbox는 at-least-once라서 소비자가 멱등해야 합니다.
  • wallet과 ledger는 처리 전에 existsByOrderId로 이미 처리한 orderId인지 봅니다. 이미 처리했으면 저장 없이 SUCCESS 응답만 다시 보냅니다(SettlementServiceTest가 2번 호출해도 1번만 반영됨을 검증).
  • 수정함 처음에는 check-then-act에 유니크 제약이 없어 동시 재전달에 뚫렸습니다. 지금은 거래 테이블 idempotency_key(orderId·참조·방향으로 만든 키)에 UNIQUE를 걸고, 같은 트랜잭션의 잔액 갱신까지 롤백된 중복 키 위반을 "이미 처리됨"으로 해석합니다. existsByOrderId는 빠른 길로만 남았고, 동시 6개 → 1번 반영을 테스트로 확인합니다.
PSP 호출이 타임아웃 나면 왜 FAILURE가 아니라 UNKNOWN인가요?
  • 타임아웃은 "요청이 PSP에 안 갔다"일 수도, "승인됐는데 응답만 못 받았다"일 수도 있습니다. FAILURE로 확정하면 후자에서 돈은 빠졌는데 주문은 실패가 됩니다.
  • 그래서 PaymentErrorHandler는 타임아웃과 분류 안 된 모든 예외를 UNKNOWN으로 두고 failed_count를 올립니다. UNKNOWN은 같은 Idempotency-Key로 다시 승인을 시도하는 복구 대상입니다.
  • 수정함 재승인 결과가 ALREADY_PROCESSED면 예전에는 extraDetails 누락으로 예외가 났습니다. 지금은 PSP 조회 API로 Payment 객체를 받아 orderId·금액·DONE을 확인한 뒤 정상 SUCCESS로 바꾸고, 확인이 안 되면 UNKNOWN으로 둡니다. 더 나아가면 복구 경로에서 재승인 전에 조회부터 하는 것이 좋습니다(아직 아님).
어떤 에러를 재시도하고, 왜 지수 백오프 + jitter를 썼나요?
  • 재시도 대상은 isRetryableError()(= UNKNOWN 계열: PROVIDER_ERROR, CARD_PROCESSING_ERROR, FAILED_INTERNAL_SYSTEM_PROCESSING 등)와 netty 타임아웃입니다. 잔액 부족이나 카드 거절 같은 확정 실패는 재시도해도 결과가 같으니 제외합니다.
  • Retry.backoff(2, 1s).jitter(0.1): 간격을 지수로 늘려 장애 중인 PSP에 부하를 덜 주고, jitter로 여러 요청의 재시도 시점을 흩어 동시에 몰리지 않게 합니다. 일반 지식
  • 재시도 횟수를 2회로 짧게 둔 이유는 사용자가 응답을 기다리고 있기 때문입니다. 나머지는 3분 주기 비동기 복구로 넘기는 설계입니다.
같은 결제가 두 번 승인되지 않도록 어떤 장치를 겹겹이 두었나요?
  • 체크아웃: orderId를 요청 해시(UUID v3)로 만들고 uk_payment_events_order_id로 막습니다.
  • confirm: 주문 행을 FOR UPDATE로 잠그고 NOT_STARTED·UNKNOWN에서만 EXECUTING으로 넘어갑니다. SUCCESS·FAILURE·EXECUTING이면 PaymentAlreadyProcessedException으로 현재 상태만 돌려줍니다(DB 갱신·PSP 호출 없음). 최종 상태도 EXECUTING·UNKNOWN에서만 기록해 SUCCESS를 덮어쓰지 않습니다.
  • PSP: Idempotency-Key: orderId 헤더로, 재시도나 복구로 같은 요청이 다시 가도 PSP가 한 번만 승인하게 합니다(PSP 동작에 의존).
  • 이벤트: outbox (idempotency_key, type) UNIQUE, 소비자 거래 테이블 idempotency_key UNIQUE.
  • 수정함 처음에는 EXECUTING 상태의 동시 요청이 통과했습니다. 행 락 + 조건부 UPDATE로 막았고, 동시 confirm 8개 → PSP 1회를 테스트로 확인합니다.
지갑 정산에 왜 낙관적 락을 썼나요? 다른 선택지와 비교하면?
  • 문제는 같은 판매자 지갑에 정산이 동시에 몰릴 때의 Lost Update입니다. @Version으로 충돌을 감지하고, 최신 잔액을 다시 읽어 이번 금액만 더해 최대 3회 재시도합니다. 수정함 대기는 예전 0~100ms 랜덤에서 지수 백오프(50ms부터, 상한 1초) + equal jitter로 바꿨고, 지갑·거래 순서를 고정해 동시 정산끼리의 교착도 없앴습니다.
  • 근거: JpaWalletRepositoryTest가 스레드 3개 동시 저장 후 version 3, 잔액 6000을 5회 반복 검증합니다.
  • 비교 일반 지식: 비관적 락은 충돌이 잦을 때 안정적이지만 락 대기와 데드락 관리가 필요합니다. UPDATE … SET balance = balance + ?는 가장 간단하고 충돌 자체가 없지만 이력과 도메인 규칙이 SQL로 흩어집니다. 인기 판매자처럼 hot row라면 원자적 UPDATE나 판매자별 파티션 직렬 처리가 더 낫다고 답합니다.
Kafka에서 같은 결제의 이벤트 순서는 어떻게 보장하나요?
  • Kafka는 파티션 안에서만 순서를 보장합니다. 일반 지식 그래서 PartitionKeyUtil이 abs(orderId.hashCode()) % 6을 outbox metadata에 저장하고, 발행할 때 KafkaHeaders.PARTITION으로 지정합니다. 같은 orderId는 항상 같은 파티션으로 갑니다. PaymentEventMessageSenderTest가 이를 검증합니다.
  • 한계: 메시지 key가 없고 파티션 수 6을 코드에 박아 두어서, 토픽 파티션 수를 바꾸면 깨집니다. 지금은 이벤트 타입이 하나뿐이라 순서 문제가 실제로 드러나는 시나리오도 없습니다. 소비 측(payment의 flatMap)은 병렬이라 순서를 지키지 않습니다.
  • 개선: key = orderId로 기본 파티셔너를 쓰고, 소비자는 버전이나 상태 조건으로 "늦게 온 오래된 이벤트"를 무시하게 만듭니다.
DLQ는 어떻게 동작하나요?
  • 설정상 wallet·ledger 소비자는 max-attempts: 5 후 payment_wallet_dlq / payment_ledger_dlq로 격리됩니다. payment 쪽 응답 소비자도 wallet_payment_dlq 등이 설정되어 있습니다.
  • 솔직한 상태: 설정만 있습니다. DLQ를 모니터링하거나 재처리하는 코드가 없고, 토픽 자동 생성이 꺼져 있어 DLQ 토픽도 미리 만들어야 합니다. 바인더는 DLQ에도 원래 파티션 번호로 보내므로 DLQ 파티션 수가 원본(6)보다 적으면 격리 자체가 실패합니다(테스트를 붙이며 확인). wallet·ledger에서 지갑 누락·예전 형식 메시지가 DLQ로 가는 것은 테스트로 확인했습니다. payment의 리액티브 소비자에는 바인더 재시도와 DLQ가 기대대로 적용되지 않을 수 있습니다(추정).
  • 개선: DLQ 적재 시 알림 → 원인 수정 → 재처리 도구(원래 토픽으로 replay)를 만들고, 일시적 오류는 지연 재시도 토픽(retry-5s, retry-1m)으로 단계화합니다. 일반 지식
복식부기와 append-only 장부는 왜 쓰나요? 여기선 어떻게 강제하나요?
  • 모든 돈의 이동을 차변·대변 한 쌍으로 같은 금액만큼 기록하면, 총합이 0이 아닐 때 오류를 즉시 알 수 있고 "어디서 어디로"가 추적됩니다. 수정이나 삭제 대신 반대 분개를 추가해서 감사 추적을 보존합니다. 일반 지식
  • 여기서는 주문마다 REVENUE CREDIT + ITEM_BUYER DEBIT을 만들고, DB 트리거(SIGNAL 45000)로 UPDATE와 DELETE를 막습니다.
  • 수정함 처음에는 두 금액이 같은 값에서 나와 검사가 형식적이었고, 트리거도 자동 적용되지 않았습니다. 지금은 저장 전에 거래별 DEBIT 합 = CREDIT 합(방향 기준), 대변 합 = 결제 총액을 도메인과 어댑터 두 곳에서 확인하고, spring.sql.init.mode: always로 트리거를 기동 때 적용하며 거부되는 것을 테스트로 확인합니다. 더 하려면 DB 권한으로 UPDATE·DELETE 자체를 막습니다.
대사(Reconciliation)는 어떻게 설계하겠어요?
  • 현재: README에 계획만 있고 코드는 없습니다.
  • 설계안 일반 지식: ① 내부 대사: 일 단위로 payment SUCCESS 합계 = wallet 정산 합계 = ledger CREDIT 합계를 orderId 단위로 대조합니다. ② 외부 대사: PSP 정산 파일이나 조회 API와 payment 상태를 대조해서 UNKNOWN이나 threshold를 초과한 건의 최종 상태를 확정합니다. ③ 불일치는 자동 보정(이벤트 재발행, 반대 분개)이나 수동 검토 큐로 보냅니다.
  • 이 프로젝트에서 찾았던 약점(정산 0건인데 SUCCESS, 지갑 없는 판매자 누락, 완료 레이스)이 모두 대사가 있었다면 잡혔을 종류라는 점을 연결해서 말하면 좋습니다. 셋 다 코드로는 고쳤지만(수정함), 대사는 "모르는 다음 버그"를 잡는 안전망이라 여전히 필요합니다.
wallet과 ledger가 둘 다 끝났는지를 Payment는 어떻게 아나요? 문제는 없나요?
  • 각자 처리 후 wallet/ledger 토픽으로 SUCCESS를 보내면, payment가 해당 플래그를 세우고 둘 다 서 있으면 is_payment_done을 세웁니다. 오프셋은 처리 후 ReceiverOffset.commit()으로 수동 커밋합니다.
  • 문제(수정 전): 두 메시지가 동시에 오면 둘 다 "상대가 아직"이라고 판단해 완료 플래그가 영구히 안 섰습니다. 판단은 메모리 스냅샷에서 하고, UPDATE에는 트랜잭션이 없었습니다.
  • 수정함 한 트랜잭션에서 자기 플래그 UPDATE → "모든 플래그가 1"을 조건으로 한 완료 UPDATE를 실행합니다. 첫 UPDATE의 행 락이 두 완료를 직렬화하고, 뒤쪽의 조건부 UPDATE는 최신 커밋 값을 봅니다. 동시 도착 테스트로 확인합니다.
(꼬리 질문) 복구 스케줄러, 실제로 돌려 보셨어요?
  • 정직하게 답합니다. "코드를 다시 보니 @EnableScheduling이 없고 @Profile("dev")도 활성화하지 않아서 실제로는 돌지 않았습니다. 테스트는 메서드를 직접 호출했고, assert 없이 sleep만 해서 이 문제를 못 잡았습니다."
  • 배운 점: "스케줄러나 비동기 경로는 실행됐다는 증거(메트릭, 로그)와 결과 assert(Awaitility)가 있어야 한다. 테스트를 메서드 직접 호출로만 짜면 배선(wiring) 오류를 못 잡는다."
  • 수정함 한 일: 인바운드 어댑터 PaymentScheduler(@EnableScheduling, 프로퍼티로 끄기), 회차를 block으로 기다려 겹침 방지, 복구 대상 선점 UPDATE(다중 인스턴스 중복 방지), "UNKNOWN이 결국 SUCCESS가 된다"를 검증하는 Testcontainers 통합 테스트와 스케줄러 기동 테스트. 남은 일: 실행 메트릭과 알림.
payment는 왜 WebFlux/R2DBC이고 wallet·ledger는 MVC/JPA인가요? 구조는 왜 헥사고날인가요?
  • payment는 외부 PSP 호출(최대 30초 타임아웃)을 기다리는 I/O 중심 서비스라 논블로킹이 스레드를 덜 씁니다. wallet·ledger는 DB 트랜잭션과 낙관적 락이 핵심이라 JPA·블로킹이 단순합니다(각 build.gradle 주석에 의도가 적혀 있음).
  • 대가: R2DBC는 JPA가 없어서 DatabaseClient로 SQL을 직접 쓰고, 리액티브 트랜잭션과 이벤트 연동(TransactionalEventPublisher)이 까다롭습니다. 수정함 문자열 포맷으로 만들던 INSERT는 바인딩으로 바꿨습니다(따옴표가 든 Toss 실패 메시지에서 SQL 오류가 났음).
  • 헥사고날: PSP(Toss)나 상품 조회(Mock)를 포트 뒤로 숨겨 테스트에서 PaymentExecutorPort를 mock으로 바꿔 끼웠습니다. 수정함 서비스가 어댑터 예외를 import하던 위반은 예외를 application/exception으로 옮겨 풀었고, ArchUnit으로 고정하는 것은 남은 일입니다.
