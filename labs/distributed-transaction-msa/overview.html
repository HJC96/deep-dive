MSA — 서비스를 나누자 부분 커밋이 생겼다

모놀리스의 예약·좌석·지갑을 서비스 3개와 DB 3개로 분리한 기준선. 기능 순서(좌석 예약 → 크레딧 차감 → 예약 확정)는 같지만 각 작업이 서로 다른 앱·DB에서 커밋된다. 좌석 커밋 뒤 지갑이 실패하면 좌석만 남는 부분 커밋을 실제 HTTP 통합 테스트로 재현한다.

Java 21Spring Boot 3.4.1RestClient앱 3개 · DB 3개MySQL (운영 설정)H2 ×3 (테스트)

01한눈에

30초 요약 — 왜 문제인가

시리즈에서의 위치 — 4단계가 같은 실패 시나리오를 다룹니다
STEP 1 · 기준선MonolithDB 1개 · @Transactional 1개 → STEP 2 · 문제 · 지금 여기MSA서비스 3개 · 부분 커밋 → STEP 3 · 해법 A2PC (XA)prepare 후 결정 · 락 대기 → STEP 4 · 해법 BTCCTry 커밋 · Cancel 보상
문제

예약·좌석·지갑을 서비스 3개 · DB 3개로 나누자 하나의 로컬 트랜잭션으로 묶을 수 없게 됐다. 좌석이 커밋된 뒤 지갑이 실패하면 좌석만 잡힌 채 남는다.

접근

세 Spring 앱을 실제 HTTP(RestClient)로 연결하고, 각 서비스는 자기 DB에만 @Transactional. 통합 테스트가 세 앱을 랜덤 포트·독립 H2로 띄워 부분 커밋을 재현·고정한다.

결론

Reservation Service의 롤백은 reservation_db에만 적용된다. 잔액 50,000 실패 시 reserved_count 2, 이력 1건이 남는다. 이 부분 커밋이 2PC·TCC가 풀어야 할 문제다.

공통 실패 시나리오 정원 10석 워크숍에서 좌석 2석 × 30,000 = 60,000 크레딧이 필요한데 지갑 잔액은 50,000. 좌석은 잡히지만 지갑이 실패한다. 이미 잡힌 좌석이 되돌아가는가? 네 모듈이 모두 이 질문에 답한다.

02흐름

단계를 클릭하면 상세 설명이 나옵니다. 아래는 실패 시 시퀀스.

→ → → →

POST /reservations/{id}/place → ReservationService.place()가 reservation_db의 로컬 트랜잭션을 시작하고 findById로 예약을 읽는다. CONFIRMED면 기존 결과 반환.

모놀리스와 달리 행 락(FOR UPDATE)이 없다.

SeatClient.reserve(reservationId, …) → POST /internal/seats/reserve. Seat Service는 자기 트랜잭션으로 reservedCount 증가 + SeatReservationHistory(requestId = reservationId) INSERT 후 응답 전에 커밋한다. amount 60,000 반환.

WalletClient.debit(reservationId, userId, 60,000) → POST /internal/wallets/debit. Wallet Service가 자기 트랜잭션으로 잔액 차감 + WalletLedger INSERT 후 커밋.

두 호출이 모두 200이면 reservation.confirm(amount) → reservation_db 커밋. 세 DB가 모두 바뀐다: CONFIRMED, reservedCount 2, 이력 1건, balance 40,000, 원장 1건.

잔액 50,000 → Wallet Service가 409 NOT_ENOUGH_CREDIT. RestClient가 HttpClientErrorException을 던지고 reservation_db만 롤백(CREATED 유지).

STEP 2에서 이미 커밋된 seat_db는 그대로 — reservedCount 2, 이력 1건. 보상(취소) 로직은 없다.

03비교·핵심 구현

서비스별 핵심 코드. 실제 파일에서 발췌.

Reservation의 @Transactional 안에서 HTTP 호출 함정

코드 모양은 모놀리스와 거의 같다. 하지만 이 @Transactional이 관리하는 것은 reservation_db 하나뿐이다.

@Transactional
public ReservationResult place(long reservationId) {
    Reservation reservation = reservationRepository.findById(reservationId)
            .orElseThrow(() -> new ReservationNotFoundException(reservationId));
    if (reservation.getStatus() == ReservationStatus.CONFIRMED) {
        return ReservationResult.from(reservation);
    }

    long amount = seatClient.reserve(
            reservationId, reservation.getWorkshopId(), reservation.getSeatCount());
    walletClient.debit(reservationId, reservation.getUserId(), amount);
    reservation.confirm(amount);
    return ReservationResult.from(reservation);
}
어떻게
HTTP 호출은 같은 트랜잭션에 참여하지 않는다. Seat Service는 자기 트랜잭션을 시작하고 응답 전에 커밋한다(README).
결과
지갑 409 → 이 메서드만 롤백. 좌석은 이미 커밋된 뒤라 되돌릴 수 없다.
모놀리스와 차이
findByIdForUpdate → findById. 예약 행 락이 사라졌다.

Seat Service: 자기 DB에 커밋 먼저 커밋

@Transactional
public long reserve(long requestId, long workshopId, int seatCount) {
    WorkshopSeat workshop = workshopRepository.findById(workshopId)
            .orElseThrow(() -> new WorkshopNotFoundException(workshopId));
    long amount = workshop.reserve(seatCount);
    historyRepository.save(new SeatReservationHistory(requestId, workshopId, seatCount, amount));
    return amount;
}
어떻게

requestId

Wallet Service: 잔액 부족이면 409 실패 지점

@Transactional
public void debit(long requestId, long userId, long amount) {
    Wallet wallet = walletRepository.findById(userId)
            .orElseThrow(() -> new WalletNotFoundException(userId));
    wallet.debit(amount);
    ledgerRepository.save(new WalletLedger(requestId, userId, amount));
}

// WalletExceptionHandler
@ExceptionHandler(NotEnoughCreditException.class)
public ResponseEntity<ErrorResponse> handleUnavailable(NotEnoughCreditException exception) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(new ErrorResponse("NOT_ENOUGH_CREDIT", exception.getMessage()));
}

잔액 50,000 < 60,000 → NotEnoughCreditException → wallet_db 롤백 → HTTP 409.
호출 측

reservationId를 requestId로 전달 추적용

Reservation Service는 새 ID를 만들지 않고 reservationId를 두 클라이언트의 첫 인자로 넘긴다. 하위 서비스에서는 이름이 requestId다.

public long reserve(long requestId, long workshopId, int seatCount) {
    SeatReserveResponse response = restClient.post()
            .uri("/internal/seats/reserve")
            .body(new SeatReserveRequest(requestId, workshopId, seatCount))
            .retrieve()
            .body(SeatReserveResponse.class);
    if (response == null) throw new IllegalStateException("seat service returned an empty response");
    return response.amount();
}

05한계·약점

README = README "아직 남아 있는 문제", 코드 = 코드에서 확인한 것.

README 중간 실패로 인한 부분 커밋

이 모듈이 일부러 재현하는 문제. 좌석 커밋 후 지갑 실패 → 좌석 2·이력 1건 잔존. 이어서 2PC와 TCC가 같은 시나리오로 이 문제를 다룬다.

README 재시도하면 좌석이 다시 증가할 수 있다

실패 후 예약은 CREATED이므로 같은 예약을 다시 place하면 Seat Service가 다시 reservedCount를 올린다. SeatReservationHistory.requestId에 unique 제약이 없어 이력도 막지 못한다(README: "저장만 한다").

README HTTP 타임아웃 시 상대 커밋 여부를 알 수 없다

응답을 못 받으면 Seat가 커밋했는지 아닌지 호출 측은 바로 알 수 없다. 조회 API나 멱등 재시도가 필요하다. 코드 게다가 SeatClient/WalletClient는 builder.baseUrl(…)만 설정하고 타임아웃을 지정하지 않는다(코드 전체에 timeout 설정 없음).

README 보상 작업 없음 · 상태 모델 없음

이미 반영된 좌석을 취소하는 API가 없고, 세 서비스가 최종 상태에 도달했는지 추적할 상태(예: PENDING/FAILED/COMPENSATED)도 없다. ReservationStatus는 CREATED, CONFIRMED뿐.

코드 예약 행 락이 없다 — 같은 예약의 동시 실행 미보호

모놀리스는 findByIdForUpdate로 같은 예약의 동시 실행을 직렬화했지만, MSA ReservationRepository는 JpaRepository 기본 메서드뿐이고 place는 findById를 쓴다. 같은 예약이 동시에 두 번 실행되면 둘 다 CREATED를 보고 Seat를 두 번 호출할 수 있다 추론 · 동시성 테스트 없음.

코드 하위 서비스 409가 그대로 예외로 올라온다

ReservationExceptionHandler는 ReservationNotFoundException(404)만 처리한다. 지갑의 409는 HttpClientErrorException으로 올라오는데 매핑 핸들러가 없어, HTTP 클라이언트에게는 Spring 기본 오류 응답(보통 500)이 갈 것으로 보인다 추론 · 컨트롤러 테스트 없음. 테스트는 서비스 메서드를 직접 호출해 예외 타입만 확인한다.

코드 DB 트랜잭션 안에서 원격 호출

place()의 @Transactional이 열린 채로 두 번의 HTTP 호출을 기다린다. 하위 서비스가 느리면 그동안 reservation_db 커넥션을 점유한다 일반 지식. 이 모듈은 문제 재현이 목적이라 그대로 둔 것.

코드 테스트 범위

테스트는 MsaLocalTransactionTest 2개뿐(성공/지갑 실패). 세 앱 모두 H2 in-memory(MODE=MySQL)이고, Seat·Wallet 서비스 단위 테스트와 Reservation 컨트롤러 테스트는 없다. 좌석 부족·타임아웃·재시도 시나리오도 테스트되지 않았다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

Reservation Service에 @Transactional이 있는데 왜 좌석이 롤백되지 않나요?

@Transactional(JpaTransactionManager)은 자기 DataSource 하나, 즉 reservation_db만 관리한다. HTTP로 호출된 Seat Service는 자기 트랜잭션을 열고 응답 전에 이미 커밋했다. 원격 호출은 트랜잭션 전파 대상이 아니다.

부분 커밋 후 시스템 상태를 정확히 설명해 보세요.

예약 CREATED, 좌석 reservedCount 2, 좌석 이력 1건, 잔액 50,000, 원장 0건. 결제도 확정도 없이 좌석 2석만 점유. 테스트 walletFailureCannotRollBackTheSeatServiceCommit가 이 상태를 고정한다.

그 상태에서 사용자가 충전 후 재시도하면?

예약이 CREATED라 Seat 호출이 다시 일어나 reservedCount가 2→4가 될 수 있다(README "재시도하면 좌석이 다시 증가할 수 있음"). requestId unique 제약 + "이미 처리한 requestId면 기존 결과 반환" 멱등 처리가 있어야 막힌다.

Seat 호출이 타임아웃 나면 어떻게 해야 하나요?

커밋됐는지 모르는 상태다. 무작정 재시도하면 중복 반영, 포기하면 좌석 누수. 정석은 멱등한 하위 API(같은 requestId면 같은 결과)를 만들고 재시도하거나, requestId로 상태 조회 후 결정하는 것 일반 지식. 이 모듈은 둘 다 없다.

호출 순서를 바꿔 지갑을 먼저 차감하면 해결되나요?

아니다. 지갑 커밋 후 좌석이 부족하면 이번엔 돈만 빠지고 좌석이 없는 반대 방향 부분 커밋이 생긴다 추론. 순서는 어느 쪽 불일치를 감수할지를 고를 뿐이다.

해결책 선택지를 비교해 보세요 (2PC / TCC / Saga / Outbox).
  • 2PC(XA): 전원 prepare 후 커밋 — 부분 커밋 없음, 대신 락 블로킹·코디네이터 의존 (다음 단계)
  • TCC: Try로 자원 예약·커밋, Confirm/Cancel — 락 없음, 대신 참여자 코드·멱등 처리 (4단계)
  • Saga 일반 지식: 각 단계 로컬 커밋 + 실패 시 보상 트랜잭션 역순 실행. 예약(hold) 단계 없이 바로 반영.
  • Transactional Outbox 일반 지식: DB 변경과 "보낼 이벤트"를 같은 로컬 트랜잭션으로 저장하고 별도 릴레이가 발행 — 이벤트 유실 없이 Saga를 구동.

이 저장소에서 실제로 구현·테스트된 것은 2PC와 TCC뿐.

트랜잭션 안에서 외부 HTTP를 호출하는 게 왜 안티패턴인가요?

일반 지식 ① 롤백해도 원격 부수효과는 되돌아가지 않는다(이 모듈이 증명). ② 원격 응답을 기다리는 동안 DB 커넥션·락을 점유해 풀 고갈 위험. ③ 타임아웃 시 결과 불명. 보통 외부 호출은 트랜잭션 밖으로 빼고 상태 머신·보상으로 관리한다.

reservationId를 requestId로 재사용한 이유와 부족한 점은?

새 ID 없이 하나의 예약에서 파생된 좌석 처리와 지갑 처리를 연결할 수 있다(README). 부족한 점: 하위 서비스가 저장만 하고 unique 제약·중복 판단이 없어 멱등 키 역할은 못 한다.
