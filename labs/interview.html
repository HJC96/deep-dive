선착순 쿠폰 재고 차감 — 동시성 제어 9가지를 한 테이블에서 비교

선착순 쿠폰에서 동시성 문제가 왜 생기나요? @Transactional이면 안전하지 않나요?
  • "읽기 → 계산 → 쓰기"가 원자적이지 않아, 두 트랜잭션이 같은 값(200)을 읽고 같은 값(199)을 쓰는 lost update.
  • @Transactional은 원자성(전부 커밋/롤백)을 주지만 다른 트랜잭션과의 상호 배제를 주지 않음. 일반 SELECT는 락 없이 읽음 일반 지식.
  • 이 모듈은 Thread.yield()로 끼어들기를 유도해 200건 후 재고 ≠ 0을 재현.

9가지 중 실무에서 하나를 고른다면? 이유는?

  • 로직이 복잡해 한 문장으로 안 되면 비관적 락 또는 분산락.

비관적 락 vs 낙관적 락, 언제 무엇을 쓰나요?
  • 비관적: 충돌이 잦을 때. 미리 막아 재시도 비용 없음. 대신 대기·커넥션 점유·데드락 위험.
  • 낙관적: 충돌이 드물 때. 락 비용 없음. 충돌 시 예외 → 재시도 코드 필수.
  • 근거: README 예시에서 같은 row에 200개를 몰았더니 낙관적 락 3,156ms vs 비관적 락 429ms.

낙관적 락 재시도를 왜 @Transactional 메서드 밖에 두었고, self 주입은 왜 필요했나요?
  • 충돌은 커밋 시점에 감지되고 그 트랜잭션은 롤백 대상 → 같은 트랜잭션 안에서는 재시도 불가. 그래서 "시도 1회 = 트랜잭션 1개"(issueOnce), 루프(issue)는 바깥.
  • this.issueOnce()는 프록시를 거치지 않아 @Transactional이 적용되지 않음(self-invocation). 그래서 @Lazy로 자기 프록시를 주입받아 self.issueOnce() 호출.
  • 대안: 재시도 로직을 별도 퍼사드 클래스로 분리하면 self 주입 불필요 (README).

네임드 락에서 REQUIRES_NEW를 쓴 이유와 그 비용은?
  • GET_LOCK/RELEASE_LOCK은 같은 세션(커넥션)에서 해야 하므로 바깥 @Transactional로 커넥션 고정.
  • 차감을 같은 트랜잭션에 두면 락 해제 시점에 아직 커밋 전 → 다음 스레드가 옛 값을 읽음. 그래서 REQUIRES_NEW로 먼저 커밋.
  • 비용: 요청당 커넥션 2개. 이 테스트는 Hikari 40, 스레드 32라 버티지만, 풀이 작으면 고갈 위험(README 한계).

직접 만든 Redis SET NX 락의 문제점은? Redisson과 무엇이 다른가요?

수정함 Redis 락 값이 고정 "LOCK"이고, 해제 시 소유자 확인 없이 delete

예전 RedisLockCouponIssueService는 모든 요청이 같은 값 "LOCK"으로 setIfAbsent하고, finally에서 무조건 redisTemplate.delete(lockKey)했습니다.

시나리오: A의 작업이 TTL(30초)보다 길어져 락이 만료 → B가 락 획득 → A가 끝나며 B의 락을 삭제 → C도 진입 → 동시 실행. 기존 동시성 테스트(짧은 작업)에서는 드러나지 않았습니다.

수정: 락 값에 요청별 UUID 토큰을 넣고, 해제는 "값이 내 토큰일 때만 DEL"을 Lua 스크립트로 원자 실행합니다. 테스트가 "내 락 만료 → 다른 토큰이 같은 key를 잡음 → 내 unlock은 false, 남의 락은 그대로"를 재현합니다.

수정함 네임드 락이 GET_LOCK 반환값을 무시

NamedLockRepository 주석에 "성공 1, 타임아웃 0, 에러 NULL"이라고 적어 놓고, 예전 NamedLockCouponIssueService.issue()는 반환값을 확인하지 않고 바로 self.issueOnce()를 호출했습니다. 10초 안에 락을 못 얻으면 락 없이 차감이 실행되고, finally에서 잡지 못한 락에도 RELEASE_LOCK을 호출했습니다.

콘서트 좌석 예약 — Redis로 선점하고, Kafka로 DB 쓰기를 떼어 낸다

좌석 선점에 왜 분산락(SET NX)이 아니라 Redis Set(SADD)을 썼나요?
  • 불변식이 "좌석은 한 번만, 사용자도 한 번만" = 유니크 멤버십. SADD는 새로 추가될 때만 1을 반환 → 그 자체가 원자적 선점 판정. 락을 잡고 풀 필요가 없음.
  • 두 불변식을 Set 두 개로 각각 표현: seat:applied-users, seat:held-seats.
  • 트레이드오프: Set은 멤버별 TTL이 없어 키 전체 TTL만 가능. 좌석별 만료가 필요하면 좌석당 키 SET NX EX가 맞음(코드 주석).

Kafka를 넣으면 무엇이 좋아지고, 무엇을 대가로 치르나요?
  • 좋아지는 것: 요청 경로에서 DB 쓰기 제거 → 느린 DB에서도 즉시 응답(README 예시: 직접 쓰기 실패 88건 vs Kafka 0건). 스파이크를 토픽이 버퍼링. 브로커에 기록된 커맨드는 앱이 죽어도 남아 다시 소비할 수 있음(send()는 브로커 ack을 기다리지 않아, 기록되기 전에 앱이 죽으면 그 커맨드는 사라질 수 있음 — README).
  • 대가: 최종 일관성(응답 시점엔 DB에 아직 없음, 예시에서 확정까지 3,780ms). at-least-once라 멱등 처리 필요. 확정 실패 처리(FailedEvent, 재처리) 필요. 운영 구성요소 증가.

Redis에서 선점은 됐는데 Kafka 발행이나 DB 확정이 실패하면?
  • DB 확정 실패: Consumer가 catch → FailedEvent 저장 → 오프셋 커밋(무한 재시도 방지). 재처리 배치는 README상 향후 구현.
  • 발행 실패: send() future의 실패 콜백에서 Redis 선점 해제 수정함. 다만 클라이언트는 이미 "접수"를 받았으므로 최종 결과 보장은 Outbox 패턴·결과 조회 API 일반 지식.
  • 직접 쓰기 경로의 DB 실패: 선점을 되돌리고 예외 전파 수정함.
  • 최후 안전망: 키 TTL 300초(첫 선점부터 고정)로 선점이 영원히 남지는 않음.

Cache Aside와 Read Through의 차이는?
  • 핵심은 miss 시 저장소를 누가 호출하느냐. Aside는 서비스, Read Through는 캐시 계층(loader).

  • 이 레포에선 둘 다 2회 읽기에 store read 1 (ReadPatternTest). 결과는 같고 책임 위치가 다름.
  • 꼬리질문 대비: Redis만 두면 Read Through가 생기지 않는다 → Caffeine LoadingCache나 공통 래퍼로 구현 (README).

쓰기 시 캐시를 갱신(put)하지 않고 삭제(evict)하는 이유는?
  • README의 일반 조회 추천은 Cache Aside + Write Around(evict). 읽히지 않을 데이터로 캐시를 오염시키지 않고, 다음 읽기가 저장소 최신 값을 다시 적재.

Write Through / Around / Behind는 각각 언제 쓰나?
  • Through: 쓰기 직후 바로 읽음. 쓰기 경로가 느려지고 부분 실패(저장 성공·캐시 실패) 처리 필요.

  • Behind: 쓰기 처리량이 최우선. 일시적 불일치 + 유실 위험 → 영속 큐, retry, idempotency (README).

Cache Penetration 방어: negative caching과 Bloom filter의 장단점은?
  • Negative caching: 구현 쉬움, 첫 조회 1회만 저장소. 대신 없는 키마다 캐시 공간을 쓰고, TTL이 길면 새로 생긴 값을 가림 (이 구현은 negative TTL을 둠 수정함).
  • Bloom filter: 메모리 적게 쓰고 저장소 조회 전 차단. false=확실히 없음, true=있을 수도. false positive 존재.

수정: evict는 값만 비우고 버전을 tombstone으로 남기며, 쓰기 경로용 evict(key, newVersion)을 추가했습니다. evict 경쟁을 재현하는 테스트 2개를 추가했습니다. 남은 점: tombstone이 key마다 남아 메모리를 쓰고(실무는 짧은 TTL), 버전은 여전히 호출자가 넘기며 저장소의 버전 컬럼과 연동되지 않습니다.

  • 예전 구현: floorMod(key.hashCode(), maxJitter+1) — 결정적이라 테스트하기 쉽지만, 연속 id는 hashCode가 1씩 달라 jitter가 133~137ms로 몰림.
  • 지금 수정함: 해시를 SplitMix64 finalizer로 섞어 결정성을 유지하며 분산. 테스트가 분포 폭(차이 5초 초과, 구간 9개 이상)까지 단언. 대안은 ThreadLocalRandom 난수(대신 같은 key의 TTL이 매번 달라지고 테스트에 시드 주입 필요).

Monolith — 하나의 DB, 하나의 @Transactional

예약 "생성"과 "실행"을 왜 두 API로 나눴나요? 이게 2PC인가요?

서버가 먼저 reservationId를 발급하면 그 ID 하나로 실행 대상 잠금·재실행 판단·원장 키를 모두 해결할 수 있다. 클라이언트가 임의 멱등 키를 만들 필요가 없다.

해결책 선택지를 비교해 보세요 (2PC / TCC / Saga / Outbox).
  • 2PC(XA): 전원 prepare 후 커밋 — 부분 커밋 없음, 대신 락 블로킹·코디네이터 의존 (다음 단계)
  • TCC: Try로 자원 예약·커밋, Confirm/Cancel — 단계 사이 락 없음, 대신 참여자 코드·멱등 처리 (4단계)
  • Saga 일반 지식: 각 단계 로컬 커밋 + 실패 시 보상 트랜잭션 역순 실행. 예약(hold) 단계 없이 바로 반영.
  • Transactional Outbox 일반 지식: DB 변경과 "보낼 이벤트"를 같은 로컬 트랜잭션으로 저장하고 별도 릴레이가 발행 — 이벤트 유실 없이 Saga를 구동.

해결책 가운데 분산 트랜잭션 단계에서 구현·테스트한 것은 2PC와 TCC다. Transactional Outbox는 payment-system에 구현돼 있고, Saga는 이 저장소에 없다.

distributed-transaction-2pc 질문 10 약점 7

2PC — 묻고 나서 정한다, 대신 락을 쥐고 기다린다

2PC를 1분 안에 설명해 보세요.

1단계(투표): 코디네이터가 모든 참여자에게 작업 후 PREPARE를 요청 — 참여자는 변경을 디스크에 기록하고 락을 쥔 채 YES/NO. 2단계(결정): 전원 YES면 COMMIT, 하나라도 NO면 ROLLBACK. 이 모듈은 MySQL XA SQL로 이 두 단계를 직접 실행했다.

원문에서 보기 →

prepare가 정확히 무엇을 보장하나요? 왜 락을 계속 쥐나요?

"서버가 죽었다 살아나도 커밋할 수 있다"는 약속. 그 약속을 지키려면 다른 트랜잭션이 같은 행을 바꾸지 못하게 막아야 하므로 락을 유지한다. XA END 뒤에도 락은 풀리지 않는다. 이것이 정합성을 얻는 방법이자 대가.

2PC의 블로킹 문제(in-doubt)란?

YES를 던진 참여자가 결정을 못 들으면 혼자 커밋도 롤백도 못 하고 락을 쥔 채 멈춘다. 테스트에서 코디네이터 커넥션을 닫자 XA RECOVER에 1건이 남고, 다른 커넥션의 같은 행 UPDATE는 Lock wait timeout. 결정을 아는 쪽의 XA COMMIT으로만 풀렸다.

distributed-transaction-tcc 질문 10 약점 7

TCC — 자원을 잡아 둔 채 바로 커밋하고, Confirm으로 확정하거나 Cancel로 되돌린다

TCC를 설명하고 2PC와 가장 큰 차이를 말해 보세요.

Try에서 자원을 잡아 두고 바로 커밋, 전원 성공하면 Confirm, 하나라도 실패하면 Cancel(반대 방향 업무 작업). 2PC는 prepare 후 락을 쥐고 결정을 기다리지만 TCC는 단계 사이에 락이 없다. 대신 되돌리기를 DB가 아니라 참여자 코드가 한다.

원문에서 보기 →

지갑 Try에서 frozen만 올리지 않고 balance를 실제로 깎는 이유는?

Try가 커밋되면 락이 없다. balance를 그대로 두면 다음 요청이 같은 돈을 보고 또 쓸 수 있다(이중 지출). balance에서 빼서 frozen으로 옮겨야 한다. 좌석도 같은 이유로 정원 검사에 heldCount를 포함한다.

Confirm이 두 번 오면? 왜 두 번 올 수 있나요?

Confirm 응답이 유실되면 코디네이터는 재전송한다. 로그를 안 보면 held→reserved를 두 번 옮겨 2석이 4석(초과 판매). 참여자는 로그 state가 TRIED일 때만 적용하고 CONFIRMED면 무시한다(Confirm을두번받아도_한번만적용된다).

빈 취소(empty rollback)와 매달림(suspension)을 설명해 보세요.

Try가 유실·지연된 채 코디네이터가 Cancel을 보내면 참여자는 본 적 없는 요청의 Cancel을 받는다 → 자원은 안 건드리고 CANCELLED를 기록(빈 취소). 그 기록이 없으면 뒤늦게 온 Try가 자원을 잡아 두는데 코디네이터는 이미 끝났으니 아무도 회수하지 않는다(매달림). 그래서 Try는 CANCELLED 로그를 보면 거부한다. Seata는 이를 空回滚·悬挂로 부른다(README).

"격리를 포기했다"는 게 실무에서 무슨 의미인가요?

Try만 끝난 held/frozen 값이 커밋되어 다른 트랜잭션에 보인다. 예: 잔여 좌석 화면이 아직 확정 안 된 hold를 반영하고, 그 hold가 Cancel되면 잠깐 매진처럼 보였다가 풀린다. 그래서 조회 화면·정산은 reserved와 held를 구분해서 다뤄야 한다 추론.

결제·정산·장부를 왜 하나의 트랜잭션(또는 2PC)으로 묶지 않았나요?
  • 서비스마다 DB가 다르고(payment_db / wallet_db / ledger_db), 그 사이에 외부 PSP(Toss)가 있습니다. Toss는 우리 트랜잭션 코디네이터에 참여할 수 없으니 2PC는 처음부터 불가능합니다.
  • 2PC는 코디네이터가 장애 나면 참여자가 락을 쥔 채 블로킹되고, 모든 참여자가 XA를 지원해야 하며, 가장 느린 참여자에 맞춰 지연이 늘어납니다. 일반 지식 이 문제는 같은 레포의 distributed-transaction-2pc 실험에서 다룹니다.
  • 그래서 각자 로컬 트랜잭션만 쓰고, 아웃박스 + 멱등 소비자 + 재시도로 최종 일관성을 노렸습니다. 대가는 중간 상태가 보인다는 것(SUCCESS인데 아직 is_payment_done=0)과 대사가 꼭 필요하다는 것입니다.

트랜잭셔널 아웃박스가 뭔가요? 이 프로젝트에선 어떻게 구현했나요?
  • "DB 커밋 + 메시지 발행"이라는 dual write 문제의 해법입니다. 이벤트를 같은 DB의 outbox 테이블에 같은 트랜잭션으로 써서 원자성을 확보하고, 발행은 나중에 합니다.
  • 구현: updatePaymentStatusToSuccess 한 트랜잭션에서 상태 SUCCESS + outbox INSERT + 트랜잭션 이벤트 등록 → @TransactionalEventListener(AFTER_COMMIT)에서 즉시 발행 → 브로커 ack 결과로 outbox를 SUCCESS/FAILURE로 표시 → 릴레이가 1분 넘은 INIT/FAILURE를 재발행합니다.
  • 솔직하게 말할 점: 처음에는 릴레이 스케줄러가 @EnableScheduling 누락과 @Profile("dev")로 돌지 않았고, Kafka 바인딩 설정 키도 틀려 발행 자체가 안 됐습니다. 수정함 스케줄러 어댑터와 설정 키가 고쳐졌고, Testcontainers Kafka 테스트가 "커밋 → 발행 → outbox SUCCESS"와 릴레이 재발행을 확인합니다. 지금은 폴링이고, 규모가 커지면 CDC(Debezium)를 고려하겠습니다. 일반 지식

아웃박스는 같은 메시지를 두 번 보낼 수 있잖아요. 중복은 어떻게 처리하나요?

  • wallet과 ledger는 처리 전에 existsByOrderId로 이미 처리한 orderId인지 봅니다. 이미 처리했으면 저장 없이 SUCCESS 응답만 다시 보냅니다(SettlementServiceTest가 2번 호출해도 1번만 반영됨을 검증).

PSP 호출이 타임아웃 나면 왜 FAILURE가 아니라 UNKNOWN인가요?
  • 타임아웃은 "요청이 PSP에 안 갔다"일 수도, "승인됐는데 응답만 못 받았다"일 수도 있습니다. FAILURE로 확정하면 후자에서 돈은 빠졌는데 주문은 실패가 됩니다.
  • 그래서 PaymentErrorHandler는 타임아웃과 분류 안 된 모든 예외를 UNKNOWN으로 두고 failed_count를 올립니다. UNKNOWN은 같은 Idempotency-Key로 다시 승인을 시도하는 복구 대상입니다.
  • 수정함 재승인 결과가 ALREADY_PROCESSED면 예전에는 extraDetails 누락으로 예외가 났습니다. 지금은 PSP 조회 API로 Payment 객체를 받아 orderId·금액·DONE을 확인한 뒤 정상 SUCCESS로 바꾸고, 확인이 안 되면 UNKNOWN으로 둡니다. 더 나아가면 복구 경로에서 재승인 전에 조회부터 하는 것이 좋습니다(아직 아님).

어떤 에러를 재시도하고, 왜 지수 백오프 + jitter를 썼나요?
  • 재시도 대상은 isRetryableError()(= UNKNOWN 계열: PROVIDER_ERROR, CARD_PROCESSING_ERROR, FAILED_INTERNAL_SYSTEM_PROCESSING 등)와 netty 타임아웃입니다. 잔액 부족이나 카드 거절 같은 확정 실패는 재시도해도 결과가 같으니 제외합니다.
  • Retry.backoff(2, 1s).jitter(0.1): 간격을 지수로 늘려 장애 중인 PSP에 부하를 덜 주고, jitter로 여러 요청의 재시도 시점을 흩어 동시에 몰리지 않게 합니다. 일반 지식
  • 재시도 횟수를 2회로 짧게 둔 이유는 사용자가 응답을 기다리고 있기 때문입니다. 나머지는 3분 주기 비동기 복구로 넘기는 설계입니다.

같은 결제가 두 번 승인되지 않도록 어떤 장치를 겹겹이 두었나요?
  • 체크아웃: orderId를 요청 해시(UUID v3)로 만들고 uk_payment_events_order_id로 막습니다.
  • confirm: 주문 행을 FOR UPDATE로 잠그고 NOT_STARTED·UNKNOWN에서만 EXECUTING으로 넘어갑니다. SUCCESS·FAILURE·EXECUTING이면 PaymentAlreadyProcessedException으로 현재 상태만 돌려줍니다(DB 갱신·PSP 호출 없음). 최종 상태도 EXECUTING·UNKNOWN에서만 기록해 SUCCESS를 덮어쓰지 않습니다.
  • PSP: Idempotency-Key: orderId 헤더로, 재시도나 복구로 같은 요청이 다시 가도 PSP가 한 번만 승인하게 합니다(PSP 동작에 의존).
  • 이벤트: outbox (idempotency_key, type) UNIQUE, 소비자 거래 테이블 idempotency_key UNIQUE.
  • 수정함 처음에는 EXECUTING 상태의 동시 요청이 통과했습니다. 지금은 행 락 + 조건부 UPDATE로 막혀 있고, 테스트가 동시 confirm 8개 → PSP 1회를 확인합니다.

지갑 정산에 왜 낙관적 락을 썼나요? 다른 선택지와 비교하면?
  • 문제는 같은 판매자 지갑에 정산이 동시에 몰릴 때의 Lost Update입니다. @Version으로 충돌을 감지하고, 최신 잔액을 다시 읽어 이번 금액만 더해 최대 3회 재시도합니다. 수정함 대기는 예전 0~100ms 랜덤에서 지수 백오프(50ms부터, 상한 1초) + equal jitter로 바뀌었습니다. 지갑·거래 순서가 고정돼 동시 정산끼리의 교착 가능성이 줄고, 교착으로 희생된 트랜잭션은 같은 방식으로 다시 시도됩니다.
  • 근거: JpaWalletRepositoryTest가 스레드 3개 동시 저장 후 version 3, 잔액 6000을 5회 반복 검증합니다.
  • 비교 일반 지식: 비관적 락은 충돌이 잦을 때 안정적이지만 락 대기와 데드락 관리가 필요합니다. UPDATE … SET balance = balance + ?는 가장 간단하고 충돌 자체가 없지만 이력과 도메인 규칙이 SQL로 흩어집니다. 인기 판매자처럼 hot row라면 원자적 UPDATE나 판매자별 파티션 직렬 처리가 더 낫다고 답합니다.

DLQ는 어떻게 동작하나요?

복구·릴레이 스케줄러가 실제로는 한 번도 돌지 않는다 확실 수정함

레포 어디에도 @EnableScheduling이 없어서 @Scheduled가 무시됩니다. 게다가 두 서비스 모두 @Profile("dev")인데 dev 프로필을 켜는 설정이 없어서 빈 자체가 만들어지지 않습니다. 그 결과 UNKNOWN이나 멈춘 EXECUTING은 회복되지 않고, AFTER_COMMIT 발행에 실패한 outbox는 영원히 INIT으로 남습니다.

개선 방향: 설정 클래스에 @EnableScheduling을 추가하고 프로필 조건을 운영에서도 켜지게 바꿉니다. 여러 인스턴스로 띄울 때는 ShedLock 같은 분산 락이나 SELECT … FOR UPDATE SKIP LOCKED로 중복 실행을 막습니다. 마지막 실행 시각과 처리 건수를 메트릭으로 노출해 "안 도는 스케줄러"를 탐지합니다.

수정함 @Profile("dev")를 없애고, 인바운드 어댑터 PaymentScheduler(@EnableScheduling + @ConditionalOnProperty(payment.scheduler.enabled, 기본 true))가 두 유스케이스를 3분마다 부릅니다. 유스케이스는 Mono를 돌려주고 스케줄러가 block으로 기다려 회차가 겹치지 않습니다. 다중 인스턴스 중복은 복구 쪽 선점 UPDATE로 막고, 릴레이는 at-least-once라 소비자 멱등성에 맡깁니다. 실행 메트릭은 아직 없습니다.

최종 상태 전이가 이전 상태를 확인하지 않고, EXECUTING 중 동시 confirm도 통과한다 확실 수정함

updatePaymentStatusToSuccess/Failure/Unknown은 WHERE order_id = ?로 무조건 덮어씁니다. 늦게 끝난 요청이 SUCCESS를 UNKNOWN으로 덮는 것도 가능합니다. 진입 검사도 EXECUTING을 허용하므로, 같은 건에 동시 요청 두 개가 모두 PSP까지 갑니다(이중 승인은 Idempotency-Key로 막힌다는 전제, 추정). 덧붙여 존재하지 않는 orderId는 EXECUTING 전이가 0행으로 "성공"하고, SUM(amount)가 NULL이라 NPE가 나서 UNKNOWN 응답을 받습니다.

수정함 모든 전이가 한 트랜잭션에서 SELECT … FOR UPDATE로 주문 행을 잠그고 이전 상태를 확인한 뒤, WHERE payment_order_status IN (…) 조건부 UPDATE를 합니다. 최종 상태는 EXECUTING·UNKNOWN에서만, confirm 선점은 NOT_STARTED·UNKNOWN에서만 허용합니다. 이미 SUCCESS·FAILURE면 덮어쓰지 않고 no-op, 처리 중(EXECUTING)인 결제의 재요청은 PSP를 부르지 않고 EXECUTING으로 응답합니다. 복구는 UNKNOWN·3분 넘은 EXECUTING만 선점합니다. 없는 orderId는 DB에 쓰지 않고 PAYMENT_NOT_FOUND FAILURE입니다. 동시 confirm 8개 → PSP 1회를 테스트로 확인합니다.

라이브러리 동작에 기대는 부분들 추정
  • 타임아웃 재시도 필터: WebClient는 요청 단계의 I/O 오류를 WebClientRequestException으로 감쌉니다. 그래서 instanceof TimeoutException이 맞지 않아 즉시 재시도가 안 될 수 있습니다(에러 분류도 "그 외" → UNKNOWN). 개선: Exceptions.unwrap이나 cause 체인을 검사합니다.
  • unicast sink + FAIL_FAST: 여러 스레드가 동시에 emitNext하면 FAIL_NON_SERIALIZED로 발행에 실패할 수 있습니다. 수정함 EmitFailureHandler.busyLooping(2s)로 바꿨습니다.
  • Kafka 트랜잭션과 DB 트랜잭션이 따로: wallet·ledger는 transaction-id-prefix를 설정했지만, JPA 저장(TransactionTemplate, saveAll)과 streamBridge.send가 하나로 묶여 있지 않습니다. 실제로는 "DB 커밋 → 발행"이고, 발행에 실패하면 재전달과 멱등성 검사에 기대게 됩니다.

repeated에서 새로 만든 Provider가 실제 암호화에 쓰이는가? — 쓰이지 않음, 확인함 수정함

확인 결과 (ProviderRegistrationTest): BC가 이미 있으면 Security.addProvider(new BouncyCastleProvider())는 -1을 돌려주고 목록을 바꾸지 않습니다. AesUtilBefore.encrypt를 여러 번 불러도 이름이 BC인 Provider는 처음 그 인스턴스 하나이고, Cipher.getInstance(T, "BC").getProvider()는 그 등록 인스턴스와 같은 객체입니다. 매번 만든 Provider는 할당 비용(op당 약 2.85MB)만 남기고 버려집니다.

원래 분석: AesUtilBefore는 새 인스턴스를 addProvider한 뒤 이름 "BC"로 Cipher.getInstance합니다. 같은 이름이 이미 등록돼 있으면 addProvider는 추가하지 않으므로(일반 지식), 암호화에는 처음 등록된 인스턴스가 쓰이고 새 인스턴스는 버려질 가능성이 높습니다. 그렇다면 repeated도 공유 Provider의 getService를 거치는 셈인데, 이를 검증한 측정은 저장소에 없습니다. 면접에서는 "확인 필요"로 답하는 게 안전합니다.
