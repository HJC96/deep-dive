캐시 패턴 실험실 — 읽기·쓰기 패턴 5개와 장애 3대장을 순수 Java로

캐시는 "넣으면 빨라진다"로 끝나지 않습니다. 언제 채우고, 언제 지우고, 동시에 몰리면 어떻게 되는지에 따라 오래된 값이 남거나 DB가 터집니다. 이 모듈은 Redis·Spring 없이 InMemoryCache와 InMemoryProductStore만으로 패턴마다 작은 클래스를 만들고, 저장소 read/write 횟수를 세는 단위 테스트로 차이를 확인합니다.

Java 21순수 Java (Spring 없음)JUnit 5 + AssertJInMemoryCacheRedis 없음

01한눈에

30초 요약

문제

캐시를 잘못 채우거나 지우면 DB와 다른 오래된 값이 남고, 인기 키 동시 miss·없는 키 반복 조회·동시 만료가 일어나면 요청이 DB로 몰립니다.

접근

읽기 2개(Cache Aside, Read Through), 쓰기 3개(Write Through/Around/Behind), race 1개, 3대장(Stampede/Penetration/Avalanche) 방어 클래스를 각각 만들고 저장소 호출 횟수로 비교.

결론

일반 조회는 Cache Aside + Write Around(쓰기 후 evict)가 기본값. 문제별로 single-flight / refresh-ahead, negative caching / Bloom filter, TTL jitter, 버전 비교를 덧붙입니다.

02흐름

README의 학습 순서입니다. 단계를 클릭하면 무엇을 보는지 나옵니다.

→ → →

누가 저장소를 호출하느냐의 차이. Cache Aside는 서비스가 miss를 확인하고 직접 store.findById, Read Through는 서비스가 readThroughCache.get만 부르고 캐시 계층이 loader로 저장소를 부릅니다.

쓰기 직후 캐시에 무엇이 남느냐의 차이. Write Through는 최신 값(put), Write Around는 비움(evict), Write Behind는 캐시만 최신이고 저장소는 flush() 때 반영.

Cache Aside에서 읽기가 v1을 읽은 뒤, 쓰기가 v2 저장 + evict를 끝내고, 읽기가 뒤늦게 v1을 put하면 캐시 v1 / 저장소 v2로 어긋납니다. 방어: VersionedCache(낮은 버전 put 거부).

  • Stampede: 인기 키 동시 miss → SingleFlightCache, RefreshAheadCache
  • Penetration: 없는 키 반복 조회 → NegativeCachingCache, BloomFilter
  • Avalanche: 많은 키 동시 만료 → ExpiringCache + TTL jitter

패턴별 App ↔ Cache ↔ DB 흐름

실선은 호출, 점선은 응답. 탭을 눌러 패턴을 바꿔 보세요.

서비스가 직접 miss를 확인하고 저장소에서 읽어 캐시에 넣습니다. 쓰기 때는 저장 후 evict. 가장 흔한 형태이고 캐시 정책을 코드에서 명시적으로 제어합니다.

서비스 코드는 products.get(id) 한 줄. miss 처리와 loader 호출은 ReadThroughCache가 담당합니다. 실무에선 Caffeine 같은 loading cache나 Redis 앞 공통 래퍼로 표현된다고 README가 설명합니다(Redis 단독으로는 Read Through가 자동으로 생기지 않음).

저장 직후 캐시에도 최신 값이 있으므로 다음 읽기는 바로 hit. 대신 쓰기 경로가 두 곳을 거쳐 느려지고, 저장 성공 후 캐시 put 실패 같은 부분 실패를 처리해야 합니다.

쓰기는 캐시를 "돌아서" 저장소에만. 읽히지 않을 데이터가 캐시를 오염시키지 않습니다. 첫 읽기 요청자가 재적재 비용을 냅니다. 코드는 Cache Aside 서비스와 거의 같고, README는 "관찰 포인트가 달라 이름만 다르다"고 설명합니다.

응답이 가장 빠르고 저장소 쓰기를 모을 수 있지만, 이 예제의 pendingWrites는 메모리 Map이라 flush 전 종료 시 유실됩니다. README: 실무에서는 영속 큐, retry, idempotency, 실패 보상 흐름이 필요.

03비교·핵심 구현

탭을 눌러 케이스별로 봅니다. 코드는 실제 파일에서 발췌했습니다.

Cache Aside vs Read Through 핵심: 누가 저장소를 부르나

Cache Aside — 서비스가 직접

public Optional<Product> findById(long id) {
    Optional<Product> cached = cache.get(id);
    if (cached.isPresent()) {
        return cached;
    }

    Optional<Product> loaded = store.findById(id);
    loaded.ifPresent(product -> cache.put(id, product));
    return loaded;
}

Read Through — 캐시 계층이 loader로

// ReadThroughCache
public Optional<V> get(K key) {
    Optional<V> cached = cache.get(key);
    if (cached.isPresent()) {
        return cached;
    }

    Optional<V> loaded = loader.apply(key);
    loaded.ifPresent(value -> cache.put(key, value));
    return loaded;
}

// ReadThroughProductService
public Optional<Product> findById(long id) {
    return products.get(id);
}
결과
ReadPatternTest: 두 패턴 모두 같은 id를 두 번 읽으면 store.readCount()==1, misses==1, hits==1. 쓰기 후 containsKey(1L)는 false, 다음 읽기에서 readCount()==2.
트레이드오프
Cache Aside는 단순하지만 서비스마다 miss 코드가 반복. Read Through는 로딩 규칙을 공유하지만 캐시 계층이 저장소 loader를 알아야 하고 계층이 하나 늘어남. 쓰기 정책은 둘 다 별도로 골라야 함.

Write Through / Around / Behind

패턴save() 안에서쓰기 직후 캐시저장소 반영잘 맞는 상황
Write Throughstore.save → cache.put최신 값 있음요청 안에서 즉시쓰기 직후 같은 값을 바로 읽음
Write Aroundstore.save → cache.evict해당 key 없음요청 안에서 즉시쓴 데이터가 바로 읽힌다는 보장이 없음
Write Behindcache.put → pendingWrites.put최신 값 있음flush() 때 나중에쓰기 응답 속도·처리량이 중요
 
// WriteThroughProductService
Product saved = store.save(product);
cache.put(product.id(), saved);

// WriteAroundProductService
Product saved = store.save(product);
cache.evict(product.id());

// WriteBehindProductService
cache.put(product.id(), product);
pendingWrites.put(product.id(), product);
// ...
public void flush() {
    for (Product product : new ArrayList<>(pendingWrites.values())) {
        store.save(product);
        pendingWrites.remove(product.id());
    }
}
결과
WritePatternTest: Through는 write 1 · read 0 · 바로 hit. Around는 write 1 · 쓰기 직후 캐시 없음 · 두 번 읽어 read 1, hit 1. Behind는 저장 직후 write 0 · pending 1 · 저장소엔 이전 값(180,000) → flush() 후 write 1 · pending 0.
왜 Around가 evict?
README: 캐시에 새 값을 넣지 않는 전략이라, 기존 캐시 값이 남아 있으면 저장소보다 오래된 값을 반환할 수 있어서 제거한다.

Cache Aside race와 VersionedCache stale 재유입

// VersionedCache
public void put(K key, long version, V value) {
    Versioned<V> current = values.get(key);
    if (current != null && version < current.version()) {
        rejectedPuts++;
        return;
    }
    values.put(key, new Versioned<>(version, value));
}
어떻게
값과 함께 단조 증가 버전을 저장하고, 현재보다 낮은 버전의 put은 버립니다(같거나 크면 반영).
결과
StaleCachePutRaceTest: 보호 없음 → 캐시 v1, 저장소 v2로 어긋남. VersionedCache → 버전 2(v2) 후 버전 1(v1) put이 거부되어 get==v2, rejectedPuts()==1.
주의
테스트에서 쓰기 B는 evict가 아니라 버전 2로 put합니다. evict하면 버전 정보도 지워져 이후 v1 put이 통과합니다(아래 약점 참고).

Cache Stampede — SingleFlightCache / RefreshAheadCache

// SingleFlightCache
public V get(K key, Function<K, V> loader) {
    V cached = values.get(key);
    if (cached != null) {
        return cached;
    }

    Object lock = locks.computeIfAbsent(key, k -> new Object());
    synchronized (lock) {
        // 락을 잡은 사이 다른 스레드가 이미 채웠을 수 있으므로 다시 확인한다.
        V again = values.get(key);
        if (again != null) {
            return again;
        }

        V loaded = loader.apply(key);
        values.put(key, loaded);
        return loaded;
    }
}
// RefreshAheadCache
long age = now - entry.loadedAt();
if (age >= ttlMillis * refreshThreshold) {
    // 아직 만료 전이라 stale gap 없이 미리 갱신한다.
    return load(key, loader, now);
}
Single-flight
키별 락 객체 + 락 안 double-check. 16스레드 동시 miss여도 load 1회, 나머지는 결과 공유.
Refresh-ahead
TTL 1000ms, threshold 0.8. t=500 재로드 없음 → t=900 미리 갱신(v2) → expireAt이 1900으로 밀려 원래 만료 시점 t=1000에도 hard-miss 없음.
트레이드오프
single-flight는 대기 스레드가 락에서 막힘(이 구현은 같은 JVM 안에서만 유효). refresh-ahead는 안 읽힐 값도 갱신할 수 있음.
코드

Cache Penetration — NegativeCachingCache / BloomFilter

Cache Aside는 loaded.ifPresent(... put)이라 없는 값은 캐시에 안 남습니다. 그래서 없는 id를 반복 조회하면 매번 저장소까지 관통합니다.

// NegativeCachingCache: empty도 저장
Optional<V> cached = values.get(key);
if (cached != null) {
    // empty 마커도 hit으로 취급한다.
    return cached;
}
Optional<V> loaded = loader.apply(key);
values.put(key, loaded);

// BloomFilter: 하나라도 비트가 0이면 "확실히 없음"
public boolean mightContain(T value) {
    for (int seed = 0; seed < hashCount; seed++) {
        if (!bits.get(indexFor(value, seed))) {
            return false;
        }
    }
    return true;
}
Negative
첫 조회만 저장소 read, 이후는 empty hit. README: 짧은 TTL 권장 — 나중에 실제 값이 생겨도 empty가 오래 남으면 새 값을 가림.
Bloom
false는 "확실히 없음", true는 "있을 수도 있음"(false positive 가능). 테스트는 BloomFilter(1024, 3)에 1L만 넣고 99L을 걸러 저장소 read 0.
코드

Cache Avalanche — ExpiringCache + TTL jitter

개념도입니다. 막대 위치는 테스트 데이터의 실제 분포가 아니라 "고정 TTL은 한 점, 지터는 구간"이라는 모양만 보여 줍니다.

// CacheAvalancheTest
Random jitter = new Random(42); // 결정론적 지터

for (int i = 0; i < KEYS; i++) {
    long ttl = BASE_TTL + jitter.nextInt(500); // [1000, 1500)
    cache.put(i, "v" + i, ttl);
}
어떻게
ExpiringCache는 키마다 expireAt를 갖고, 시계(Clock)를 주입받아 테스트에서 MutableClock으로 시간을 흘립니다. 지터는 캐시가 아니라 호출자가 TTL을 다르게 주는 방식.
결과
고정 TTL: t=1000에 active 0 (100개 동시 만료). 지터: t=1000에 >0, t=1250에도 >0 (그리고 ≤ t=1000 값), t=1500에 0.

05한계·약점

README 인정 문서·주석이 스스로 밝힌 한계, 코드 확인 코드를 읽어 보면 드러나는 약점.

README 인정 실제 분산 캐시가 아니다 (Redis 없음)

"외부 Redis 없이 InMemoryCache 사용", 저장소는 InMemoryProductStore. 네트워크 지연, 직렬화, 캐시 서버 장애, 여러 서버 간 무효화 전파는 다루지 않습니다. Redis 버전은 labs/spring-cache-redis에서 봅니다.

README 인정 Write Behind 대기열은 메모리 Map — 유실 위험

pendingWrites가 LinkedHashMap이라 flush 전에 프로세스가 죽으면 변경이 사라집니다. flush 실패 시 재시도·부분 실패 처리도 없습니다(저장 1건 실패 시 예외로 루프 중단). README: 영속 큐, retry, idempotency, 보상 흐름 필요.

주석 인정 NegativeCachingCache에 TTL이 없다

javadoc: "이 예제는 TTL 없이 negative 캐싱의 효과만 보여준다." 한 번 empty가 저장되면 나중에 실제 상품이 생겨도 영원히 empty를 돌려줍니다. 무효화 메서드(evict)도 없습니다. README는 짧은 TTL을 권장만 합니다.

주석 인정 RefreshAheadCache는 "백그라운드"가 아니라 동기 갱신

javadoc 첫 문단은 "즉시 응답하면서도 백그라운드로 새로 적재"라고 쓰지만, 바로 뒤에 "결정론적 검증을 위해 동기적으로 refresh한다"고 밝힙니다. 실제로 threshold를 넘긴 요청 스레드가 loader.apply를 직접 기다립니다.

코드 확인 게다가 내부가 HashMap이고 락이 없어, 동시 요청 여러 개가 threshold를 넘기면 모두 refresh를 실행합니다(stampede 방어 의도와 상충). 동시성 테스트는 없습니다.

코드 확인 VersionedCache는 evict 기반 race를 막지 못한다

evict()가 values.remove(key)로 버전 정보까지 지웁니다. 실제 Cache Aside처럼 쓰기 B가 evict하면 이후 읽기 A의 버전 1 put은 비교할 현재 값이 없어 그대로 통과합니다. 테스트는 쓰기 B가 버전 2로 put하는 시나리오라 이 구멍이 드러나지 않습니다. 또 버전은 호출자가 수동으로 넘기며, 저장소의 버전 컬럼과 연동되지 않습니다.

코드 확인 race 테스트는 실제 동시성이 아니라 순차 호출로 재현

StaleCachePutRaceTest는 서비스를 거치지 않고 store.findById → store.save → cache.evict → cache.put을 한 스레드에서 순서대로 호출해 "교차"를 흉내 냅니다. 결정적이라 이해하기 좋지만, CacheAsideProductService 자체의 race를 스레드로 보여 주지는 않습니다.

코드 확인 Stampede "보호 없음" 테스트는 서비스 코드가 아니다

보호 없음 케이스는 CacheAsideProductService가 아니라 테스트 안의 ConcurrentHashMap과 CountDownLatch로 "모든 스레드가 miss를 확인할 때까지 기다린 뒤 로드"하도록 강제합니다. 그래서 16은 설계상 최악의 경우이지 자연 발생 빈도가 아닙니다.

코드 확인 대부분의 캐시 클래스가 thread-safe하지 않다

InMemoryCache(LinkedHashMap, hits/misses int), VersionedCache, NegativeCachingCache, RefreshAheadCache, ExpiringCache(HashMap)는 동기화가 없습니다. 동시성을 고려한 것은 SingleFlightCache뿐입니다. 단일 스레드 학습용으로 읽어야 합니다.

코드 확인 SingleFlightCache: 만료·무효화 없음, 락 객체 누적, null 불가
  • 한 번 넣은 값은 영원히 남습니다(TTL·evict 메서드 없음).
  • locks 맵의 키별 락 객체를 지우지 않아 키 수만큼 쌓입니다.
  • ConcurrentHashMap은 null 값을 거부하므로 loader가 null을 반환하면 NPE.
  • synchronized라 같은 JVM 안에서만 유효. 서버가 여러 대면 분산 락이 필요(→ labs/spring-cache-redis).
코드 확인 Bloom filter는 서비스에 통합되지 않았다

테스트가 직접 if (existingIds.mightContain(MISSING_ID))로 감쌉니다. 서비스·캐시 계층에 끼워 넣은 구현은 없고, false positive 비율이나 상품 추가/삭제 시 필터 갱신은 다루지 않습니다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요. 일반 지식은 이 레포 밖의 널리 알려진 내용입니다.

Cache Aside와 Read Through의 차이는?
  • 핵심은 miss 시 저장소를 누가 호출하느냐. Aside는 서비스, Read Through는 캐시 계층(loader).
  • Aside: 단순·명시적, 대신 서비스마다 miss 코드 반복. Read Through: 로딩 규칙 공유, 대신 캐시 계층이 저장소를 알아야 함.
  • 이 레포에선 둘 다 2회 읽기에 store read 1 (ReadPatternTest). 결과는 같고 책임 위치가 다름.
  • 꼬리질문 대비: Redis만 두면 Read Through가 생기지 않는다 → Caffeine LoadingCache나 공통 래퍼로 구현 (README).
쓰기 시 캐시를 갱신(put)하지 않고 삭제(evict)하는 이유는?
  • README의 일반 조회 추천은 Cache Aside + Write Around(evict). 읽히지 않을 데이터로 캐시를 오염시키지 않고, 다음 읽기가 저장소 최신 값을 다시 적재.
  • 일반 지식 두 쓰기가 동시에 put하면 DB 커밋 순서와 캐시 put 순서가 뒤집혀 오래된 값이 남을 수 있음. 삭제는 "다음 읽기에서 다시 읽기"로 수렴하므로 상대적으로 안전.
  • 단, 삭제해도 읽기·쓰기 교차 race는 남음 → 다음 질문.
Cache Aside에서 오래된 값이 캐시에 다시 들어가는 시나리오와 대책은?
  • 읽기 A가 miss → v1 조회 → (쓰기 B가 v2 저장 + evict) → A가 뒤늦게 v1 put. 결과: 캐시 v1, 저장소 v2.
  • 이 레포의 대책: VersionedCache — 낮은 버전 put 거부(rejectedPuts).
  • 약점까지 말하기: evict하면 버전 정보가 사라져 막지 못함 → 삭제 대신 "버전 마커(tombstone)"를 남기거나 TTL로 피해 기간을 제한.
  • 일반 지식 짧은 TTL, 지연 이중 삭제(delayed double delete), DB 변경 이벤트(CDC) 기반 무효화도 흔한 대안.
Write Through / Around / Behind는 각각 언제 쓰나?
  • Through: 쓰기 직후 바로 읽음. 쓰기 경로가 느려지고 부분 실패(저장 성공·캐시 실패) 처리 필요.
  • Around: 쓴 데이터가 바로 읽힌다는 보장이 없음. 첫 읽기 비용을 읽기 요청자가 부담.
  • Behind: 쓰기 처리량이 최우선. 일시적 불일치 + 유실 위험 → 영속 큐, retry, idempotency (README).
Cache Stampede를 설명하고 막는 방법은?
  • 인기 키가 동시에 miss/만료되면 요청이 한꺼번에 저장소로. 테스트에선 16스레드 → load 16.
  • Single-flight: 키별 락 + 락 안 double-check → load 1. Refresh-ahead: TTL 80% 시점에 미리 갱신해 hard-expiry 자체를 없앰.
  • 꼬리질문: 이 구현은 synchronized라 JVM 하나에서만 유효. 서버가 여러 대면 Redis SET NX 락 등 분산 락 필요.
  • 일반 지식 확률적 조기 만료(PER), 만료 시 stale 값을 주면서 비동기 갱신하는 stale-while-revalidate도 있음.
Cache Penetration 방어: negative caching과 Bloom filter의 장단점은?
  • Negative caching: 구현 쉬움, 첫 조회 1회만 저장소. 대신 없는 키마다 캐시 공간을 쓰고, TTL이 길면 새로 생긴 값을 가림 (이 구현은 TTL 없음).
  • Bloom filter: 메모리 적게 쓰고 저장소 조회 전 차단. false=확실히 없음, true=있을 수도. false positive 존재.
  • 일반 지식 기본 Bloom filter는 원소 삭제가 불가능해 데이터 삭제가 잦으면 재구축하거나 Counting Bloom filter를 씀. 공격성 랜덤 키는 입력 검증·rate limit도 함께.
Cache Avalanche와 TTL jitter는?
  • 같은 TTL로 대량 적재하면 같은 순간에 만료 → 저장소 폭주. 테스트: 고정 TTL 100키가 t=1000에 모두 만료.
  • jitter로 TTL을 [1000,1500)로 흩어 만료를 시간에 걸쳐 분산.
  • 일반 지식 캐시 서버 자체 장애로 인한 avalanche는 jitter로 못 막음 → 캐시 이중화, 로컬+원격 2단 캐시, 서킷 브레이커·rate limit.
동시성·시간 문제를 테스트에서 어떻게 결정적으로 재현했나?
  • 시간: Clock 인터페이스를 주입하고 테스트는 MutableClock.advance/setTo로 시간을 직접 흘림 (TTL·refresh-ahead·avalanche).
  • 난수: new Random(42)로 지터를 고정.
  • 동시성: CountDownLatch로 16스레드를 동시에 출발시키고, 보호 없음 케이스는 모든 스레드가 miss를 본 뒤 로드하도록 강제.
  • race: 순차 호출로 교차 순서를 고정 (한계: 진짜 스레드 race는 아님).
(꼬리) Refresh-ahead 구현을 운영 수준으로 바꾸려면?
  • 현재: 요청 스레드가 동기로 갱신, HashMap·락 없음 → 동시 요청이 각자 refresh.
  • 개선: 갱신을 별도 executor로 비동기 실행하고 기존 값을 즉시 반환, 키별 "갱신 중" 플래그나 single-flight로 1회만 갱신.
  • 일반 지식 Caffeine의 refreshAfterWrite가 이 모델(비동기 갱신 중 기존 값 제공)을 제공.
