Spring Boot Actuator — 상태·버전·횟수·현재값·시간을 관측하는 13단계

운영 중인 앱이 살아 있는지, 어떤 빌드가 떠 있는지, 무엇이 몇 번 일어났고 얼마나 느린지 모르면 장애에 대응할 수 없습니다. 이 모듈은 Postman 폴더 0~12를 따라 Health·Info·Counter·Gauge·Timer 3종·Percentile·HTTP 메트릭·커스텀 엔드포인트를 각각 가장 작은 예제로 만들어 /actuator 응답으로 확인합니다.

Java 21Spring Boot 3.4.1MicrometerAOP (@Timed/@Counted)App :8080 · Actuator :9090Postman 컬렉션

01한눈에

30초 요약

문제

로그만으로는 “지금 트래픽을 받아도 되나”, “어느 버전이 떠 있나”, “p99가 얼마나 느린가”에 답할 수 없습니다.

접근

관리 포트 9090에 health·info·metrics·features만 노출. 섹션마다 앱 API를 호출 → /actuator/metrics/{name}?tag=k:v로 값 변화를 관찰(README + Postman). 대표 동작은 ActuatorEndpointTest·CustomMetricsTest가 HTTP로 검증.

결론

질문에 맞는 타입을 고르는 것이 핵심: 상태=Health, 버전=Info, 횟수=Counter, 현재 개수=Gauge, 시간=Timer, 꼬리 지연=Percentile. 태그는 값 종류가 적은 것만.

02흐름

단계를 클릭하면 상세 설명이 나옵니다. 메트릭이 만들어져 조회되기까지.

→ → → →

예: POST /notifications/email, POST /files/convert, GET /contents/search?keyword=.... Spring MVC 요청은 자동으로 http.server.requests Timer에도 기록됩니다(섹션 11).

직접 기록: Counter.increment(), Timer.record(() -> ...), Timer.Sample.stop(timer). AOP 기록: @Counted/@Timed — MetricsAspectConfig의 CountedAspect·TimedAspect 빈 + spring-boot-starter-aop가 있어야 동작. Gauge는 기록하지 않고 조회 시점에 List::size를 호출합니다.

모든 meter에 공통 태그가 붙습니다: 설정 management.metrics.tags(application=actuator-lab, environment=local, region=kr) + 코드 MetricsTagConfig의 MeterFilter.commonTags(hostname).

GET :9090/actuator/metrics/app.notification.sent?tag=channel:email → measurements(COUNT / TOTAL_TIME / MAX / VALUE)와 availableTags. Timer 평균 = TOTAL_TIME / COUNT. 필터는 availableTags에 보이는 값 기준.

POST /partners/system/down → PartnerSystemHealthIndicator가 Health.down() 반환 → /actuator/health/partnerSystem body status: DOWN, HTTP 503(기본 매핑). 컴포넌트 id partnerSystem은 빈 이름에서 HealthIndicator를 뗀 것.

03비교·핵심 구현

먼저 “무엇을 알고 싶은가”로 타입을 고르고, 아래 13개 섹션 지도와 탭에서 코드를 봅니다.

어떤 걸 쓰나 — README “선택 기준”

Health

정상/비정상인가?
외부 시스템 연결, 트래픽 수용 가능 여부. DOWN이면 503.

Info

어떤 버전이 떠 있나?
build/git/커스텀 release 정보.

Counter

몇 번 일어났나?
단조 증가 누적. 발송 성공 수, 요청 수.

Gauge

지금 몇 개인가?
오르내리는 현재값. 대기열 크기.

Timer

얼마나 걸렸나?
COUNT + TOTAL_TIME + MAX. record / Sample / @Timed.

Percentile

느린 꼬리는?
p50 중앙값, p95, p99(tail latency). 평균이 숨기는 지연.

Tag

조건별로 나눠 보기
channel=email, result=fail. 값 종류가 적어야 함.

Common Tags

앱/환경/인스턴스 식별
모든 metric에 application·environment·region·hostname.

Custom Endpoint

운영용 조작 창구
@Endpoint로 기능 토글 읽기/쓰기/삭제. 인증 필요.

설정
management.server.port: 9090(앱 8080과 분리), show-details/show-components: always, management.info.env.enabled: true(→ yml의 info.app.*, info.team 노출), git.mode: simple.

Boot 플러그인 대신 build.gradle의 커스텀 태스크 generateBuildInfo(META-INF/build-info.properties), generateGitProperties(git rev-parse로 git.properties)를 processResources 전에 실행.
포인트

Counter · @Counted · Tags 횟수

// NotificationService 생성자 — 태그 없는 "전체" counter는 두지 않는다
this.emailNotificationCounter = sentCounter(meterRegistry, "email");
this.smsNotificationCounter = sentCounter(meterRegistry, "sms");
this.otherNotificationCounter = sentCounter(meterRegistry, "other"); // 나머지 channel 값

private static Counter sentCounter(MeterRegistry meterRegistry, String channel) {
    return Counter.builder("app.notification.sent")
            .tag("channel", channel)
            .tag("region", "kr")
            .register(meterRegistry);
}

@Counted(value = "app.notification.requested", description = "알림 발송 요청 횟수")
public NotificationReceipt send(String channel, String recipient, String message) {
    NotificationReceipt receipt = new NotificationReceipt(channel, recipient, message, "SENT");
    counterFor(channel).increment(); // email / sms / other 중 하나만
    return receipt;
}

// MetricsTagConfig
return MeterFilter.commonTags(List.of(Tag.of("hostname", hostname())));
Counter vs @Counted
Counter: 성공한 경우만 코드에서 직접 증가. @Counted: 메서드 호출 횟수를 AOP로 자동 기록.
필터
?tag=channel:email, 복수 태그 ?tag=channel:email&tag=region:kr. 필터 없이 조회하면 같은 이름의 시계열을 모두 더한 값 — 그래서 전체 합계용 태그 없는 counter를 따로 두면 이중 집계된다.
좋은/나쁜 태그
좋음: application, environment, region, hostname. 나쁨: userId, email, requestId, 전체 URL — 값 종류가 무한히 늘면 카디널리티 폭발.

Gauge — 값을 저장하지 않고 조회 시점에 읽음 현재값

// PendingNotificationManager
private final List<String> pendingNotifications = Collections.synchronizedList(new ArrayList<>());

public PendingNotificationManager(MeterRegistry meterRegistry) {
    // Gauge는 값을 저장하지 않고 actuator 조회 시점에 List::size를 호출한다.
    Gauge.builder("app.notification.pending.size", pendingNotifications, List::size)
            .description("현재 발송 대기 중인 알림 수")
            .register(meterRegistry);
}
흐름
enqueue 2번 → VALUE 2 → dequeue → VALUE 1 (README 요청 순서표의 기대값).
Counter와 차이
Counter: “몇 번 발생했나”(누적, 줄지 않음). Gauge: “지금 몇 개인가”(오르내림).

Timer.record · Timer.Sample · @Timed 시간

// 7. Timer.record — 특정 블록 (FileProcessingService)
return fileConversionTimer.record(() -> doConvert(fileName, format)); // 내부 sleep(2_000)

// 8. Timer.Sample — 시작/종료 분리, 결과별 태그 (DocumentValidationService)
Timer.Sample sample = Timer.start(meterRegistry);
String result = "error";              // 예외로 끝나면 이 값이 tag가 된다
try {
    boolean passed = callExternalValidator(documentType, valid); // 350/600ms
    result = passed ? "success" : "fail"; // 실제 결과를 본 뒤 결정
    return new DocumentValidationResult(documentType, passed, result);
} finally {
    Timer timer = Timer.builder("app.document.validation.time")
            .tag("result", result)
            .register(meterRegistry);
    sample.stop(timer);
}

// 9. @Timed — 메서드 전체 (ReportService)
@Timed(value = "app.report.generation.time", description = "리포트 생성 작업 소요 시간")
public ReportResult generate(String reportType) { sleep(750); /* ... */ }
방식쓰임 (README)주의
Timer.record특정 코드 블록 측정람다 안 코드만 측정
Timer.Sample결과 기반 태그, 시작/종료 위치가 다름try/finally로 stop() 보장, 예외면 result=error
@Timed메서드 전체 시간TimedAspect 빈 + AOP 필요, 프록시 경유 호출만

Percentile — 평균이 숨기는 느린 꼬리 tail latency

@Timed(
        value = "app.content.search.time",
        description = "콘텐츠 검색 API 응답 시간",
        percentiles = {0.5, 0.95, 0.99}
)
public ContentSearchResult search(String keyword) {
    sleep(delayFor(keyword));
    // ...
}

private long delayFor(String keyword) {
    return switch (keyword.length() % 3) {
        case 0 -> 120;
        case 1 -> 450;
        default -> 900;
    };
}
조회
app.content.search.time.percentile?tag=phi:0.95 — 별도 metric 이름에 phi 태그로 분위수가 나뉩니다. phi 없이 조회하면 세 분위수 값의 합(실측 약 2.35)이 나와 지연 시간으로 읽을 수 없습니다.
지연 예
키워드 길이 % 3 기준(코드 상수): actuator(8자) → 900ms, observability(13자) → 450ms.
의미
p50 중앙값, p95 = 95% 요청이 이 시간 이하, p99 = 느린 꼬리 구간.

자동 수집 — 코드 없이 생기는 메트릭 무료

  • jvm.memory.used (area: heap/nonheap)
  • jvm.gc.pause, jvm.threads.live
  • system.cpu.usage, process.cpu.usage, process.uptime

11. HTTP Metrics

  • http.server.requests Timer
  • 기본 태그: method, status, uri, outcome, exception
  • 예: ?tag=uri:/files/convert, ?tag=status:404

앱 API를 호출해야 값이 생깁니다. 체크리스트: “metric 이름이 없음 → 관련 App API 호출 여부”, “MAX가 갑자기 낮음 → Micrometer time window 리셋 가능성”.

Custom Endpoint — @Endpoint(id = "features") 인증 필요

@Component
@Endpoint(id = "features")
public class FeatureToggleEndpoint {
    private final Map<String, Boolean> toggles = new ConcurrentHashMap<>();

    @ReadOperation                       // GET /actuator/features
    public Map<String, Boolean> features() { return toggles; }

    @ReadOperation                       // GET /actuator/features/{name}
    public Map<String, Object> feature(@Selector String name) { ... }

    @WriteOperation                      // POST /actuator/features/{name}  body {"enabled": true}
    public Map<String, Object> setFeature(@Selector String name, Boolean enabled) { ... }

    @DeleteOperation                     // DELETE /actuator/features/{name}
    public Map<String, Object> removeFeature(@Selector String name) { ... }
}
노출 조건
id는 소문자/숫자, exposure.include에도 features를 넣어야 보임(코드 주석).
주의
README: “운영용 custom endpoint는 인증/인가와 노출 범위 제어 필요.” 이 모듈에는 보안 설정이 없습니다.

05한계·약점

README가 스스로 밝힌 한계와, 코드에서 확인되는 약점.

코드 테스트가 contextLoads 하나뿐 수정함

어떻게 고쳤나: 앱·관리 포트를 랜덤으로 띄우는 @SpringBootTest(RANDOM_PORT, management.server.port=0) + TestRestTemplate로 ActuatorEndpointTest(health DOWN → 503, info의 app/team/build/release, features 쓰기·읽기·삭제)와 CustomMetricsTest(Counter·tag 필터, Gauge, Timer.record, @Timed, Timer.Sample result tag, percentile)를 추가했습니다. metric은 컨텍스트 안에서 누적되므로 호출 전후 차이로 검증합니다.

원래 ActuatorLabApplicationTest는 컨텍스트가 뜨는지만 봤습니다. Health 503, 메트릭 값, 태그 필터, 커스텀 엔드포인트 동작은 모두 Postman/curl(scripts/curl-actuator.sh)로 수동 확인하는 구조입니다.

README 수정함 로컬 절대경로 하드코딩

README “실행”이 개인 PC의 절대경로로 이동하는 줄로 시작하던 것을 지웠습니다. 프로젝트 루트에서 ./gradlew :spring-boot-actuator:run이면 됩니다.

README-코드 불일치 “현재 설정”에 info 블록 누락 수정함

어떻게 고쳤나: README “현재 설정” yml에 info 블록을 넣고 설정 표에 info.app.*, info.team 행을 추가했습니다.

원래 README “설정” 섹션의 yml에는 info.app.*, info.team이 없지만 실제 application.yml에는 있습니다(섹션 2에서 따로 보여 줌). 설정 표의 “/actuator/info에 app, team 표시”는 이 블록 덕분입니다.

코드 같은 이름에 태그 없는 Counter + 태그 있는 Counter — 이중 집계 확인 수정함

테스트로 확인: 예전 코드로 send(email)·email·sms 3회 후 필터 없는 app.notification.sent COUNT는 6.0이었습니다(email 필터 2.0). README 예시 3.0은 틀린 값이었습니다.

어떻게 고쳤나: 태그 없는 counter를 없애고 모든 시계열이 channel(email/sms/other)·region 태그를 갖게 했습니다. 정해지지 않은 channel 값은 other로 묶어 카디널리티도 막습니다. 이제 같은 3회 후 필터 없는 COUNT가 3.0이고 CustomMetricsTest가 이를 검증합니다.

원래 구조: app.notification.sent는 태그 없는 meter 1개와 channel=email/sms meter 2개로 등록되고, email 발송 시 두 meter가 모두 증가했습니다. 또 Prometheus 같은 레지스트리는 같은 이름에 태그 키 집합이 다른 meter를 허용하지 않는 경우가 있어 운영에선 “전체”를 별도 meter로 두기보다 태그 합산으로 구합니다.

README Percentile 예시 VALUE 0.45 — 틀린 값 확인 수정함

테스트로 확인: actuator(900ms)·observability(450ms) 2회 후 phi 0.5 ≈ 0.44~0.50, phi 0.95·0.99 ≈ 0.92, 필터 없는 조회 ≈ 2.35(= 세 값의 합). README의 “필터 없음 0.45”는 어떤 조회와도 맞지 않았습니다.

어떻게 고쳤나: README 예시를 ?tag=phi:0.95 조회(≈ 0.92)로 바꾸고 phi별 실측 표와 “필터 없는 VALUE는 합이라 해석 불가” 설명, 키워드별 지연 계산을 넣었습니다.

원래 README 예시는 필터 없는 app.content.search.time.percentile 조회에 VALUE 0.45를 보여 주지만, 필터가 없으면 phi 0.5/0.95/0.99 값이 함께 집계되고, 기본 키워드 actuator(8자)는 900ms 경로입니다. 실제 값은 다를 수 있습니다(코드 분석 추정, 실행 검증 안 됨). 분위수는 ?tag=phi:0.95처럼 하나씩 보는 것이 정확합니다.

코드 Timer.Sample의 result 태그는 작업 전에 이미 정해짐 수정함

어떻게 고쳤나: result 초깃값을 error로 두고, 외부 검증 호출이 정상으로 끝난 뒤 돌려받은 값으로 success/fail을 정합니다. 예외(문서 종류가 비어 있음)로 끝나면 result=error로 시간이 기록되는 것을 CustomMetricsTest가 검증합니다.

원래 README는 “결과를 본 뒤 tag 결정”이라고 하지만 코드는 valid 파라미터로 작업 전에 result를 정합니다. 작업 중 예외(InterruptedException → IllegalStateException)가 나도 success/fail 태그로 기록됩니다. 진짜 결과 기반이라면 예외 시 result=error 같은 분기가 필요합니다.

README 보안 · 운영 주의
  • 커스텀 엔드포인트는 인증/인가 필요(README). 현재 features는 보안 없이 쓰기/삭제 가능, 토글은 메모리에만 저장(재시작 시 사라짐).
  • show-details: always는 내부 정보를 노출합니다 — 관리 포트를 외부에 열지 않는 전제.
  • 일반 지식 partnerSystem 같은 외부 의존을 liveness 프로브에 포함하면 외부 장애 때 앱이 재시작 루프에 빠질 수 있어, 보통 readiness에만 반영합니다.
  • 일반 지식 percentiles는 인스턴스 안에서 계산되어 여러 인스턴스 간 합산이 불가 — 집계가 필요하면 histogram 발행.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

Health와 Metrics는 어떻게 다른가요?

Health는 지금 정상/비정상(UP/DOWN)인지 — 상태. Metrics는 시간에 따른 수치 — 추세. Health DOWN이면 HTTP 503을 내려 로드밸런서나 오케스트레이터가 트래픽을 빼거나 재시작 판단을 할 수 있습니다. 이 모듈은 PartnerSystemHealthIndicator로 외부 게이트웨이 상태를 반영합니다.

Counter와 Gauge는 언제 각각 쓰나요?

Counter는 “몇 번 일어났나” — 단조 증가(발송 성공 수). Gauge는 “지금 몇 개인가” — 오르내림(대기열 크기). Gauge는 값을 저장하지 않고 조회 시점에 함수(List::size)를 호출합니다. 일반 지식 Gauge는 대상 객체를 약한 참조로 잡아 GC되면 값이 사라질 수 있으므로 오래 사는 객체에 등록합니다.

Timer.record, Timer.Sample, @Timed의 차이는?
  • record: 람다로 감싼 특정 블록만 측정.
  • Sample: start와 stop을 분리 — 시작/끝 위치가 다르거나 결과에 따라 태그(result=success|fail|error)를 붙일 때. finally로 stop 보장.
  • @Timed: 메서드 전체를 AOP로 — 코드 침투가 가장 적지만 TimedAspect 빈이 필요하고 프록시를 거친 호출만 측정.
@Timed/@Counted가 동작하지 않는다면 무엇을 확인하나요?

① TimedAspect/CountedAspect 빈 등록(이 모듈은 MetricsAspectConfig) ② spring-boot-starter-aop 의존성 ③ 같은 클래스 내부 호출이 아닌지(프록시 기반이라 self-invocation은 측정 안 됨, 일반 지식) ④ 해당 API를 실제로 호출했는지(호출 전에는 metric 이름이 없음).

메트릭 태그를 설계할 때 주의할 점은?

태그 값 조합마다 시계열이 생기므로 값 종류가 적은 것만 씁니다(channel, region, result, status). userId·email·requestId·전체 URL은 카디널리티 폭발. 공통 식별은 common tags(application, environment, region, hostname)로 모든 meter에 한 번에 붙입니다.

평균 응답시간 대신 p95/p99를 보는 이유는?

평균은 소수의 매우 느린 요청을 가립니다. p99는 “100명 중 가장 느린 1명”의 경험 — 사용자 체감과 SLO는 꼬리 지연이 좌우합니다. 이 모듈은 키워드 길이로 120/450/900ms를 섞어 분위수 차이를 관찰합니다. 일반 지식 여러 인스턴스를 합치려면 클라이언트 percentile 대신 histogram 버킷을 발행해 서버에서 계산합니다.

Actuator를 별도 포트(9090)로 분리하는 이유는?

앱 트래픽(8080)과 운영 엔드포인트를 네트워크 수준에서 분리해, 관리 포트는 내부망·모니터링 시스템에만 열 수 있습니다. 노출도 exposure.include로 health·info·metrics·features만 화이트리스트.

/actuator/info에 git·빌드 정보는 어떻게 넣었나요?

Actuator는 classpath의 META-INF/build-info.properties와 git.properties를 읽습니다. 이 모듈은 build.gradle에 커스텀 태스크 generateBuildInfo, generateGitProperties를 만들어 processResources 전에 생성합니다. 추가로 InfoContributor(ReleaseInfoContributor)로 release 블록을 붙입니다. 일반 지식 보통은 Boot Gradle 플러그인의 springBoot { buildInfo() }와 git-properties 플러그인을 씁니다.

커스텀 Actuator 엔드포인트는 어떻게 만드나요?

@Endpoint(id = "features") 빈에 @ReadOperation(GET), @WriteOperation(POST), @DeleteOperation(DELETE)을 붙이고, 경로 변수는 @Selector, body 키는 메서드 파라미터로 매핑됩니다. exposure.include에 id를 추가해야 노출되며, 운영에선 인증/인가가 필수입니다.
