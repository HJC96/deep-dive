Java 샌드박스 — AES Provider 반복 등록을 JMH로 재고, 언어 기능을 테스트로 확인

메인 실험은 "AES 암호화할 때마다 Security.addProvider(new BouncyCastleProvider())를 부르면 얼마나 느린가"를 JMH로 측정하고, -prof gc/-prof stack으로 원인까지 확인한 것입니다. 결과에 반전이 있습니다: 빠른 쪽(1회 등록)이 8스레드에서 거의 확장되지 않았습니다. 그 밖에 제네릭·가변인자·컬렉션 팩토리·record·리플렉션·싱글턴·파사드를 작은 테스트로 정리해 두었습니다.

Java 21JMH 1.37me.champeau.jmh 0.7.2BouncyCastle bcprov-jdk18on 1.78.1JUnit 5 · AssertJ

01한눈에

30초 요약 (AES 실험)

문제

레거시 유틸이 encrypt()마다 new BouncyCastleProvider()를 만들어 등록을 시도. 알고리즘·키·IV·평문은 같고 Provider 반복 등록 시도 여부와 Provider를 찾는 방식(이름 "BC" / 객체)이 다릅니다.

접근

AesUtilBefore(매번 등록, static) vs AesUtilAfter(Provider 생성자 주입). JMH Throughput, 워밍업 3×1s, 측정 5×1s, fork 1, 1스레드·8스레드. 원인은 gc·stack 프로파일러로 확인.

결론

1스레드 약 1,526배 차이(README 18코어 실측). repeated는 op당 약 2.85MB 할당이 범인. 반전: once는 8스레드에서 ×1.4만 확장 — 공유 Provider의 getService가 캐시에 없는 이름을 찾을 때 들어가는 synchronized(this) 블록에서 줄을 섬(암달의 법칙).

한 줄 암기: "무거운 객체를 매 호출 만들지 말고 한 번 만들어 주입하라" + "병목은 느려 보이는 쪽이 아니라 직렬 구간 비중이 큰 쪽에서 터진다. 추측하지 말고 프로파일러로 확인하라."

02흐름

단계를 클릭하면 상세 설명이 나옵니다. encrypt() 한 번이 거치는 경로를 두 방식으로 비교합니다.

① Before — 매 호출 Provider 생성·등록 (repeated)

→ → →

비용의 본체. gc 프로파일상 repeated는 op당 2,848,583 B(약 2.85MB)를 할당, once(4,032 B)의 약 707배. README 설명: 생성자가 BC 지원 알고리즘 수백 개를 내부 맵에 등록하기 때문. 이 할당은 스레드마다 따로 일어나므로 병렬화가 잘 됩니다.

JVM 전역 java.security.Security의 Provider 목록에 등록을 시도. 같은 이름이 이미 있으면 추가되지 않고 -1을 반환합니다 — ProviderRegistrationTest로 확인. README도 "초점은 실제 추가 횟수가 아니라 매 호출 생성·등록을 시도하는 경로의 비용"이라고 적습니다.

이름 "BC"로 Provider를 찾습니다. 그래서 방금 만든 인스턴스가 아니라 이미 등록된 BC 인스턴스가 쓰입니다 — 테스트로 확인 ProviderRegistrationTest: cipher.getProvider()가 등록된 인스턴스와 isSameAs, 방금 만든 것과는 다름. 즉 repeated도 once와 같은 공유 인스턴스의 getService를 거칩니다.

cipher.init(ENCRYPT_MODE, SecretKeySpec, IvParameterSpec) → doFinal(plainText). 이 부분은 After와 동일. 변환: AES/CBC/PKCS7Padding.

② After — Provider 1회 준비 후 주입 (once), 8스레드일 때의 병목

→ → →

벤치마크의 @State(Scope.Benchmark) CryptoInput.setUp()이 Security.getProvider("BC")를 찾고 없으면 한 번 등록한 뒤 new AesUtilAfter(provider). 측정 루프 밖이라 이 비용은 집계되지 않습니다.

Provider 객체를 직접 넘기므로 이름 조회가 없습니다. 내부적으로 BC의 Provider.getService()가 불립니다.

stack 프로파일(8스레드 once): 51% BLOCKED, 그중 99.9%가 BouncyCastleProvider.getService. README 해석: getService는 이중 검사 락인데 null 결과를 캐시하지 않아, Cipher.getInstance가 조회하는 이름 변형 중 매칭 안 되는 키(예: AES/CBC)는 매번 synchronized(this)에 다시 들어갑니다. Provider가 하나뿐이라 8스레드가 같은 모니터에 줄을 섭니다.

암호화 본 연산은 Before와 동일. once는 일 자체가 적어서 위의 직렬 구간 비중이 커지고, 그래서 스레드를 늘려도 ×1.4밖에 안 늘어납니다.

03비교·핵심 구현

위: AES 실험의 핵심 코드. 아래: README에 설명이 없는 나머지 예제들.

Before — 매 호출 등록 약 559 ops/s (1T)

public static byte[] encrypt(byte[] plainText, byte[] key, byte[] iv) throws GeneralSecurityException {
    Security.addProvider(new BouncyCastleProvider());

    Cipher cipher = Cipher.getInstance(TRANSFORMATION, BouncyCastleProvider.PROVIDER_NAME);
    cipher.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(key, KEY_ALGORITHM), new IvParameterSpec(iv));
    return cipher.doFinal(plainText);
}
문제
매 호출 약 2.85MB 할당(gc 프로파일). static 유틸이 매 호출 Security.addProvider로 JVM 전역 Security 상태를 건드려 테스트 간 상태 제어도 어려움.

After — Provider 생성자 주입 약 853,343 ops/s (1T)

public final class AesUtilAfter {
    private final Provider provider;

    public AesUtilAfter(Provider provider) {
        this.provider = Objects.requireNonNull(provider);
    }

    public byte[] encrypt(byte[] plainText, byte[] key, byte[] iv) throws GeneralSecurityException {
        Cipher cipher = Cipher.getInstance(TRANSFORMATION, provider);
        cipher.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(key, KEY_ALGORITHM), new IvParameterSpec(iv));
        return cipher.doFinal(plainText);
    }
}
장점
등록(전역 상태)과 암호화 로직 분리. 단위 테스트에서 new AesUtilAfter(new BouncyCastleProvider())로 전역 등록 없이 생성 가능(README).
남은 특성
여러 스레드가 같은 Provider 객체를 공유하면 BC의 getService 동기화에서 경합. README는 "BC 내부 특성이라 관찰까지만"으로 정리.

코드와 테스트만 있는 학습 예제들. 테스트 이름이 곧 결론입니다.

제네릭 · 와일드카드 (PECS)

static int sum(List<? extends Number> values) { ... }          // 읽기(produce): Number로 꺼냄, add 불가
static void addDefaultScores(List<? super Integer> values) {   // 쓰기(consume): Integer 넣기 가능
    values.add(100);
    values.add(90);
}
static Object bodyOfAnyBox(Box<?> box) { ... }       // 아무 Box나 받음, 값은 Object
static Object bodyOfObjectBox(Box<Object> box) { ... }  // 정확히 Box<Object>만
  • raw type으로 List<String>에 Integer를 넣으면 꺼낼 때 ClassCastException.
  • ? extends는 읽기, ? super는 쓰기. super로 읽으면 Object까지만 보장.
  • <?> = 받기 자유·쓰기 불가, <Object> = 받기 빡빡·쓰기 자유(제네릭은 무공변). ResponseEntity<?> vs ResponseEntity<Object> 비유.

@SuppressWarnings({"unchecked", "varargs"})
static String firstAfterHeapPollution(List<String>... values) {
    Object[] array = values;
    array[0] = List.of(100);          // 배열을 통해 잘못된 타입이 섞임

static KeywordGroup unsafe(String... keywords) { return new KeywordGroup(keywords); }
static KeywordGroup safe(String... keywords)   { return new KeywordGroup(Arrays.copyOf(keywords, keywords.length)); }

05한계·약점

README가 스스로 밝힌 한계와, 코드·문서에서 확인되는 약점.

README 명시

  • 절대값은 머신·JVM·부하에 따라 다름. once 8스레드는 run마다 55만~122만으로 변동이 큼.
  • README 정정함 README는 "같은 fork 안에서 두 벤치마크가 순차 실행되므로 한쪽 등록분이 다른 쪽에 남음"이라 적었지만, JMH는 벤치마크마다 따로 fork합니다(실행 출력에 벤치마크별 # Fork: 1 of 1). 각 fork 안에서 BC는 한 번만 실제로 등록되고, repeated의 이후 addProvider는 매번 -1입니다.
  • once 경로의 getService 경합은 BC 내부 특성이라 "관찰까지만" — 해결책은 다루지 않음.

코드·문서 분석

repeated에서 새로 만든 Provider가 실제 암호화에 쓰이는가? — 쓰이지 않음, 확인함 수정함

확인 결과 (ProviderRegistrationTest): BC가 이미 있으면 Security.addProvider(new BouncyCastleProvider())는 -1을 돌려주고 목록을 바꾸지 않습니다. AesUtilBefore.encrypt를 여러 번 불러도 이름이 BC인 Provider는 처음 그 인스턴스 하나이고, Cipher.getInstance(T, "BC").getProvider()는 그 등록 인스턴스와 같은 객체입니다. 매번 만든 Provider는 할당 비용(op당 약 2.85MB)만 남기고 버려집니다.

해석에 주는 영향: repeated도 once와 같은 공유 인스턴스의 synchronized getService를 거칩니다. 그런데도 ×6.7로 확장되는 것은 경합 지점이 없어서가 아니라 할당 비용이 압도적이라 경합이 묻히기 때문입니다. README "매번 만든 Provider는 암호화에 쓰이지 않는다" 절과 해석 2)에 반영했습니다.

원래 분석: AesUtilBefore는 새 인스턴스를 addProvider한 뒤 이름 "BC"로 Cipher.getInstance합니다. 같은 이름이 이미 등록돼 있으면 addProvider는 추가하지 않으므로(일반 지식), 암호화에는 처음 등록된 인스턴스가 쓰이고 새 인스턴스는 버려질 가능성이 높습니다. 그렇다면 repeated도 공유 Provider의 getService를 거치는 셈인데, 이를 검증한 측정은 저장소에 없습니다. 면접에서는 "확인 필요"로 답하는 게 안전합니다.

Javadoc의 실행 경로가 틀림: :labs:java-sandbox:jmh 수정함

어떻게 고쳤나: javadoc을 ./gradlew :java-sandbox:jmh로 바꿨습니다.

AesProviderRegistrationSingleThreadBenchmark javadoc은 ./gradlew :labs:java-sandbox:jmh라고 적지만, settings.gradle은 프로젝트를 :java-sandbox로 등록합니다. README와 EightThreads javadoc의 :java-sandbox:jmh가 맞습니다.

오차 설명 불일치: javadoc "±95% 신뢰구간" vs README "99.9% 신뢰구간" 수정함

어떻게 고쳤나: javadoc을 "99.9% 신뢰구간의 절반(JMH 기본값)"으로 바꿨습니다. 실제 JMH 출력도 ±(99.9%), CI (99.9%)로 찍힙니다.

SingleThread javadoc은 Error를 "±95% 신뢰구간"이라 하고, README는 "99.9% 신뢰구간의 절반"이라 합니다. JMH 기본 출력은 99.9% 신뢰구간입니다 일반 지식.

EightThreads javadoc이 once 경로를 Cipher.getInstance(..., "BC")로 설명 수정함

어떻게 고쳤나: once 경로는 AesUtilAfter의 Cipher.getInstance(TRANSFORMATION, provider)(객체로 찾음)로, repeated 경로는 이름 "BC"로 찾은 등록 인스턴스를 쓴다고 나눠 적었습니다.

once 경로(AesUtilAfter)는 이름 "BC"가 아니라 Provider 객체로 getInstance합니다. 경합 지점(getService)에 대한 결론은 같지만 설명이 코드와 다릅니다.

통계적 근거가 얇다: fork 1, 측정 5회

fork 1 × 5 iteration은 JVM 간 편차를 보지 못합니다. README도 once 8스레드 값이 크게 흔들렸다고 적습니다. 결론의 "방향"(수백~천 배 차이, 확장 배수 역전)은 크지만, 정확한 배수를 인용할 때는 단서를 붙이세요.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

왜 System.nanoTime 루프 대신 JMH를 썼나요?
  • JIT 워밍업: 초반 인터프리터 구간이 평균을 왜곡 → @Warmup으로 제외.
  • 죽은 코드 제거: 결과를 안 쓰면 JIT가 호출을 지움 → Blackhole.consume.
  • 상수 폴딩·상태 오염: @State로 입력 분리, @Fork로 깨끗한 JVM.
  • 근거: SingleThread 벤치마크 javadoc "왜 직접 재지 않고 JMH를 쓰나".
repeated가 1,500배 가까이 느린 원인을 어떻게 확정했나요?
  • 추측(객체 생성 비용)을 -prof gc로 검증: gc.alloc.rate.norm repeated 2,848,583 B/op vs once 4,032 B/op.
  • 범인은 암호화 연산이 아니라 매 호출 new BouncyCastleProvider()(수백 개 알고리즘 매핑을 채우는 생성자).
  • 교훈: 무거운 객체는 한 번 만들어 재사용·주입.
빠른 once가 8스레드에서 ×1.4밖에 확장되지 않은 이유는?
  • -prof stack: 51% BLOCKED, 그중 99.9%가 BouncyCastleProvider.getService.
  • getService는 DCL 구조지만 null 결과를 캐시하지 않아, Cipher.getInstance가 조회하는 이름 변형 중 매칭 없는 키는 매번 synchronized에 들어감 → 공유 Provider 하나에 8스레드가 줄 섬 (README 분석).
  • 암달의 법칙: 일이 적은 쪽은 직렬 구간 비중이 커서 확장이 막힘. repeated는 스레드 로컬 할당이 지배라 ×6.7. repeated도 같은 등록 BC 인스턴스의 getService를 거치지만(ProviderRegistrationTest) 할당 비용에 묻힘.
  • 프로파일 전 가설("JCE 내부 검증")이 틀렸다는 점도 README에 기록 — 측정의 가치.
운영에서 once의 경합까지 줄이려면 어떤 선택지가 있나요?
  • README는 "관찰까지만"이라 저장소에 검증된 해법은 없음. 아래는 아이디어 수준(검증 필요).
  • 스레드별 Cipher 재사용(ThreadLocal) → getInstance 호출 자체를 줄임. Cipher는 스레드 안전하지 않으므로 공유 금지 일반 지식.
  • JDK 기본 Provider로 충분한 변환이면 BC 대신 사용(예: AES/CBC/PKCS5Padding) — 패딩 호환성 확인 필요.
  • 무엇이든 바꾼 뒤 같은 JMH·프로파일로 재측정.
static 유틸 대신 생성자 주입으로 바꾼 설계상 이점은?
  • 전역 상태(Security 등록)와 비즈니스 로직(암호화) 분리 → 등록은 애플리케이션 초기화에서 1회.
  • 테스트 용이성: new AesUtilAfter(new BouncyCastleProvider())로 전역 상태를 건드리지 않고 생성.
  • 스프링이라면 Provider나 AesUtilAfter를 빈으로 등록해 주입하는 형태와 자연스럽게 연결.
JMH 결과의 Score, Error, Cnt는 어떻게 읽나요?
  • Mode thrpt = 처리량, Units ops/s는 클수록 빠름. @Threads(8)의 값은 8스레드 합계.
  • Cnt = 집계된 측정 반복 수(5), 워밍업 제외.
  • Error = 신뢰구간 절반. JMH 기본은 99.9%(출력의 ±(99.9%)). javadoc의 95% 표기는 99.9%로 고쳤습니다.
(기타 예제) List<? extends T>와 List<? super T>는 언제 쓰나요?
  • PECS: Producer Extends, Consumer Super. 꺼내 읽으면 extends(sum), 넣으면 super(addDefaultScores).
  • <?>는 아무 타입이나 받지만 넣을 수 없고, <Object>는 정확히 Object 컨테이너만 받음 — 제네릭은 무공변.
(기타 예제) List.of, Collections.unmodifiableList, List.copyOf의 차이는?
  • 셋 다 구조 변경 불가. unmodifiableList는 원본의 view라 원본 변경이 보이고, copyOf/of는 별도 리스트.
  • List.of는 null 불가, 요소 객체를 deep copy하지 않음. record compact constructor에서 List.copyOf로 방어적 복사하는 이유.
(기타 예제) LazyHolder 싱글턴이 synchronized 없이 스레드 안전한 이유는?
  • 중첩 클래스 Holder는 getInstance() 첫 호출 시 초기화되고, 클래스 초기화는 JVM이 한 번만, 스레드 안전하게 수행 일반 지식: JLS 클래스 초기화.
  • 테스트: 100번 동시 호출해도 인스턴스 1개.
