앞의 트랙을 모두 합친 종합 실험

labs/payment-system

payment-system: 한 트랜잭션으로 묶을 수 없는 결제를 상태·아웃박스·멱등성으로 맞추기

README의 "알려진 문제" 전부와 코드 분석에서 나온 결함을 세 서비스에 걸쳐 고쳤습니다. 테스트를 Testcontainers로 바꾸는 과정에서 결제 서비스가 Kafka에 이벤트를 아예 발행하지 않던 더 큰 버그도 드러나 함께 고쳤습니다.

문제수정검증
Kafka 바인딩이 아예 만들어지지 않음: spring.cloud.stream.function.definition은 Spring Cloud Stream 4.x가 읽지 않는 키라, 결제 이벤트 발행·완료 이벤트 소비가 모두 동작하지 않았음spring.cloud.function.definition으로 수정Kafka 경유 통합 테스트
복구·아웃박스 릴레이 스케줄러가 돌지 않음(@EnableScheduling 없음 + @Profile("dev"))PaymentScheduler가 3분마다 실행, payment.scheduler.enabled로 끔. 회차가 겹치지 않음스케줄러 단위 테스트
Toss ALREADY_PROCESSED_PAYMENT를 성공으로 분류하면서 상세 정보가 없어 IllegalArgumentException결제 조회 API로 orderId·금액·DONE을 확인해 정상 성공으로, 아니면 UNKNOWN으로 남겨 복구PSP 응답 매핑 단위 테스트
결제 수단이 간편결제 하나라 카드 결제는 승인 후 예외Toss 수단 8개·타입 3개 추가, 모르는 값은 UNKNOWN + 경고 로그, 컬럼 길이 확장결제수단 단위 테스트
복구 조회 LIMIT 10이 주문 행 단위라 한 결제가 잘려 금액 검증 실패 → FAILURE결제 단위로 10건을 고른 뒤 그 결제의 주문을 모두 붙임복구 테스트
결제 완료 집계 경쟁 조건(is_payment_done이 영원히 false 가능)한 트랜잭션에서 자기 플래그 + "모든 주문이 끝났을 때만" 조건부 UPDATE동시 완료 테스트
최종 상태를 이전 상태 확인 없이 덮어씀, 같은 결제의 동시 confirm이 둘 다 통과SELECT … FOR UPDATE + 조건부 UPDATE. 처리 중이면 PSP를 부르지 않고 EXECUTING 응답동시 confirm 테스트
없는 orderId면 NPE가 UNKNOWN으로 기록됨PAYMENT_NOT_FOUND 실패, DB에 쓰지 않음단위 테스트
지갑·장부가 아무도 채우지 않는 자기 DB의 payment_orders를 읽음주문 라인을 이벤트 payload에 실어 보냄(Event-Carried State Transfer), 로컬 테이블 삭제지갑·장부 통합 테스트
지갑·장부 멱등성이 조회 후 저장, unique 제약 없음idempotency_key UNIQUE, 중복은 "이미 처리됨" 성공. INSERT 정렬과 교착 재시도동시 중복 메시지 테스트
지갑이 없는 판매자는 조용히 건너뜀WalletNotFoundException으로 실패 → 재시도 후 DLQDLQ 테스트
복식부기 검사가 같은 값끼리 비교하는 동어반복거래별 차변 합 = 대변 합, 대변 합 = 결제 총액, 방향·양수·계정 검사복식부기 단위 테스트
낙관적 락 재시도 대기가 0~100ms 랜덤지수 백오프(50ms → 상한 1초) + jitter백오프 단위 테스트
애플리케이션 계층이 어댑터 예외에 의존, domain에 Spring 컴포넌트예외를 application/exception으로, 발행기를 adapter/out/stream으로 이동컴파일
schema.sql이 자동 적용되지 않아 장부 트리거가 걸리지 않음세 서비스 spring.sql.init.mode: always, Hibernate validate통합 테스트
테스트가 모두 로컬 인프라 전제라 CI에서 제외, 일부는 sleep만 하고 단언 없음Testcontainers 기반으로 전환(Toss 실서버 테스트만 제외), Awaitility로 결과 단언117개 테스트
이력 INSERT가 문자열 연결이라 '가 든 Toss 메시지에서 실패바인딩 파라미터 사용테스트
아웃박스 발행 sink가 FAIL_FAST라 동시 발행 시 이벤트 유실 가능busyLooping으로 변경테스트
가정 Toss 결제 조회(GET /v1/payments/{paymentKey}) 응답이 승인 응답과 같은 Payment 객체라는 점은 Toss 문서에 기댄 가정이고, 실제 Toss 서버로는 확인하지 않았습니다. 호환성 이벤트 payload가 바뀌어(payloadVersion 2) Payment를 먼저 배포해야 하고, 옛 형식 메시지는 DLQ로 갑니다.
