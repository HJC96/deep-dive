낙관적 락(@Version)과 요청당 SQL 수 모니터링

두 사람이 같은 재고를 읽고 각자 수정하면 한쪽 수정이 사라집니다(lost update). 이 모듈은 @Version으로 “나중에 저장한 쪽을 거부”하는 동작을 스레드 없이 결정적으로 재현하고, 별도로 Hibernate StatementInspector로 HTTP 요청 하나가 SQL을 몇 개 날리는지 세어 Micrometer 메트릭으로 내보냅니다.

Java 21Spring Boot 3.4.1Spring Data JPA · HibernateMySQL 8.0.36 (Testcontainers)Micrometer · Prometheus

01한눈에

30초 요약

문제

A가 재고 10을 읽어 둔 사이 B가 9로 바꿔 커밋. A가 옛 값 기준으로 9를 저장하면 B의 수정이 덮여 사라집니다. 또, N+1처럼 “요청 하나에 쿼리가 폭발”해도 지표가 없으면 모릅니다.

접근

Product에 @Version Long version. @Transactional 서비스 메서드로 트랜잭션 경계를 끊어 “옛 스냅샷”과 “먼저 커밋한 수정”을 순서대로 만들어 충돌 재현. 쿼리 수는 인터셉터 + ThreadLocal + StatementInspector.

결론

먼저 커밋한 쪽이 이기고 나중 쪽은 ObjectOptimisticLockingFailureException (stock 9, version 1). 재시도는 호출자 몫. 쿼리 메트릭은 URI 패턴으로 태깅하고 ThreadLocal은 finally에서 clear.

02흐름

단계를 클릭하면 상세 설명이 나옵니다.

낙관적 락 충돌 (케이스 3)

→ → →

productService.getById(id) — @Transactional(readOnly = true) 메서드가 끝나면 영속성 컨텍스트가 닫혀 A가 받은 Product(stock 10, version 0)는 detached(준영속) 스냅샷이 됩니다.

productService.decreaseStock(id) — 새 트랜잭션에서 조회 → product.decreaseStock() → 커밋 시 dirty checking으로 UPDATE. DB는 stock 9, version 1.

productService.decreaseStockAndSave(staleA) — A의 스냅샷(version 0)에서 재고를 줄이고 saveAndFlush(내부적으로 merge). DB의 version은 이미 1.

버전 불일치 → ObjectOptimisticLockingFailureException. 최종 DB: stock 9, version 1. A까지 반영됐다면 8이었을 것 — 9라는 것은 A가 거부됐다는 증거입니다. SQL 로그와 테스트의 SQL 카운트로 확인한 실제 경로: merge가 SELECT로 현재 행(version 1)을 읽고 스냅샷 version 0과 비교해 UPDATE 없이 예외를 던집니다(SELECT 1, UPDATE 0).

요청당 쿼리 카운트

→ → →

QueryCountInterceptor.preHandle가 HTTP 메서드와 URI 패턴(HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE, 예: /products/{id}/decrease)으로 RequestContext를 만들어 QueryCountContextHolder(ThreadLocal)에 넣습니다.

Hibernate가 SQL을 JDBC로 넘기기 직전마다 QueryCountStatementInspector.inspect(sql)가 불립니다. 같은 스레드의 컨텍스트를 꺼내 QueryType.from(sql)(첫 키워드: SELECT/INSERT/UPDATE/DELETE/OTHER)별로 카운트만 올리고 SQL은 그대로 반환. 인스펙터는 모든 스레드가 공유하므로 상태를 두지 않습니다.

jpa.queries.per_request(DistributionSummary, baseUnit queries, p50/p95, 태그 method·uri)에 총 개수를, jpa.queries.by_type(Counter, 태그 method·uri·type)에 종류별 개수를 기록합니다.

Tomcat은 스레드를 재사용하므로 지우지 않으면 다음 요청이 이전 컨텍스트를 물려받습니다. 성공·예외와 무관하게 finally에서 QueryCountContextHolder.clear()(ThreadLocal.remove()).

케이스 1. 버전 자동 증가 통과

케이스 2. 최신 스냅샷 저장 — 예외 없음 대조군

케이스 3과 똑같이 detached 스냅샷을 saveAndFlush하지만, 그 사이 아무도 안 건드렸습니다.

Product fresh = productService.getById(id);   // version 0, detached
productService.decreaseStockAndSave(fresh);   // DB version도 0 → 일치 → 성공

Product current = productRepository.findById(id).orElseThrow();
assertThat(current.stock()).isEqualTo(9);
assertThat(current.version()).isEqualTo(1L);
왜 필요
이 대조군이 있어야 케이스 3의 예외가 “낙관적 락 때문”이지 saveAndFlush나 detached 저장 자체 탓이 아님이 증명됩니다.

케이스 3. 옛 스냅샷 저장 → 충돌 예외

Product staleA = productService.getById(id);     // A의 스냅샷 (version 0)
productService.decreaseStock(id);                // B가 먼저 커밋 → DB version 0 → 1

RequestContext sql = startSqlCapture();       // 이 구간의 SQL을 종류별로 센다
assertThatThrownBy(() -> productService.decreaseStockAndSave(staleA))
        .isInstanceOf(ObjectOptimisticLockingFailureException.class);
assertThat(sql.countOf(QueryType.SELECT)).isEqualTo(1);  // merge의 SELECT
assertThat(sql.countOf(QueryType.UPDATE)).isZero();      // UPDATE는 실행되지 않음

Product current = productRepository.findById(id).orElseThrow();
assertThat(current.stock()).isEqualTo(9);        // A까지 반영됐다면 8
assertThat(current.version()).isEqualTo(1L);
// ProductService
@Transactional
public void decreaseStockAndSave(Product product) {
    product.decreaseStock();
    productRepository.saveAndFlush(product);
}
어디서 걸리나
detached 엔티티의 saveAndFlush는 merge → SELECT로 DB version(1)을 읽고 스냅샷 version(0)과 메모리에서 비교 → StaleObjectStateException → Spring이 ObjectOptimisticLockingFailureException으로 변환. UPDATE ... WHERE version = ?가 0행이라서 나는 예외는 영속 엔티티를 고친 뒤 flush할 때의 경로입니다.
왜 스레드 없이
실제 동시 실행은 타이밍에 따라 결과가 달라집니다. 트랜잭션 경계를 메서드 단위로 끊어 순서를 고정하면 매번 같은 충돌이 납니다(결정적 재현).
트레이드오프
충돌을 사후에 감지 → 충돌하면 요청 실패, 재시도는 호출자 몫. 선착순처럼 충돌이 잦으면 재시도 폭주 → 비관적 락·원자적 UPDATE가 유리(README, coupon-issue 실험 참고).

쿼리 카운트 — 세 조각 등록 monitoring/

// QueryMonitoringConfig
@Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(new QueryCountInterceptor(meterRegistry));
}

@Bean
HibernatePropertiesCustomizer queryCountStatementInspectorCustomizer() {
    QueryCountStatementInspector inspector = new QueryCountStatementInspector();
    return properties -> properties.put(AvailableSettings.STATEMENT_INSPECTOR, inspector);
}

// QueryCountStatementInspector
public String inspect(String sql) {
    RequestContext context = QueryCountContextHolder.get();
    if (context != null) {
        context.increment(QueryType.from(sql));
    }
    return sql;
}
왜 ThreadLocal
StatementInspector는 Spring 빈이 아니라 SQL 실행 콜 스택 한가운데서 불립니다. “지금 어떤 API를 처리 중인지”를 인자로 받을 길이 없어 같은 스레드에 미리 심어 둔 값을 꺼냅니다.
분업
인스펙터는 카운트만 올리고, MeterRegistry 기록은 인터셉터가 요청 끝에 한 번.

메트릭 이름·태그 설계 카디널리티

DistributionSummary.builder("jpa.queries.per_request")
        .baseUnit("queries")
        .tag("method", context.httpMethod())
        .tag("uri", context.uriPattern())
        .publishPercentiles(0.5, 0.95)
        .register(meterRegistry)

05한계·약점

README가 스스로 밝힌 한계와, 코드에서 확인되는 약점.

README 충돌하면 요청이 실패 — 재시도는 호출자 몫

낙관적 락은 사후 감지입니다. 충돌이 잦은 상황(선착순 등)에서는 재시도 폭주 → 비관적 락·원자적 UPDATE가 유리하다고 README가 밝힙니다. 이 모듈에는 재시도 로직이 없습니다.

README 다른 스레드·요청 밖 SQL은 세지 않음

비동기로 다른 스레드에 넘긴 작업은 ThreadLocal 컨텍스트가 없어 카운트되지 않고(의도된 한계), 부팅 시 스키마 생성·배치 스레드 SQL은 조용히 건너뜁니다.

코드 쿼리 모니터링에 테스트가 없음 일부 수정함

추가한 것: QueryCountInterceptorTest(컨텍스트 없는 단위 테스트)가 패턴 태깅, UNKNOWN 폴백, ThreadLocal 정리를 확인합니다. OptimisticLockTest도 StatementInspector로 SQL 수를 셉니다. HTTP 엔드투엔드(“POST /products/{id}/decrease 요청당 3개”)는 여전히 README의 수동 curl 예시입니다.

원래 테스트는 OptimisticLockTest 하나뿐이었습니다. “요청당 3개”, p50/p95 3.0 등은 README의 수동 curl 예시이며 자동 검증되지 않습니다.

코드 실제 동시성·dirty checking 경로 충돌은 미검증

충돌은 detached 엔티티의 saveAndFlush(merge) 경로로만 재현합니다. 두 트랜잭션이 실제로 겹쳐 각자 decreaseStock(dirty checking)으로 커밋하는 상황은 테스트하지 않습니다.

README 케이스 3의 “affected rows = 0” 설명은 틀림 — 확인함 수정함

확인 결과: SQL 로그상 decreaseStockAndSave(staleA) 구간에는 merge의 select ... where id=? 하나만 있고 update는 없습니다. merge가 읽어 온 version(1)과 스냅샷 version(0)이 달라 UPDATE 전에 예외가 납니다. 대조군(케이스 2)은 select 뒤 update ... where id=? and version=?(version 0)이 1행을 바꿉니다.

어떻게 고쳤나: README 케이스 2·3의 설명과 시퀀스 다이어그램을 merge의 SELECT → 버전 비교 흐름으로 고치고, 두 경로(detached merge vs 영속 엔티티 UPDATE 0행) 비교표를 넣었습니다. OptimisticLockTest가 구간별 SELECT/UPDATE 수(케이스 2: 1/1, 케이스 3: 1/0)를 단언합니다.

원래 README는 케이스 3을 “UPDATE ... WHERE version = 0 → affected rows 0 → 예외”로 그립니다. 일반 지식 Hibernate의 merge는 detached 엔티티를 먼저 SELECT로 로드한 뒤 버전이 다르면 UPDATE 전에 예외를 던질 수 있습니다. 테스트는 예외 타입과 최종 상태만 확인하므로 실제로 어느 경로인지는 SQL 로그(org.hibernate.SQL: debug)로 확인해야 합니다.

코드 패턴이 없으면 원시 URI로 폴백 수정함

어떻게 고쳤나: 패턴이 없으면 고정값 UNKNOWN(Spring Boot http.server.requests와 같은 규칙)으로 태깅합니다. QueryCountInterceptorTest가 서로 다른 두 경로가 하나의 uri=UNKNOWN 시계열로 묶이는 것을 확인합니다.

원래 resolveUriPattern은 best-matching 패턴이 없으면 request.getRequestURI()를 태그로 씁니다. 존재하지 않는 경로를 대량으로 찌르면 태그 값이 늘어날 수 있습니다(카디널리티 위험). 또한 use_sql_comments를 켜면 SQL 앞 주석 때문에 QueryType이 OTHER로 분류됩니다(코드 주석이 밝힌 전제).

일반 지식 클라이언트 측 percentile은 인스턴스 간 합산 불가

publishPercentiles(0.5, 0.95)는 각 인스턴스 안에서 계산된 값이라 여러 서버의 p95를 평균 내도 전체 p95가 아닙니다. 전체 분포가 필요하면 histogram 버킷을 발행해 서버(Prometheus) 측에서 계산합니다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

Lost update란 무엇이고 @Version은 어떻게 막나요?

두 트랜잭션이 같은 값을 읽고 각자 수정해 나중 저장이 앞 저장을 덮는 현상입니다. @Version이 있으면 UPDATE에 “내가 읽은 버전일 때만” 조건이 붙고 성공 시 버전을 올립니다. 그 사이 다른 커밋이 버전을 올렸다면 조건이 맞지 않아 예외 → 먼저 커밋한 쪽이 이깁니다. 테스트: 최종 stock 9, version 1. 단, 이 실험처럼 detached 스냅샷을 save하면 merge가 먼저 SELECT로 읽은 version과 비교해 UPDATE 전에 예외를 던집니다.

낙관적 락과 비관적 락은 언제 각각 쓰나요?
  • 낙관적: 충돌이 드문 경우. 락 대기 없이 진행하고 충돌 시 예외 + 재시도.
  • 비관적(SELECT ... FOR UPDATE, 일반 지식): 충돌이 잦은 경우(선착순·재고 차감). 대기는 생기지만 재시도 폭주가 없음.
  • 원자적 UPDATE(SET stock = stock - 1 WHERE stock > 0): 단순 카운터면 가장 가벼움. README가 coupon-issue 실험을 참고하라고 안내.
낙관적 락 예외가 나면 어떻게 처리하나요?

Spring은 JPA/Hibernate 예외를 ObjectOptimisticLockingFailureException으로 변환합니다. 일반 지식 보통 최신 데이터를 다시 읽어 재시도(횟수 제한 + 백오프)하거나, 사용자에게 “다른 사람이 먼저 수정했습니다”를 알립니다. 재시도는 반드시 새 트랜잭션에서 다시 읽어야 의미가 있습니다.

동시성 버그를 테스트할 때 왜 스레드 대신 트랜잭션 경계로 재현했나요?

스레드 경합은 타이밍에 따라 결과가 달라 flaky합니다. @Transactional 서비스 메서드 하나가 트랜잭션 하나라는 점을 이용해 “옛 스냅샷 읽기 → 다른 커밋 → 옛 스냅샷 저장” 순서를 고정하면 매번 같은 충돌이 납니다. 그리고 대조군(충돌 없음)으로 원인을 분리합니다.

detached 엔티티란? 왜 이 실험에서 중요한가요?

영속성 컨텍스트가 닫혀 더 이상 변경 감지 대상이 아닌 엔티티입니다. getById의 트랜잭션이 끝나면 반환 객체는 detached가 되어 “옛 스냅샷”을 들고 있게 됩니다. 이를 다시 저장하려면 save/saveAndFlush(merge)가 필요하고, 그때 버전 비교가 일어납니다.

HTTP 요청당 SQL 수는 어떻게 셌나요?

인터셉터가 요청 시작에 ThreadLocal로 카운터를 심고, Hibernate StatementInspector가 SQL 실행 직전마다 같은 스레드의 카운터를 올리고, 요청 끝(afterCompletion)에 Micrometer에 기록한 뒤 finally로 ThreadLocal을 지웁니다. 인스펙터는 HibernatePropertiesCustomizer로 STATEMENT_INSPECTOR에 인스턴스로 등록합니다.

ThreadLocal을 clear하지 않으면 어떤 일이 생기나요?

Tomcat 워커 스레드는 풀에서 재사용되므로 다음 요청이 이전 요청의 컨텍스트를 물려받아 카운트가 섞이고, 객체가 계속 참조되어 메모리 누수가 됩니다. 그래서 예외가 나도 실행되는 finally에서 remove()합니다.

메트릭 태그에 URL을 그대로 넣으면 왜 안 되나요?

태그 값 조합마다 별도 시계열이 생깁니다. /products/1, /products/2…가 각각 시계열이 되면 저장·조회 비용이 폭발합니다(카디널리티 폭발). 그래서 BEST_MATCHING_PATTERN_ATTRIBUTE의 /products/{id}를 씁니다.

요청당 쿼리 수에 왜 Timer가 아닌 DistributionSummary를 썼나요?

기록 값이 시간이 아니라 “개수”이기 때문입니다. DistributionSummary는 임의 값의 분포(count/sum/max/percentile)를 기록합니다. baseUnit("queries")라 Prometheus 이름도 jpa_queries_per_request_queries이고, p95 3.0은 3초가 아니라 3개입니다. 이 지표로 N+1(특정 URI의 쿼리 수 급증)을 감지할 수 있습니다.
