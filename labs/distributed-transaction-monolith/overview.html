Monolith — 하나의 DB, 하나의 @Transactional

분산 트랜잭션 시리즈의 기준선. 워크숍 좌석 예약·크레딧 차감·원장 기록·예약 확정을 하나의 애플리케이션, 하나의 데이터베이스, 하나의 로컬 트랜잭션으로 처리한다. 잔액이 모자라면 좌석까지 함께 롤백된다는 것을 확인하고, 이 보장이 DB를 나누는 순간 사라진다는 것을 다음 단계로 넘긴다.

01한눈에

30초 요약 — 왜 이 모듈이 필요한가

시리즈에서의 위치 — 4단계가 같은 실패 시나리오를 다룹니다
STEP 1 · 기준선 · 지금 여기MonolithDB 1개 · @Transactional 1개 → STEP 2 · 문제MSA서비스 3개 · 부분 커밋 → STEP 3 · 해법 A2PC (XA)prepare 후 결정 · 락 대기 → STEP 4 · 해법 BTCCTry 커밋 · Cancel 보상
문제

좌석 예약·크레딧 차감·원장 기록·예약 확정 중 일부만 반영되면 "좌석은 잡혔는데 결제가 안 된" 상태가 생긴다.

접근

네 변경을 ReservationTransaction.place() 하나의 @Transactional로 묶고, 예약 행을 SELECT … FOR UPDATE로 잠가 재실행·동시 실행을 한 번만 처리한다.

결론

DB가 하나면 원자성은 DB가 공짜로 준다. 잔액 부족이면 좌석까지 롤백되어 reserved_count 0. 이 "공짜"가 DB를 쪼개는 순간 사라진다는 것이 다음 단계(MSA)의 출발점.

공통 실패 시나리오 정원 10석 워크숍에서 좌석 2석 × 30,000 = 60,000 크레딧이 필요한데 지갑 잔액은 50,000. 좌석은 잡히지만 지갑이 실패한다. 이미 잡힌 좌석이 되돌아가는가? 네 모듈이 모두 이 질문에 답한다.

02흐름

단계를 클릭하면 상세 설명이 나옵니다. 아래는 실패 시 시퀀스.

→ → → →

POST /reservations → ReservationService.create()가 Reservation을 CREATED로 INSERT하고 reservationId를 발급한다. 좌석과 크레딧은 건드리지 않는다(테스트 createOnlyStoresReservation).

클라이언트가 멱등 키를 만드는 대신 서버가 ID를 발급하고, 이 ID가 조회·재실행 판단·원장 키에 모두 쓰인다.

POST /reservations/{id}/place → ReservationTransaction.place()에서 트랜잭션 시작. findByIdForUpdate(PESSIMISTIC_WRITE)로 예약 행을 잠근다.

이미 CONFIRMED면 아무것도 하지 않고 기존 결과를 반환 → 재실행·동시 실행이 한 번만 처리된다.

SeatService.reserve() → WorkshopSeat.reserve(): reservedCount + seatCount > capacity면 NotEnoughSeatsException, 아니면 reservedCount를 올리고 금액(pricePerSeat × seatCount = 60,000)을 반환한다.

WalletService.debit() → Wallet.debit(): 잔액이 모자라면 NotEnoughCreditException. 성공하면 WalletLedger를 ledgerKey = "reservation:{id}:debit"로 INSERT (unique = true).

마지막으로 reservation.confirm(amount) → CONFIRMED. 메서드가 끝나면 네 변경이 한 번에 커밋된다 (reservedCount 2, balance 100,000→40,000, 원장 1건).

잔액 50,000 < 60,000 → NotEnoughCreditException(RuntimeException) → 트랜잭션 전체 롤백. STEP 3에서 올린 reservedCount도 되돌아간다.

예약 생성은 별도 트랜잭션으로 이미 커밋됐으므로 Reservation은 CREATED로 남고, 충전 후 같은 ID로 다시 실행할 수 있다. HTTP는 409 RESERVATION_UNAVAILABLE.

03비교·핵심 구현

탭을 눌러 핵심 구현을 봅니다. 코드는 실제 파일에서 발췌.

하나의 @Transactional 핵심

좌석·지갑·원장·예약 확정을 한 메서드, 한 트랜잭션 안에서 실행한다. 중간에 RuntimeException이 나면 전부 롤백된다.

@Transactional
public ReservationResult place(long reservationId) {
    Reservation reservation = repository.findByIdForUpdate(reservationId)
            .orElseThrow(() -> new ReservationNotFoundException(reservationId));
    if (reservation.getStatus() == ReservationStatus.CONFIRMED) {
        return ReservationResult.from(reservation);
    }

    long amount = seatService.reserve(reservation.getWorkshopId(), reservation.getSeatCount());
    String ledgerKey = "reservation:" + reservationId + ":debit";
    walletService.debit(reservation.getUserId(), amount, ledgerKey);
    reservation.confirm(amount);
    return ReservationResult.from(reservation);
}
어떻게
SeatService·WalletService에는 @Transactional이 없다. 바깥 트랜잭션에 그대로 참여하고, 같은 커넥션·같은 DB에서 실행된다.
결과
성공: reservedCount 2, balance 40,000, 원장 1건, CONFIRMED. 잔액 부족: 좌석까지 0으로 롤백, 예약 CREATED.
트레이드오프
가장 단순하고 강한 보장. 대신 네 데이터가 같은 DB에 있어야만 성립한다.

재실행·동시 실행 = 예약 행 비관적 락 멱등

같은 reservationId로 두 번(또는 20건 동시에) 실행돼도 좌석·크레딧은 한 번만 처리돼야 한다.

public interface ReservationRepository extends JpaRepository<Reservation, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select reservation from Reservation reservation where reservation.id = :reservationId")
    Optional<Reservation> findByIdForUpdate(@Param("reservationId") long reservationId);
}
어떻게
첫 요청이 행 락을 쥐고 처리·커밋할 때까지 나머지는 대기. 락이 풀리면 CONFIRMED를 읽고 기존 결과를 돌려준다.
결과

05한계·약점

README = README가 스스로 밝힌 것, 코드 = 코드에서 확인한 것.

README DB를 나누면 이 로컬 트랜잭션을 그대로 쓸 수 없다

README "다음 문제": 예약·좌석·지갑을 reservation_db/seat_db/wallet_db로 분리하면, 좌석 커밋 뒤 크레딧 차감이 실패해도 Reservation Service의 롤백으로 seat_db를 되돌릴 수 없다. → MSA 단계에서 재현.

코드 좌석·지갑 행은 락 없이 읽는다 — 다른 예약끼리의 동시 실행은 미검증

SeatService.reserve()와 WalletService.debit()은 일반 findById를 쓰고, WorkshopSeat·Wallet에 @Version도 없다. 락은 예약 행에만 걸린다.

그래서 동시성 테스트(20건)는 같은 reservationId만 다룬다. 서로 다른 예약 두 건이 같은 워크숍(또는 같은 지갑)을 동시에 실행하면 둘 다 같은 reservedCount/balance를 읽고 덮어써 갱신 유실이 날 수 있다 추론 · 테스트 없음.

보완 예: 좌석·지갑 행도 PESSIMISTIC_WRITE, @Version 낙관적 락 + 재시도, 또는 UPDATE … SET reserved_count = reserved_count + ? WHERE reserved_count + ? <= capacity 같은 조건부 UPDATE.

코드 테스트는 H2(MODE=MySQL), 운영 설정은 MySQL

application.yml은 MySQL을 가리키지만 테스트는 jdbc:h2:mem:monolith;MODE=MySQL로 돈다. SELECT … FOR UPDATE의 대기·데드락·격리 수준 동작은 실제 MySQL(InnoDB)과 다를 수 있고, 이 모듈에는 MySQL 통합 테스트가 없다.

코드 실패 상태가 모델에 없다

ReservationStatus는 CREATED, CONFIRMED 둘뿐이다. 잔액 부족으로 실패해도 예약은 CREATED로 남고 실패 사유·시도 횟수가 기록되지 않는다. 단일 DB에서는 롤백으로 충분하지만, 분산 단계에서는 "어디까지 갔는지"를 남길 상태가 필요해진다(README MSA "상태 모델 없음").

코드 ddl-auto: update

src/main/resources/application.yml이 spring.jpa.hibernate.ddl-auto: update다. 학습용으로는 편하지만 운영에서는 Flyway/Liquibase 같은 마이그레이션 도구가 일반적이다 일반 지식.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

예약 "생성"과 "실행"을 왜 두 API로 나눴나요? 이게 2PC인가요?

서버가 먼저 reservationId를 발급하면 그 ID 하나로 실행 대상 잠금·재실행 판단·원장 키를 모두 해결할 수 있다. 클라이언트가 임의 멱등 키를 만들 필요가 없다.

2PC는 아니다. 생성과 실행은 각각 독립된 로컬 트랜잭션이고, 실행 트랜잭션이 쓰는 DB는 하나다(README).

잔액 50,000으로 60,000을 결제하면 무엇이 남나요?

NotEnoughCreditException으로 실행 트랜잭션 전체가 롤백된다. 이미 올린 reservedCount도 0으로 돌아가고, 지갑·원장은 변경 없음. 예약은 생성 트랜잭션이 이미 커밋했으므로 CREATED로 남는다(테스트로 검증). HTTP는 409.

같은 예약을 20번 동시에 실행하면 어떻게 한 번만 처리되나요?

예약 행을 PESSIMISTIC_WRITE(SELECT … FOR UPDATE)로 조회한다. 첫 요청이 락을 쥐고 처리·커밋하는 동안 나머지는 대기하고, 락이 풀리면 CONFIRMED를 보고 기존 결과를 반환한다. concurrentPlaceRequestsProcessReservationOnce가 20 스레드로 검증한다.

비관적 락 대신 낙관적 락(@Version)을 쓰면요?

일반 지식 낙관적 락은 충돌 시 예외 → 재시도가 필요하다. 같은 예약에 대한 중복 실행처럼 충돌이 확실히 예상되는 경우엔 대기 후 결과를 돌려주는 비관적 락이 단순하다. 충돌이 드물고 대기를 피하고 싶으면 낙관적 락이 낫다.

그럼 서로 다른 예약 두 건이 같은 워크숍 좌석을 동시에 잡으면 안전한가요?

이 모듈은 보장하지 않는다. 락은 예약 행에만 걸리고 WorkshopSeat·Wallet은 락·@Version 없이 읽고 덮어쓴다. 갱신 유실 가능성이 있고 테스트도 없다. 보완: 좌석 행 비관적 락, @Version, 또는 조건부 UPDATE로 검사와 변경을 한 문장에 묶기.

예약 행 락이 있는데 원장 ledgerKey에 unique 제약까지 둔 이유는?

락은 애플리케이션 코드 경로가 지켜야 성립한다. ledgerKey unique는 다른 경로·버그로 같은 예약이 두 번 차감되려 할 때 DB가 막는 마지막 방어선이다 추론. README는 "원장 키를 만드는 ID"로서의 역할을 설명한다.

NotEnoughCreditException이 checked 예외였다면?

일반 지식 Spring @Transactional은 기본적으로 RuntimeException·Error에서만 롤백한다. checked 예외면 rollbackFor를 지정하지 않는 한 커밋될 수 있다. 이 모듈의 예외는 모두 RuntimeException을 상속한다.

place()를 ReservationService가 아니라 별도 빈 ReservationTransaction에 둔 이유는?

README에 명시된 이유는 없다. 추론 Spring AOP 프록시는 같은 클래스 내부 호출(self-invocation)에 @Transactional을 적용하지 않으므로, 트랜잭션 경계를 별도 빈으로 분리해 두면 바깥(ReservationService)에서 재시도·후처리를 트랜잭션 밖에 붙이기 쉽다.

이 구조를 서비스 3개로 쪼개면 무엇이 깨지나요?

@Transactional은 자기 DB 하나만 관리한다. 좌석이 seat_db에 커밋된 뒤 지갑이 실패하면 예약 서비스의 롤백으로 좌석을 되돌릴 수 없다 → MSA 단계에서 좌석 2석이 남는 부분 커밋을 재현한다.
