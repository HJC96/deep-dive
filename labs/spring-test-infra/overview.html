Testcontainers · 동적 프로퍼티 · ArchUnit — 테스트 인프라를 작은 실험으로

실제 MySQL로 테스트하려면 실행할 때마다 바뀌는 랜덤 포트·JDBC URL을 Spring 설정에 넣어야 합니다. 이 모듈은 정적 yml을 일부러 틀리게 두고 @DynamicPropertySource가 덮어써 진짜 컨테이너 DB에 붙는지 검증합니다. 또 컨테이너 생명주기(@Container vs 수동), ArchUnit으로 계층 의존 방향과 필드 주입 금지를 테스트로 고정합니다.

Java 21Spring Boot 3.4.1Testcontainers (MySQL 8.0.36)ArchUnit 1.4.1Docker 필요

01한눈에

30초 요약

문제

컨테이너 DB 주소는 실행 시점에야 정해져 yml에 미리 쓸 수 없습니다. 컨테이너 시작/종료 책임이 흩어지기 쉽고, “Controller→Service→Repository”나 “생성자 주입” 같은 규칙은 코드 리뷰만으로는 무너집니다.

접근

① 틀린 정적 datasource + 동적 등록 → select database()로 실제 연결 확인 ② @Container 유무·수동 start/stop 비교 ③ ArchUnit layeredArchitecture() ④ NO_CLASSES_SHOULD_USE_FIELD_INJECTION.

결론

동적 프로퍼티가 정적 yml보다 우선합니다. @Container는 JUnit이 생명주기를 맡고, 같은 @Testcontainers 클래스의 필드라도 어노테이션이 없으면 시작되지 않습니다. 아키텍처 규칙은 바이트코드 기준 테스트로 깨지면 실패하게 만들 수 있습니다.

02흐름

단계를 클릭하면 상세 설명이 나옵니다. (DynamicPropertySourceTest)

→ → → →

@ActiveProfiles("dynamic-property-source")로 application-dynamic-property-source.yml이 켜집니다. 값은 일부러 틀림: jdbc:mysql://localhost:1/this_datasource_should_not_be_used, wrong-user, wrong-password.

@Testcontainers + @Container static MySQLContainer → JUnit 확장이 테스트 클래스 시작 전에 컨테이너를 띄웁니다(DB명 dynamic_property_source, user test). 호스트 포트는 랜덤.

@DynamicPropertySource static void registerProperties(DynamicPropertyRegistry)가 spring.datasource.url/username/password를 컨테이너 값(Supplier)으로 등록. 이 값은 Spring Environment에서 yml보다 높은 우선순위를 가집니다.

자동 구성된 DataSource로 연결해 select database() = dynamic_property_source, connection.isValid(2) = true. URL에 localhost:1이 없고 username이 test인지도 단언합니다.

동적 등록이 없다면 DataSource는 정적 값(localhost:1, wrong-user)으로 연결을 시도해 실패할 것입니다. 추론 이 실패 경로 자체는 테스트로 실행하지 않습니다 — 그래서 일부러 틀린 값을 두어 “통과했다 = 동적 값이 이겼다”가 되게 설계한 것입니다.

03비교·핵심 구현

탭을 눌러 케이스별로 봅니다.

@DynamicPropertySource — 실행 시점 값 주입 통과

@Testcontainers
@SpringBootTest
@ActiveProfiles("dynamic-property-source")
class DynamicPropertySourceTest {

    @Container
    private static final MySQLContainer MYSQL = new MySQLContainer(DockerImageName.parse("mysql:8.0.36"))
            .withDatabaseName("dynamic_property_source")
            .withUsername("test")
            .withPassword("test");

    @DynamicPropertySource
    static void registerProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", () -> MYSQL.getJdbcUrl() + "?serverTimezone=UTC");
        registry.add("spring.datasource.username", MYSQL::getUsername);
        registry.add("spring.datasource.password", MYSQL::getPassword);
    }
    // ...
}
왜 static
ApplicationContext를 만들기 전에 호출되어야 하므로 인스턴스가 없는 static 메서드입니다.
왜 Supplier
MYSQL::getUsername처럼 지연 평가 — 컨테이너가 뜬 뒤 실제 값을 읽습니다.
결과
URL이 jdbc:mysql://localhost:로 시작하고 /dynamic_property_source 포함, localhost:1 미포함. username test. 쿼리 결과 dynamic_property_source.

@Container vs 수동 start/stop 생명주기

@Container (자동)

@Testcontainers
class ContainerAnnotationLifecycleTest {
    @Container
    private static final MySQLContainer MANAGED_MYSQL = ...;

    // 같은 위치(static 필드), 어노테이션만 없다
    private static final MySQLContainer NOT_MANAGED_MYSQL = ...;

    // 테스트 실행 중
    assertThat(MANAGED_MYSQL.isRunning()).isTrue();
    assertThat(NOT_MANAGED_MYSQL.isRunning()).isFalse();
}

수동

class ManualContainerLifecycleTest {
    @BeforeAll
    static void startContainer() {
        runningBeforeStart = MYSQL.isRunning(); // false
        MYSQL.start();
    }

    @AfterAll
    static void stopContainer() {
        MYSQL.stop();
        assertThat(MYSQL.isRunning()).isFalse();
    }
}
차이
@Container는 선언 = 시작·종료 위임. 수동은 선언(필드)/시작(@BeforeAll)/종료(@AfterAll) 위치가 흩어집니다. 이 테스트는 Spring 컨텍스트가 없고, Spring 테스트라면 @DynamicPropertySource 등록이 네 번째 위치로 더해집니다.
세 번째 방식
spring-data-jpa 모듈의 MySQLContainerTest는 static {}에서 한 번 start하고 stop하지 않는 싱글톤 컨테이너 패턴 — 캐시된 Spring 컨텍스트가 죽은 포트를 가리키지 않게 하려는 것입니다(그 파일 주석).

ArchUnit — 계층 의존 방향 고정 통과

ArchRule rule = layeredArchitecture()
        .consideringAllDependencies()
        .layer("Controller").definedBy(BASE_PACKAGE + ".controller..")
        .layer("Service").definedBy(BASE_PACKAGE + ".service..")
        .layer("Repository").definedBy(BASE_PACKAGE + ".repository..")
        .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
        .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
        .whereLayer("Repository").mayOnlyBeAccessedByLayers("Service");

assertThatCode(() -> rule.check(classes)).doesNotThrowAnyException();

// 위반 케이스: 같은 규칙에 violation 패키지를 Repository 계층으로 추가
.layer("Repository").definedBy(BASE_PACKAGE + ".repository..", VIOLATION_PACKAGE + ".repository..")
assertThatThrownBy(() -> rule.check(classesWithViolation))
        .isInstanceOf(AssertionError.class)
        .hasMessageContaining("ControllerCallingRepository");
legacy 제외 이유
mayOnlyBeAccessedByLayers는 계층으로 정의되지 않은 패키지의 접근도 위반으로 잡기 때문(README). 그래서 importPackages에 controller/service/repository만 넣습니다.
음성 테스트
위반 예제 archunit.violation.repository.ControllerCallingRepository(Repository가 SampleController 호출)를 별도 패키지에 두고, 위반 케이스에서만 Repository 계층에 넣어 AssertionError를 확인합니다. 정상 케이스는 이 패키지를 임포트하지 않습니다.

필드 주입 금지 규칙 legacy에서 위반 탐지

// legacy/LegacyNotificationService — 일부러 위반
@Service
public class LegacyNotificationService {
    @Autowired
    private SampleRepository sampleRepository;
}

// CodingRuleTest
JavaClasses classes = new ClassFileImporter().importPackages(BASE_PACKAGE + ".legacy");
assertThatThrownBy(() -> NO_CLASSES_SHOULD_USE_FIELD_INJECTION.check(classes))
        .isInstanceOf(AssertionError.class);
결과
controller/service/repository만 import → 통과(전부 생성자 주입). legacy만 import → AssertionError.
왜 금지
필수 의존성이 생성자에 드러나지 않고, 테스트에서 목 주입에 리플렉션이 필요하며, 순환 의존이 생성 시점에 드러나지 않습니다(README).

05한계·약점

README가 스스로 밝힌 한계와, 코드에서 확인되는 약점.

README-코드 불일치 케이스 1 README 스니펫이 실제 테스트와 다름 수정함

어떻게 고쳤나: README 스니펫을 실제 테스트와 같게 맞추고(@ActiveProfiles, withDatabaseName/withUsername/withPassword), 각 줄이 어떤 기대값의 근거인지 확인 포인트에 적었습니다.

원래 README 스니펫에는 @ActiveProfiles("dynamic-property-source")와 .withDatabaseName("dynamic_property_source").withUsername("test").withPassword("test")가 없습니다. README만 보고 따라 하면 틀린 yml 프로필이 켜지지 않아 “틀린 값을 덮어쓴다”는 실험 의미가 사라지고, DB 이름 단언도 성립하지 않습니다. 실제 코드는 DynamicPropertySourceTest.java를 보세요.

코드 계층 위반 음성 테스트 없음 수정함

어떻게 고쳤나: 위반 예제 ControllerCallingRepository를 정상 규칙에서 제외되는 별도 패키지(archunit.violation)에 두고, LayeredArchitectureTest에 이 클래스를 Repository 계층으로 포함했을 때 AssertionError가 나는 테스트를 추가했습니다.

원래 README는 “Repository가 Controller를 호출하면 check()가 AssertionError”라고 하지만, 위반 예제 코드와 그 실패를 단언하는 테스트는 없습니다. 필드 주입 규칙(CodingRuleTest)과 달리 규칙이 실제로 위반을 잡는지 증명되지 않습니다.

코드 “@Container 없으면 시작 안 됨” 테스트는 자명함 수정함

어떻게 고쳤나: 지역 변수 대신 같은 @Testcontainers 클래스에 어노테이션만 뺀 static 필드 NOT_MANAGED_MYSQL을 두고, 테스트 실행 중 MANAGED_MYSQL은 running·이쪽은 not running임을 함께 단언합니다.

원래는 new MySQLContainer(...) 직후 isRunning()이 false인 것은 @Container와 무관하게 당연합니다. 비교 대상인 notManagedMySQL은 지역 변수라 애초에 확장이 관리할 수 없습니다. 어노테이션 유무의 차이를 보여 주려면 같은 위치(static 필드)에 어노테이션만 빼고 비교하는 편이 정확합니다.

README-코드 불일치 수동 방식의 “Spring 프로퍼티 등록 책임” 수정함

어떻게 고쳤나: README를 "선언(필드)·시작(@BeforeAll)·종료(@AfterAll)가 흩어진다, 이 테스트는 Spring 컨텍스트 없이 이 세 위치만 보이며 Spring 테스트라면 프로퍼티 등록이 네 번째 위치로 더해진다"로 고쳤습니다. 테스트에는 start() 전 not running, stop() 후 not running 단언을 더했습니다.

원래 README는 수동 방식에서 선언·시작·종료·Spring 프로퍼티 등록 책임이 흩어진다고 설명하지만, ManualContainerLifecycleTest는 Spring 컨텍스트 없이 컨테이너만 다룹니다.

코드 빌드 설정이 다른 모듈과 다름 · 컨테이너 재사용 없음
  • org.springframework.boot 플러그인 3.4.1을 직접 적용하면서 BOM(platform(...))도 함께 씁니다(버전이 루트 dependencyVersions와 별도로 하드코딩). spring, spring-data-jpa, spring-boot-actuator 등은 java(+application) 플러그인 + BOM 방식이라 모듈 간 빌드 방식이 섞여 있습니다.
  • 세 테스트 클래스가 각각 MySQL 컨테이너를 띄워 느립니다(싱글톤/재사용 미적용).
  • Docker가 없으면 Testcontainers 테스트는 실행 불가(README: “Docker가 떠 있어야 한다”).
일반 지식 다루지 않은 대안: @ServiceConnection

Spring Boot 3.1+에서는 컨테이너 필드에 @ServiceConnection을 붙이면 datasource 프로퍼티 등록을 자동으로 해 줍니다. 이 모듈은 원리 학습을 위해 @DynamicPropertySource만 다룹니다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

@DynamicPropertySource는 왜 필요하고 왜 static이어야 하나요?

컨테이너의 포트·JDBC URL은 실행할 때 정해지므로 yml에 미리 쓸 수 없습니다. 테스트 ApplicationContext가 만들어질 때 DynamicPropertyRegistry로 Environment에 값을 넣어 줍니다. 컨텍스트 생성 전에 호출되어야 해 static이고, 값은 Supplier라 컨테이너가 뜬 뒤 읽힙니다.

정적 yml과 동적 프로퍼티가 충돌하면 무엇이 이기나요? 어떻게 증명했나요?

동적 프로퍼티가 이깁니다. 정적 값을 일부러 접속 불가능한 localhost:1/wrong-user로 두고, 테스트가 실제 DB에 연결해 select database() = dynamic_property_source를 받으면 동적 값이 쓰였다는 증거입니다.

H2 대신 Testcontainers로 실제 MySQL을 쓰는 이유는?

일반 지식 H2는 SQL 방언·락·격리 수준·함수가 MySQL과 달라 “테스트는 통과, 운영에선 실패”가 생깁니다. 운영과 같은 엔진·버전(mysql:8.0.36)으로 테스트해 이 차이를 없앱니다. 대가는 Docker 의존과 느린 기동입니다.

@Testcontainers/@Container는 컨테이너를 언제 시작·종료하나요?

@Testcontainers JUnit 확장이 @Container 필드를 찾아 관리합니다. 일반 지식 static 필드면 테스트 클래스 시작 시 1번 시작해 클래스 끝에 종료, 인스턴스 필드면 테스트 메서드마다 시작/종료합니다. 이 모듈의 필드는 모두 static입니다.

여러 테스트 클래스가 컨테이너를 공유하려면?

싱글톤 컨테이너 패턴: 추상 베이스 클래스의 static {}에서 한 번 start하고 stop하지 않습니다(JVM 종료 시 Ryuk가 정리). spring-data-jpa의 MySQLContainerTest가 이 방식이며, 클래스 단위로 컨테이너를 내리면 캐시된 Spring 컨텍스트가 죽은 포트를 가리키는 문제를 피합니다.

ArchUnit은 무엇을 기준으로 검사하나요?

컴파일된 .class 파일을 ClassFileImporter로 읽어 의존 관계를 분석하고, ArchRule.check(classes)에서 위반이 있으면 AssertionError를 던집니다. 그래서 일반 단위 테스트처럼 CI에서 규칙 위반을 막을 수 있습니다.

필드 주입은 왜 지양하나요?
  • 필수 의존성이 생성자 시그니처에 드러나지 않음 — 의존이 없는 상태로도 객체 생성 가능.
  • 테스트에서 목을 넣으려면 리플렉션이나 Spring 컨텍스트가 필요.
  • 순환 의존이 생성 시점에 드러나지 않음.
  • 일반 지식 생성자 주입은 final 필드로 불변성도 보장.
mayOnlyBeAccessedByLayers를 쓸 때 legacy 패키지를 왜 import에서 뺐나요?

이 규칙은 정의된 계층 외의 패키지가 접근하는 것도 위반으로 봅니다. legacy의 LegacyNotificationService가 SampleRepository를 쓰므로, 포함하면 계층 규칙이 깨집니다. 그래서 계층 검증은 3개 패키지만, 필드 주입 위반은 legacy만 따로 검사합니다.
