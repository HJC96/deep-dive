선착순 쿠폰 재고 차감 — 동시성 제어 9가지를 한 테이블에서 비교

재고 200개짜리 쿠폰 한 장(row 하나)에 요청 200~250개가 동시에 몰리면, "읽고 → 빼고 → 쓰기" 사이에 끼어들기가 생겨 차감이 사라집니다(lost update). 이 모듈은 그 현상을 테스트로 재현한 뒤, JVM 락·DB 락·Redis 락·원자 연산 9가지로 각각 막아 보고 실행 시간을 나란히 찍어 봅니다.

Java 21Spring Boot 3.4.1Spring Data JPAMySQL 8.0.36Redis 7.2.5Redisson 3.38.1Testcontainers

01한눈에

30초 요약

문제

두 요청이 같은 quantity = 200을 읽고 둘 다 199를 저장 → 요청은 2번인데 차감은 1번. 테스트는 200번 발급 후 재고가 0이 아님을 단언합니다.

접근

같은 조건(재고 200, 스레드 풀 32)에서 9가지 방식을 구현: 제어 없음 · synchronized · 원자적 UPDATE · 비관적/낙관적 락 · 네임드 락 · Redis SET NX · Redis Lua · Redisson.

결론

"락으로 줄 세우기"보다 확인+차감을 한 번에 원자적으로(UPDATE … WHERE, Lua) 하는 쪽이 단순하고 빨랐고, 경합이 심한 곳에서 낙관적 락은 재시도 폭주로 가장 느렸습니다(README 예시 출력 기준).

한 줄 암기: 문제의 본질은 "읽기-계산-쓰기"가 원자적이지 않다는 것. 해법은 ① 구간 전체를 직렬화(락)하거나 ② 연산 자체를 원자적으로 만들거나(조건부 UPDATE / Lua) ③ 충돌을 사후 감지 후 재시도(낙관적 락) 중 하나.

02흐름

단계를 클릭하면 상세 설명이 나옵니다. 먼저 "왜 깨지는가", 다음은 "고친 방식들의 공통 골격"입니다.

① 제어 없음 — lost update가 생기는 경로

→ → → →

테스트는 Executors.newFixedThreadPool(32)에 작업 200개를 넣고, 모든 작업이 start.await()에서 기다리다가 start.countDown() 한 번에 동시에 출발합니다. 끝은 done.await()로 기다립니다. (CouponIssueServiceTest)

CouponIssueService.issue()는 @Transactional 안에서 findById로 재고를 읽습니다. 락이 없으므로 여러 스레드가 같은 값(예: 200)을 동시에 읽을 수 있습니다.

CouponStock.decrease()는 일부러 경합 구간을 벌립니다.

int currentQuantity = remainingQuantity;
Thread.yield();               // 다른 스레드에게 CPU 양보 → 끼어들기 유도
remainingQuantity = currentQuantity - 1;

JPA 변경 감지로 커밋 시점에 UPDATE coupon_stock SET quantity = 199가 나갑니다. 같은 200을 읽은 스레드들은 모두 199를 씁니다.

요청은 200번 처리됐지만 재고는 0까지 내려가지 않습니다. 테스트 단언: assertThat(couponStock.remainingQuantity()).isNotEqualTo(0). 남은 값은 실행마다 달라서 README도 "0이 아닐 수 있음"이라고만 적습니다.

② 고친 방식들의 공통 골격 — "임계 구역을 누가 지키나"

→ → →

방식별로 "문지기"가 다릅니다.

  • JVM 모니터: synchronized
  • DB row 락: SELECT … FOR UPDATE (PESSIMISTIC_WRITE)
  • DB 문자열 키 락: GET_LOCK('1', 10)
  • Redis 키 존재 여부: SET coupon:issue:lock:1 LOCK NX + TTL 30초 / Redisson RLock
  • 문지기 없음, 연산 자체가 원자적: 조건부 UPDATE, Redis Lua
  • 문지기 없음, 커밋 때 검사: @Version

락 계열(비관적·네임드·Redis·Redisson)은 안쪽에서 기존 CouponIssueService와 같은 읽기-차감-쓰기를 그대로 실행합니다. 원자 연산 계열은 이 단계가 SQL 한 문장 / Lua 스크립트 한 번으로 줄어듭니다.

핵심 규칙: 락을 풀기 전에 커밋되어야 다음 스레드가 갱신된 값을 봅니다. 네임드 락은 이를 위해 차감을 REQUIRES_NEW로 분리했고, Redis/Redisson 락은 couponIssueService.issue()(프록시의 @Transactional)가 반환된 뒤 finally에서 락을 해제합니다.

실패 시 동작이 방식마다 다릅니다.

  • 비관적·synchronized·Redisson: 그냥 대기
  • Redis SET NX: 10ms 쉬고 재시도 루프
  • 낙관적 락: 커밋 때 ObjectOptimisticLockingFailureException → 5ms 후 새 트랜잭션으로 재시도
  • 원자적 UPDATE / Lua: 재고가 없으면 affected rows = 0 / 0 반환 → 즉시 거절 (250개 중 50개)

동시성 제어 없음 재고 ≠ 0

기준선(baseline). 평범한 JPA 코드가 동시성 앞에서 어떻게 깨지는지 보여 줍니다.

@Transactional
public void issue(Long couponId) {
    CouponStock couponStock = couponRepository.findById(couponId)
            .orElseThrow(() -> new IllegalArgumentException("..."));
    couponStock.decrease();          // 내부에 Thread.yield()
    couponRepository.save(couponStock);
}
어떻게
SELECT → 메모리 −1 → 커밋 시 UPDATE. 각 단계 사이에 다른 트랜잭션이 끼어들 수 있음.
결과
isNotEqualTo(0) — 남은 재고가 0이 아님을 단언.
포인트
@Transactional만으로는 동시성이 해결되지 않는다. (MySQL 기본 격리 수준 REPEATABLE READ에서도 일반 SELECT는 락을 잡지 않음 — 일반 지식)

synchronized 재고 0 단일 JVM 한정

메서드 전체를 JVM 모니터로 감싸 한 번에 한 스레드만 들어가게 합니다.

public final class SynchronizedCouponIssueService {   // 스프링 빈 아님, 테스트에서 new로 생성
    public synchronized void issue(Long couponId) {
        CouponStock couponStock = couponRepository.findById(couponId).orElseThrow(...);
        couponStock.decrease();
        couponRepository.save(couponStock);
    }
}
어떻게
읽기·계산·저장이 순서대로 하나씩 실행.
주의
이 클래스에는 @Transactional이 없습니다. 그래서 findById, save가 각자 리포지토리 트랜잭션으로 즉시 커밋되고, 모니터를 놓기 전에 DB에 반영됩니다. 만약 메서드에 @Transactional을 붙이면 프록시가 모니터 해제 후에 커밋해 다시 lost update가 생길 수 있습니다 일반 지식.
트레이드오프
서버가 여러 대면 JVM마다 모니터가 따로라 무력. 전 구간 직렬화로 처리량 저하. (README 한계)

원자적 UPDATE 성공 200 / 실패 50

"재고가 1 이상이면 1 빼라"를 SQL 한 문장으로. 애플리케이션 락이 필요 없습니다.

@Transactional
@Modifying
@Query("""
        UPDATE CouponStock c
        SET c.remainingQuantity = c.remainingQuantity - 1
        WHERE c.couponId = :couponId AND c.remainingQuantity >= 1
        """)
int decreaseQuantity(@Param("couponId") Long couponId);

// AtomicUpdateCouponIssueService
public boolean issue(Long couponId) {
    return couponRepository.decreaseQuantity(couponId) == 1;
}
어떻게
조건 검사와 차감이 한 문장. 같은 row UPDATE는 MySQL이 row 락으로 순서대로 처리. affected rows 1이면 성공, 0이면 재고 부족.
결과
250 요청 → issuedCount == 200, 재고 0. 재고가 음수로 내려가지 않음.
트레이드오프
단순 증감에만 적합. 여러 테이블 검증·복잡한 정책은 한 문장으로 끝내기 어려움 (README 한계).

비관적 락 (SELECT … FOR UPDATE) 재고 0

읽는 순간 row에 쓰기 락을 걸어, 커밋까지 다른 트랜잭션을 기다리게 합니다.

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT c FROM CouponStock c WHERE c.couponId = :couponId")
Optional<CouponStock> findByIdWithPessimisticLock(@Param("couponId") Long couponId);

@Transactional
public void issue(Long couponId) {
    CouponStock couponStock = couponRepository.findByIdWithPessimisticLock(couponId).orElseThrow(...);
    couponStock.decrease();
    couponRepository.save(couponStock);
}
어떻게
DB가 락을 관리 → 서버가 여러 대여도 동작.
트레이드오프
전 구간 직렬화, 락 대기 동안 커넥션 점유 → 풀 고갈·락 타임아웃·데드락 위험 (README 한계).
코드

낙관적 락 (@Version) + 재시도 재고 0 가장 느림

락을 안 잡고, 커밋 때 UPDATE … WHERE version = 읽은값으로 충돌을 감지. 충돌하면 처음부터 다시.

// 재시도 루프는 트랜잭션 "밖"
public void issue(Long couponId) {
    while (true) {
        try {
            self.issueOnce(couponId);      // 프록시 경유 → 시도 1회 = 트랜잭션 1개
            return;
        } catch (ObjectOptimisticLockingFailureException conflict) {
            sleep(BACKOFF_MILLIS);         // 5ms
        }
    }
}

@Transactional
public void issueOnce(Long couponId) { ... }   // 이 시점에 커밋됨
왜 self?
this.issueOnce()는 프록시를 우회해 @Transactional이 무시됨(self-invocation). 생성자에 @Lazy OptimisticLockCouponIssueService self를 주입해 프록시를 직접 호출. @Lazy는 자기 자신 주입의 순환 참조를 끊기 위함.
왜 별도 엔티티?
@Version을 공용 CouponStock에 두면 "락 없음" 케이스까지 버전 검사를 받아 lost update가 재현되지 않음 → VersionedCouponStock로 분리 (README).
트레이드오프
충돌 = 실패라 재시도 코드가 필수. 한 row에 200개가 몰리면 재시도 폭주 → 충돌이 드문 상황에 적합 (README).
코드
labs/coupon-issue/src/main/java/dev/deepdive/coupon/service/OptimisticLockCouponIssueService.java, .../core/VersionedCouponStock.java

네임드 락 (MySQL GET_LOCK) 재고 0

row가 아니라 문자열 키에 거는 MySQL 락. 락 대상을 앱이 자유롭게 정합니다.

@Query(value = "SELECT GET_LOCK(:key, 10)", nativeQuery = true)
Integer getLock(@Param("key") String key);     // 성공 1, 타임아웃 0, 에러 NULL

@Transactional                                   // getLock/releaseLock을 같은 커넥션에 고정
public void issue(Long couponId) {
    try {
        namedLockRepository.getLock(couponId.toString());
        self.issueOnce(couponId);                // REQUIRES_NEW → 락 풀기 전에 커밋
    } finally {
        namedLockRepository.releaseLock(couponId.toString());
    }
}
어떻게
락 잡는 커넥션 1개 + 차감 커넥션 1개(REQUIRES_NEW)가 동시에 필요. 차감을 먼저 커밋해야 다음 스레드가 최신 재고를 봄.
트레이드오프
직렬화로 처리량 저하, 대기 스레드도 커넥션 점유, MySQL 종속 (README 한계).
코드

Redis 분산락 (SET NX) 재고 0 소유자 확인 없음

Redis 키가 "있으면 잠김, 없으면 열림". 직접 스핀락을 구현했습니다.

private static final Duration LOCK_TTL = Duration.ofSeconds(30);
private static final long LOCK_RETRY_MILLIS = 10L;
private static final String LOCK_VALUE = "LOCK";

public void issue(Long couponId) {
    String lockKey = "coupon:issue:lock:" + couponId;
    lock(lockKey);                         // setIfAbsent(lockKey, "LOCK", 30s) 될 때까지 10ms 간격 재시도
    try {
        couponIssueService.issue(couponId);
    } finally {
        redisTemplate.delete(lockKey);     // 내 락인지 확인하지 않고 삭제
    }
}
어떻게
DB 차감은 기존 CouponIssueService 재사용, Redis는 문지기 역할만.
트레이드오프
TTL이 짧으면 작업 중 락 만료, 길면 장애 시 대기 증가 (README). 값이 고정 문자열이라 남의 락을 지울 수 있음(아래 약점).

Redis Lua 원자 차감 성공 200 / 실패 50 가장 빠름

"확인 → 차감"을 Lua 스크립트 하나로 묶어 Redis 안에서 원자적으로 실행합니다.

local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock < 1 then
    return 0
end
redis.call('DECR', KEYS[1])
return 1
public boolean issue(Long couponId) {

어떻게
Redis는 스크립트 실행 중 다른 명령을 끼워 넣지 않음 → 확인과 차감 사이 틈이 없음. 키: coupon:stock:1.
결과

트레이드오프

Redisson 분산락 (RLock) 재고 0

직접 짠 SET NX 루프 대신 Redisson이 획득·대기·해제를 처리합니다.

public void issue(Long couponId) {
    RLock lock = redissonClient.getLock(LOCK_KEY_PREFIX + couponId);  // "coupon:issue:redisson-lock:"
    lock.lock();
    try {
        couponIssueService.issue(couponId);
    } finally {
        lock.unlock();
    }
}
어떻게
스핀 루프·TTL·해제 코드를 라이브러리에 위임. lock()을 leaseTime 없이 쓰면 watchdog이 락을 자동 연장 일반 지식.
주의
이 클래스는 @Service가 아닌 일반 클래스이고, 테스트가 Redisson.create(config)로 클라이언트를 직접 만들어 주입합니다.
트레이드오프
여전히 직렬화, Redis와 DB 모두 의존, lease/watchdog 동작 이해 필요 (README 한계).

05한계·약점

README가 스스로 밝힌 한계와, 코드에서 확인되는 약점. 면접관이 파고들 수 있는 지점입니다.

README 명시 방식별 한계

  • synchronized: 단일 JVM에서만 유효, 전 구간 직렬화.
  • 원자적 UPDATE: 단순 증감에만 적합, 복잡한 정책은 한 문장으로 어려움.
  • 비관적·네임드 락: 직렬화로 처리량 저하, 커넥션 점유 → 풀 고갈·락 타임아웃·데드락 위험. 네임드 락은 MySQL 종속.
  • 낙관적 락: 충돌 = 실패라 재시도 필수, 경합이 심하면 재시도 폭주로 가장 느림.
  • Redis SET NX: TTL 길이 딜레마(짧으면 작업 중 만료, 길면 장애 시 대기).
  • Redis Lua: Redis가 기준 저장소가 됨 → DB 동기화 전략·장애·복제 지연 설계 필요.
  • Redisson: 직렬화, Redis+DB 이중 의존, lease/watchdog 이해 필요.

코드 분석 README에 없는 약점

Redis 락 값이 고정 "LOCK"이고, 해제 시 소유자 확인 없이 delete

RedisLockCouponIssueService는 모든 요청이 같은 값 "LOCK"으로 setIfAbsent하고, finally에서 무조건 redisTemplate.delete(lockKey)합니다.

시나리오: A의 작업이 TTL(30초)보다 길어져 락이 만료 → B가 락 획득 → A가 끝나며 B의 락을 삭제 → C도 진입 → 동시 실행. 이 테스트(짧은 작업)에서는 드러나지 않습니다.

개선 일반 지식: 값에 요청별 UUID를 넣고, "값이 내 것일 때만 DEL"을 Lua로 원자 실행. 또는 Redisson 사용.

네임드 락이 GET_LOCK 반환값을 무시

NamedLockRepository 주석에 "성공 1, 타임아웃 0, 에러 NULL"이라고 적어 놓고, NamedLockCouponIssueService.issue()는 반환값을 확인하지 않고 바로 self.issueOnce()를 호출합니다. 10초 안에 락을 못 얻으면 락 없이 차감이 실행되고, finally에서 잡지도 않은 락을 해제합니다.

개선: 반환값이 1이 아니면 예외로 중단하고, 획득한 경우에만 해제.

실행 시간 비교 조건이 같지 않다 (웜업·요청 수·1회 측정)
  • 웜업(warmUpOnce, 경로별 1,000회)은 CouponIssueServiceTest(MySQL 5케이스: 락 없음·비관적·원자적·낙관적·네임드)에만 있고 synchronized는 같은 클래스라 JIT·풀 예열 효과는 공유. RedisCouponIssueServiceTest의 Redis·Lua·Redisson은 웜업 없이 측정.
  • 원자적 UPDATE·Lua는 250건, 나머지는 200건.
  • 각 값은 System.nanoTime() 1회 측정 (JMH 아님).
낙관적 락 재시도에 상한·지터가 없다

while (true) + 고정 5ms. 충돌이 계속되면 무한히 돌 수 있고, 모든 스레드가 같은 간격으로 재충돌할 수 있습니다. 운영이라면 최대 재시도 횟수와 지수 백오프+지터를 둡니다 일반 지식.

"락 없음" 테스트는 비결정적

isNotEqualTo(0)은 경합이 "운 좋게" 안 생기면 실패할 수 있습니다. Thread.yield()로 확률을 높였을 뿐 보장은 아닙니다.

빈 구성이 케이스마다 다르다

SynchronizedCouponIssueService, AtomicUpdateCouponIssueService는 final 클래스로 @Service가 아니고 테스트에서 new로 생성. RedissonLockCouponIssueService도 빈이 아니며 RedissonClient를 테스트가 직접 만듭니다. 실제 앱에 붙이려면 빈 등록·설정이 추가로 필요합니다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

선착순 쿠폰에서 동시성 문제가 왜 생기나요? @Transactional이면 안전하지 않나요?
  • "읽기 → 계산 → 쓰기"가 원자적이지 않아, 두 트랜잭션이 같은 값(200)을 읽고 같은 값(199)을 쓰는 lost update.
  • @Transactional은 원자성(전부 커밋/롤백)을 주지만 다른 트랜잭션과의 상호 배제를 주지 않음. 일반 SELECT는 락 없이 읽음 일반 지식.
  • 이 모듈은 Thread.yield()로 끼어들기를 유도해 200건 후 재고 ≠ 0을 재현.
9가지 중 실무에서 하나를 고른다면? 이유는?
  • 단순 재고 차감이면 원자적 UPDATE(WHERE quantity >= 1): 락 코드 없음, DB가 정합성 보장, 실패 여부를 affected rows로 즉시 앎. 이 실험에서도 250건 중 정확히 200건만 성공.
  • 트래픽이 DB를 넘어서면 Redis Lua로 앞단에서 걸러내고 DB 기록은 비동기로(→ seat-reservation 모듈의 Kafka 구조). 단 Redis가 기준 저장소가 되는 부담.
  • 로직이 복잡해 한 문장으로 안 되면 비관적 락 또는 분산락.
비관적 락 vs 낙관적 락, 언제 무엇을 쓰나요?
  • 비관적: 충돌이 잦을 때. 미리 막아 재시도 비용 없음. 대신 대기·커넥션 점유·데드락 위험.
  • 낙관적: 충돌이 드물 때. 락 비용 없음. 충돌 시 예외 → 재시도 코드 필수.
  • 근거: README 예시에서 같은 row에 200개를 몰았더니 낙관적 락 3,156ms vs 비관적 락 429ms.
낙관적 락 재시도를 왜 @Transactional 메서드 밖에 두었고, self 주입은 왜 필요했나요?
  • 충돌은 커밋 시점에 감지되고 그 트랜잭션은 롤백 대상 → 같은 트랜잭션 안에서는 재시도 불가. 그래서 "시도 1회 = 트랜잭션 1개"(issueOnce), 루프(issue)는 바깥.
  • this.issueOnce()는 프록시를 거치지 않아 @Transactional이 적용되지 않음(self-invocation). 그래서 @Lazy로 자기 프록시를 주입받아 self.issueOnce() 호출.
  • 대안: 재시도 로직을 별도 퍼사드 클래스로 분리하면 self 주입 불필요 (README).
네임드 락에서 REQUIRES_NEW를 쓴 이유와 그 비용은?
  • GET_LOCK/RELEASE_LOCK은 같은 세션(커넥션)에서 해야 하므로 바깥 @Transactional로 커넥션 고정.
  • 차감을 같은 트랜잭션에 두면 락 해제 시점에 아직 커밋 전 → 다음 스레드가 옛 값을 읽음. 그래서 REQUIRES_NEW로 먼저 커밋.
  • 비용: 요청당 커넥션 2개. 이 테스트는 Hikari 40, 스레드 32라 버티지만, 풀이 작으면 고갈 위험(README 한계).
  • 후속 질문 대비: 현재 코드는 GET_LOCK 반환값을 확인하지 않음 → 개선 포인트.
직접 만든 Redis SET NX 락의 문제점은? Redisson과 무엇이 다른가요?
  • 이 코드: 고정 값 "LOCK" + 소유자 확인 없는 delete → TTL 만료 후 남의 락을 지울 수 있음. 10ms 스핀 → Redis에 부하.
  • Redisson 일반 지식: 스레드 식별 값으로 소유자 확인 후 해제, pub/sub 기반 대기(스핀 감소), watchdog으로 작업 중 자동 연장, 재진입 지원.
  • 공통 한계: 락이 결국 직렬화라 처리량은 비슷 (README 예시 1,312ms 대 1,312ms).
Redis Lua가 왜 가장 빨랐고, 그대로 운영에 쓰면 무엇이 문제인가요?
  • 네트워크 왕복 1회 + Redis 내부 원자 실행, DB 접근 없음 → README 예시 41ms.
  • 문제: DB에 발급 기록이 없음. Redis 장애·유실 시 재고 기준이 사라짐. 발급 이력 동기화(비동기 큐 등), 장애·복제 지연 설계 필요 (README 한계).
  • 공정 비교 주의: 이 케이스는 웜업 없이 250건 측정.
synchronized에 @Transactional을 같이 붙이면 어떻게 되나요?
  • 프록시가 메서드 반환 후 커밋 → 모니터가 이미 풀린 상태에서 다음 스레드가 커밋 전 값을 읽어 lost update 가능 일반 지식.
  • 이 모듈의 SynchronizedCouponIssueService는 @Transactional이 없어 리포지토리 호출이 즉시 커밋되므로 테스트가 통과.
  • 그리고 다중 서버면 어차피 무력.
이 실험의 측정 방식에서 신뢰도를 높이려면?
  • 모든 케이스에 같은 웜업, 같은 요청 수, 여러 번 반복 측정 후 평균·분산 제시.
  • 지금은 1회 System.nanoTime() 값이고 MySQL 케이스만 웜업 → 순위는 경향으로만 해석.
  • 실서버 처리량은 nGrinder/k6 같은 부하 도구로 별도 측정 일반 지식.
