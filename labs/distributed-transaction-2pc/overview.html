2PC — 묻고 나서 정한다, 대신 락을 쥐고 기다린다

MSA의 부분 커밋을 2단계 커밋으로 막는다. MySQL의 XA SQL 문을 서로 다른 MySQL 서버 두 대에 직접 실행해 prepare(투표) → commit/rollback(결정)을 눈으로 확인한다. 부분 커밋은 사라지지만, prepare한 참여자가 결정을 기다리며 쥔 락이 다른 요청을 막는 비용을 테스트로 보여 준다.

문제

MSA에서는 좌석이 먼저 커밋돼 버려서 지갑이 실패해도 되돌릴 수 없었다(부분 커밋).

접근

"커밋하기 전에 전원에게 커밋할 수 있는지 묻는다." MySQL XA SQL 문(XA START/END/PREPARE/COMMIT/ROLLBACK)을 서로 다른 MySQL 컨테이너 2대에 직접 실행. 코디네이터는 테스트 메서드의 제어 흐름이다(JTA·코디네이터 클래스 없음).

결론

부분 커밋이 사라진다(좌석 0). 대가: prepare한 참여자는 결정이 올 때까지 락을 쥐고 기다린다. 코디네이터가 죽으면 같은 행 UPDATE·같은 키 INSERT가 Lock wait timeout으로 막히고, 결정을 아는 쪽이 XA COMMIT/ROLLBACK해야 풀린다.

공통 실패 시나리오 정원 10석 워크숍에서 좌석 2석 × 30,000 = 60,000 크레딧이 필요한데 지갑 잔액은 50,000. 좌석은 잡히지만 지갑이 실패한다. 이미 잡힌 좌석이 되돌아가는가? 네 모듈이 모두 이 질문에 답한다.

02흐름

단계를 클릭하면 상세 설명이 나옵니다. 아래는 실패 시 시퀀스.

→ → → →

코디네이터(테스트 메서드)가 seat_db 커넥션에서 XA START 'reservation-1','seat' → UPDATE workshop_seat … WHERE id = 100 AND reserved_count + 2 <= total_seats → 이력 INSERT → XA END.

XA END 뒤에도 락은 풀리지 않는다.

XA PREPARE 성공 = "무슨 일이 있어도 커밋할 수 있다"는 약속(YES 투표). 디스크에 기록하고, 약속을 지키려고 행 락을 계속 쥔다. 아직 커밋은 아니다 → 다른 세션은 옛 값을 본다.

UPDATE wallet SET balance = balance - 60000 WHERE user_id = 1 AND balance >= 60000 → 잔액 50,000이라 0건. XA END 후 prepare하지 않고 그 자리에서 XA ROLLBACK, NO 반환.

지갑은 prepare 전이라 결정을 기다릴 필요가 없다. 기다리는 쪽은 YES를 던진 좌석뿐(README).

한 명이라도 NO → 전원 롤백. 코디네이터가 좌석에 XA ROLLBACK 'reservation-1','seat'. 결과: reserved_count 0, 이력 0건, balance 50,000. 전원 YES였다면 둘 다 XA COMMIT(reserved 2, balance 40,000).

좌석이 prepare한 직후 코디네이터가 죽고 커넥션이 끊겨도 prepared 트랜잭션은 남는다(XA RECOVER 1건).

그동안 다른 커넥션의 같은 행 UPDATE는 innodb_lock_wait_timeout = 3 후 Lock wait timeout. 새 커넥션이 XA COMMIT해야 풀린다.

시퀀스 — 잔액 50,000 실패 시 (좌석은 락을 쥔 채 결정을 기다린다)

03비교·핵심 구현

탭을 눌러 봅니다. SQL·코드는 README와 테스트에서 발췌.

XA 문법 — 두 단계 프로토콜

-- 1단계: 각 참여자가 자기 작업을 하고 prepare까지 간다 (투표)
XA START 'reservation-1','seat';
UPDATE workshop_seat SET reserved_count = reserved_count + 2 WHERE id = 100;
XA END 'reservation-1','seat';
XA PREPARE 'reservation-1','seat';

-- 2단계: 코디네이터가 답을 모아 결정한다
XA COMMIT 'reservation-1','seat';     -- 전원 YES
XA ROLLBACK 'reservation-1','seat';   -- 한 명이라도 NO
단계SQL뜻
1XA START이 브랜치의 작업 시작
1XA END작업 끝. 락은 아직 안 풀린다
1XA PREPARE"무슨 일이 있어도 커밋할 수 있다"는 약속 = YES 투표
2XA COMMIT / XA ROLLBACK코디네이터의 결정 적용
XID
'reservation-1','seat' = 글로벌 트랜잭션 ID(gtrid) + 참여자 브랜치(bqual). 예약 하나 = 글로벌 트랜잭션 하나, 좌석·지갑 = 브랜치 둘.
왜 DB 2대
한 서버 안에서 스키마만 나누면 커밋이 원래 하나로 묶여 2PC가 풀 문제가 없다. 그래서 MySQL 컨테이너 2대(README).

참여자 브랜치 — 투표 로직 YES/NO

private boolean reserveSeatsAndPrepare(Connection seat) throws SQLException {
    execute(seat, "XA START " + SEAT_XID);
    int updated = executeUpdate(seat, """
            UPDATE workshop_seat
               SET reserved_count = reserved_count + %d
             WHERE id = %d AND reserved_count + %d <= total_seats"""
            .formatted(SEAT_COUNT, WORKSHOP_ID, SEAT_COUNT));
    if (updated == 1) {
        execute(seat, "INSERT INTO seat_reservation_history VALUES (%d, %d, %d, %d)"
                .formatted(REQUEST_ID, WORKSHOP_ID, SEAT_COUNT, AMOUNT));
    }
    execute(seat, "XA END " + SEAT_XID);

    if (updated != 1) {
        execute(seat, "XA ROLLBACK " + SEAT_XID);
        return false;
    }
    execute(seat, "XA PREPARE " + SEAT_XID);
    return true;
}
어떻게
검사를 UPDATE의 WHERE에 넣어 "영향 행 수 1 = 가능"으로 판단. 지갑(debitAndPrepare)도 같은 모양: WHERE balance >= 60000.

코디네이터가 죽으면 블로킹

투표를 받고도 결정을 못 들으면 참여자는 혼자 커밋도 롤백도 판단할 수 없다. 커밋하자니 다른 참여자가 NO였을 수 있고, 롤백하자니 이미 YES를 약속했다.

// 좌석이 YES를 던진 직후 코디네이터가 죽었다. 커넥션까지 끊긴다.
try (Connection seat = TwoDatabases.seat()) {
    assertThat(reserveSeatsAndPrepare(seat)).isTrue();
}
assertThat(TwoDatabases.preparedSeatCount()).isEqualTo(1);   // XA RECOVER

try (Connection other = TwoDatabases.seat()) {
    execute(other, "SET SESSION innodb_lock_wait_timeout = 3");
    assertThatThrownBy(() -> executeUpdate(other,
            "UPDATE workshop_seat SET reserved_count = reserved_count + 1 WHERE id = " + WORKSHOP_ID))
            .isInstanceOf(SQLException.class)
            .hasMessageContaining("Lock wait timeout");
}

// 결정을 아는 쪽이 나타나야 풀린다.
try (Connection resolver = TwoDatabases.seat()) {
    execute(resolver, "XA COMMIT " + SEAT_XID);
}
assertThat(TwoDatabases.preparedSeatCount()).isZero();
XA RECOVER
"지금 prepare된 채 결정을 기다리는 트랜잭션"을 서버에 직접 묻는 명령. 만든 커넥션과 무관하게 찾아 주므로 새 커넥션에서 마무리할 수 있다. MySQL 8에서 XA_RECOVER_ADMIN 권한 필요 → 테스트는 root로 접속.

  • 읽기는 MVCC 스냅샷이라 안 막히지만, 이미 잡힌 좌석을 남아 있다고 보여 주게 된다.

05한계·약점

README = README가 밝힌 것, 코드 = 코드·README 대조에서 확인한 것.

README 지연은 측정하지 않았다

"참여자 하나가 느리면 전원이 그만큼 기다린다 … 이건 프로토콜상 그런 것이고 여기서 지연을 측정하지는 않았다." 2PC가 느리다는 주장에 쓸 수치는 이 저장소에 없다.

README 코디네이터 로그·자동 복구 없음, 서비스 분리 안 함

코디네이터는 테스트 메서드의 제어 흐름이고 결정을 어디에도 적지 않는다. 복구는 손으로 XA RECOVER + XA COMMIT. 또 한 프로세스가 두 DB 커넥션을 직접 쥔다 — HTTP로 나뉜 서비스에서 prepare를 요청 사이에 열어 두는 상황은 재현하지 않았다(의도적 선택).

README 수정함 README와 코드가 어긋났던 곳 3군데

아래 3군데는 README에서 코드에 맞게 바로잡았습니다. 면접에서 "문서를 코드와 대조해 고친 경험"으로 쓸 수 있습니다.

  • 3행: "README.html을 내려받아…"라고 하지만 모듈에 README.html 파일이 없다.
  • 49행: "코디네이터 죽음 시나리오와 PreparedLockTest는 일부러 커밋도 롤백도 안 한 채 prepared 트랜잭션을 남기고 끝난다" — 실제 prepare_직후_코디네이터가_죽으면_…은 마지막에 새 커넥션으로 XA COMMIT해 정리하고 끝난다. 남기고 끝나는 건 PreparedLockTest뿐.
  • 55행: 시드 표에 "id=100(잔여 0), id=200(잔여 0)" — 실제 시드는 total_seats 10, reserved_count 0이므로 "예약 0(잔여 10)"이 맞다.
코드 "코디네이터 죽음"은 커넥션 close로 흉내 낸 것

프로세스·서버 장애가 아니라 try-with-resources로 커넥션을 닫은 것이다. MySQL 서버 재시작 후에도 prepared 트랜잭션이 남는지는 검증하지 않았다.

코드 지갑 쪽은 잔액 UPDATE만 — 원장이 없다

wallet 테이블(user_id, balance)만 만들고 MSA의 WalletLedger에 해당하는 테이블이 없다. 좌석 쪽은 seat_reservation_history가 request_id PK로 있어 MSA보다 중복에 강하다(MSA는 unique 없음).

코드 투표가 순차적이다

좌석이 prepare까지 끝낸 뒤에야 지갑 작업을 시작한다. 그 사이 좌석 락 보유 시간이 지갑 작업 시간만큼 늘어난다 추론. 실무 매니저는 참여자 prepare를 병렬로 보낼 수 있다 일반 지식.

코드 실행 조건: 테스트 전용 · Docker · root

src/main이 없는 테스트 전용 모듈(Spring 앱 아님). Testcontainers로 mysql:8.0.36 두 대를 띄우므로 Docker가 필요하고, XA RECOVER의 XA_RECOVER_ADMIN 권한 때문에 root로 접속한다. 일반 사용자로 바꾸면 복구 테스트가 깨진다(README).

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

2PC를 1분 안에 설명해 보세요.

1단계(투표): 코디네이터가 모든 참여자에게 작업 후 PREPARE를 요청 — 참여자는 변경을 디스크에 기록하고 락을 쥔 채 YES/NO. 2단계(결정): 전원 YES면 COMMIT, 하나라도 NO면 ROLLBACK. 이 모듈은 MySQL XA SQL로 이 두 단계를 직접 실행했다.

prepare가 정확히 무엇을 보장하나요? 왜 락을 계속 쥐나요?

"서버가 죽었다 살아나도 커밋할 수 있다"는 약속. 그 약속을 지키려면 다른 트랜잭션이 같은 행을 바꾸지 못하게 막아야 하므로 락을 유지한다. XA END 뒤에도 락은 풀리지 않는다. 이것이 정합성을 얻는 방법이자 대가.

2PC의 블로킹 문제(in-doubt)란?

YES를 던진 참여자가 결정을 못 들으면 혼자 커밋도 롤백도 못 하고 락을 쥔 채 멈춘다. 테스트에서 코디네이터 커넥션을 닫자 XA RECOVER에 1건이 남고, 다른 커넥션의 같은 행 UPDATE는 Lock wait timeout. 결정을 아는 쪽의 XA COMMIT으로만 풀렸다.

같은 request_id로 INSERT하면 왜 중복 키 에러가 아니라 락 대기인가요?

앞의 prepared 트랜잭션이 커밋될지 롤백될지 모르니 DB도 중복 여부를 확정할 수 없다. 그래서 에러 대신 기다린다. 실무에선 "실패한 요청의 재시도가 멈춰 버리는" 현상으로 나타난다(PreparedLockTest).

prepared 상태에서 다른 사용자가 SELECT하면?

막히지 않지만 MVCC 스냅샷이라 커밋 전 옛 값(reserved_count 0)을 본다. 남은 좌석 화면이 이미 잡힌 좌석을 남아 있다고 보여 줄 수 있다.

지갑이 NO일 때 지갑은 왜 코디네이터 결정을 기다리지 않나요?

prepare까지 가지 않았기 때문. 못 내겠다고 판단한 그 자리에서 XA ROLLBACK으로 스스로 정리하고 NO만 돌려준다. 결정을 기다려야 하는 건 YES를 던진 쪽뿐.

Spring에서 실제로 쓰려면? JTA를 쓰면 블로킹이 해결되나요?

JtaTransactionManager + XA DataSource + Narayana/Atomikos 같은 트랜잭션 매니저. 매니저가 결정 로그를 남기고 재기동 시 자동 복구한다. 하지만 블로킹 성질은 그대로(README). 또 Spring Boot 3.0에서 Narayana·Atomikos 스타터가 빠져 서드파티 버전을 써야 한다(README).

왜 MSA에서는 2PC를 잘 안 쓰나요?
  • 참여자가 HTTP 뒤에 있으면 prepare한 트랜잭션을 요청 사이에 열어 둬야 해 커넥션이 묶인다
  • 참여자가 늘수록 전원 YES 확률↓, 하나만 느려도 전체가 느려진다
  • 코디네이터 장애가 전체 가용성을 끌어내린다
  • XA를 지원하지 않는 참여자(외부 결제 API, 일부 MQ, NoSQL)가 흔하다 — 모두 README 근거
이 실험에서 H2를 쓰지 않은 이유는?

커넥션이 끊긴 뒤에도 살아 있는 prepared 트랜잭션과 XA RECOVER가 필요한데 H2는 지원하지 않는다(README, TwoDatabases 주석). 그래서 Testcontainers MySQL 8.0.36 두 대.

2PC의 대안은? 다음 단계와 연결해 보세요.

락을 쥐고 기다리는 대신 "일단 커밋하고 잘못되면 되돌린다". TCC는 Try에서 자원을 잡아 두고 바로 커밋, Cancel로 반대 방향 업무 작업을 한다. 블로킹이 사라지는 대신 멱등성·빈 취소·매달림을 참여자 코드가 감당한다.
