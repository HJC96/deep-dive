Spring Cache 로컬 캐시 — 어노테이션 3종과 캐시 키를 호출 횟수로 확인

Spring Cache는 "DB를 자동으로 캐시"하는 기능이 아니라, Bean 메서드 호출 앞뒤에 프록시를 끼워 캐시 조회·저장·삭제를 대신해 주는 추상화입니다. 이 모듈은 외부 Redis 없이 ConcurrentMapCacheManager(JVM 안 ConcurrentHashMap)로 @Cacheable/@CachePut/@CacheEvict와 캐시 키 규칙을 관찰하고, 로컬 캐시가 왜 여러 서버에서 한계가 있는지 정리합니다.

Java 21Spring Boot 3.4.1Spring CacheConcurrentMapCacheManagerMySQL 8.0.36 · JPATestcontainers@MockitoSpyBean

01한눈에

30초 요약

문제

같은 조회마다 DB를 치면 느리고, 캐시 코드를 직접 쓰면 반복됩니다. 게다가 캐시 키를 잘못 잡으면 다른 요청이 같은 값을 공유하거나 매번 miss가 나고, 로컬 캐시는 서버마다 따로 존재합니다.

접근

StudyBookService로 어노테이션 4가지 동작, BookLookupService로 cacheName 분리·key="#id"·DTO equals·테이블 버전 키를 실험. MySQL(Testcontainers)에 데이터를 넣고 @MockitoSpyBean BookRepository 호출 횟수로 검증.

결론

캐시 동작은 프록시 + CacheManager + 키 설계로 결정됩니다. 로컬 캐시는 빠르지만 재시작 시 소멸·서버 간 불일치·JVM 메모리 부담이 있어, 분산 환경이면 Redis 같은 리모트 캐시를 고려합니다.

02흐름

@Cacheable 메서드를 호출했을 때 프록시 안에서 일어나는 일. 단계를 클릭하세요.

→ → → →

@EnableCaching(SpringCacheApplication)이 캐시 AOP 인프라를 켭니다. 호출 코드 → 캐시 프록시 → CacheInterceptor가 CacheOperationSource로 메서드의 어노테이션(cacheNames, key, operation)을 읽습니다.

조건: 대상이 Spring Bean이어야 하고(직접 new 한 객체는 동작 안 함), 호출이 프록시를 지나야 합니다.

key = "#id"처럼 SpEL을 쓰면 그 결과가 key(README의 "Key Expression Evaluation"). 생략하면 SimpleKeyGenerator: 파라미터 0개 → SimpleKey.EMPTY, 1개 → 그 값 자체, 여러 개 → SimpleKey.

CacheResolver(기본 SimpleCacheResolver)가 CacheManager.getCache("studyBooks")로 실제 Cache를 찾습니다. 이 모듈의 CacheManager는 CacheConfig가 등록한 ConcurrentMapCacheManager.

Cache.get(key)에 값이 있으면 대상 메서드 자체를 실행하지 않고 반환. 그래서 Repository 호출 횟수로 hit/miss를 확인할 수 있습니다.

miss면 실제 메서드를 실행(→ BookRepository → MySQL)하고 결과를 Cache.put(key, result). @CachePut은 hit 여부와 무관하게 항상 실행 후 put, @CacheEvict는 실행 후(기본 beforeInvocation = false) 삭제.

로컬 캐시의 구조적 한계 — 서버가 두 대라면

README: 로컬 캐시는 "빠른 조회"에는 좋지만 "여러 서버의 캐시를 동시에 바꾸는 문제"는 직접 해결하지 않습니다. 잘 맞는 데이터는 국가별 공휴일, 서비스 설정값, 거의 바뀌지 않는 코드성 데이터. 주의할 데이터는 사용자별 데이터, 서버 간 동기화가 필요한 데이터, 대용량 데이터.

03비교·핵심 구현

탭을 눌러 케이스별로 봅니다. 코드는 실제 파일에서 발췌했습니다.

어노테이션메서드 실행캐시 동작테스트에서 확인
@Cacheablemiss일 때만get → (miss) put2회 호출에 findNameById 1회
@CachePut항상실행 후 결과로 덮어쓰기이후 조회에 findNameById 0회
@CacheEvict항상실행 후 key 삭제다음 조회에 findNameById 1회
@CacheEvict(allEntries = true)항상캐시 전체 clear()1L, 2L 모두 다시 조회

StudyBookService — @Cacheable / @CachePut / @CacheEvict

// miss일 때만 JPA Repository를 호출하고, 반환값을 studyBooks 캐시에 저장한다.
@Cacheable(cacheNames = "studyBooks", key = "#id")
public String findName(long id) {
    return findNameDirectly(id);
}

// 캐시 hit 여부와 상관없이 DB를 갱신하고, 반환값으로 studyBooks 캐시를 덮어쓴다.
@CachePut(cacheNames = "studyBooks", key = "#id")
public String renameWithCachePut(long id, String name) {
    return renameDirectly(id, name);
}

// DB 갱신 후 지정한 key의 캐시를 삭제해서 다음 조회가 다시 Repository를 타게 한다.
@CacheEvict(cacheNames = "studyBooks", key = "#id")
public String renameWithCacheEvict(long id, String name) { ... }

// 개별 key가 아니라 studyBooks 캐시 전체를 삭제한다.
@CacheEvict(cacheNames = "studyBooks", allEntries = true)
public void evictAll() {
}
검증 방법
임의 카운터 대신 @MockitoSpyBean BookRepository로 실제 Repository 호출을 verify(..., times(n)). 매 테스트 전 데이터 reset + 캐시 clear + clearInvocations.
@CachePut 포인트
반환값이 그대로 캐시 값이 되므로 조회 메서드와 같은 타입·같은 key를 돌려줘야 합니다(여기선 이름 String, key #id).
코드
src/main/java/dev/deepdive/springcache/book/StudyBookService.java, src/test/java/dev/deepdive/springcache/annotation/CacheAnnotationStudyTest.java

cacheName은 "공간", key는 "공간 안의 항목"

@Cacheable(cacheNames = "bookById", key = "#id")
public Book findBookById(long id) { ... }

@Cacheable(cacheNames = "bookName", key = "#id")
public String findBookNameById(long id) { ... }
결과
같은 1L이라도 bookById엔 Book, bookName엔 이름 String. 각각 2회 호출해도 findById 1회, findNameById 1회.
주의
같은 cacheName에 다른 타입을 넣으면 같은 key에서 충돌(ClassCast 등)할 수 있으므로 반환 타입별로 공간을 나눕니다.

key="#id" — 다른 파라미터를 의도적으로 무시 버그일 수도

@Cacheable(cacheNames = "bookSummary", key = "#id")
public String findBookSummary(long id, String language) {
    return findBookNameDirectly(id) + " summary language=" + language;
}
결과
findBookSummary(1L, "ko") 뒤 findBookSummary(1L, "en")도 "…language=ko"를 반환. findNameById 1회.
의미
README: "의도한 최적화일 수도 있고, 언어별 결과가 달라야 한다면 버그일 수도 있다." key를 생략했다면 SimpleKey [1L, "ko"]가 됩니다.

DTO를 키로 쓸 때: equals/hashCode가 전부

public record BookSearchCondition(String keyword, String language) { }

public class BookSearchConditionWithoutEquals {
    private final String keyword;
    private final String language;
    // equals/hashCode 없음 → 객체 동일성 비교
}
결과
같은 값 ("java","ko")으로 두 번 조회 시 record는 캐시 엔트리 1개(hit), equals 없는 클래스는 2개(매번 miss).
왜
파라미터가 하나라 SimpleKeyGenerator는 객체 자체를 key로 쓰고, ConcurrentHashMap은 equals/hashCode로 비교하기 때문.

테이블 버전 키 — evict 없이 "새 세대"로 넘기기

@Cacheable(cacheNames = "bookNameByTableVersion",
           key = "{#root.target.currentBookTableUpdatedAt(), #id}")
public String findBookNameByIdWithTableVersion(long id) {
    return findBookNameDirectly(id);
}

public Instant currentBookTableUpdatedAt() {
    return bookRepository.findMaxUpdatedAt()
            .orElse(Instant.EPOCH);
}

// BookRepository
@Query("select max(b.updatedAt) from BookEntity b")
Optional<Instant> findMaxUpdatedAt();
왜 필요
여러 WAS에서 한 서버의 @CacheEvict는 다른 서버 로컬 캐시를 못 지움. Redis를 바로 못 쓰면 max(updatedAt)을 키에 넣어, 테이블 어떤 row가 바뀌든 모든 서버가 새 키로 자연스럽게 miss.
결과
id=1 조회 2회(두 번째 hit) → id=2의 updatedAt을 +60초로 변경 → id=1 조회 2회(첫 번째 miss, 두 번째 hit). findMaxUpdatedAt 4회, findNameById(1L) 2회, 캐시 엔트리 2개(옛 세대 + 새 세대).
운영 팁
README: max(updated_at)이 가벼워야 하므로 인덱스(idx_books_updated_at), 그룹 컬럼이 있으면 (group_key, updated_at) 복합 인덱스.
코드
src/main/java/dev/deepdive/springcache/book/BookLookupService.java, src/main/java/dev/deepdive/springcache/book/BookEntity.java

05한계·약점

README 인정 문서가 스스로 밝힌 한계, 코드 확인 코드를 읽어 보면 드러나는 약점.

README 인정 로컬 캐시의 4가지 한계
  • 서버 재시작 시 캐시가 사라진다.
  • 서버가 여러 대면 각 서버가 서로 다른 캐시를 가진다.
  • 대용량 캐시는 JVM 메모리에 부담을 준다.
  • 서버 간 캐시 동기화가 어렵다. → 분산 환경이면 Redis 같은 리모트 캐시 고려.
README 인정 다중 WAS 문제는 설명만, 테스트로 재현하지 않음

LB + WAS 2대 다이어그램과 테이블 버전 키 아이디어는 있지만, 실제로 두 애플리케이션 컨텍스트를 띄워 불일치를 보여 주는 테스트는 없습니다. 테이블 버전 키도 한 JVM 안에서 "키가 바뀌면 miss"만 확인합니다.

코드 확인 테이블 버전 방식: 매 조회마다 쿼리 1개 추가 + 옛 세대 엔트리 누적
  • key 계산을 위해 hit일 때도 findMaxUpdatedAt()이 실행됩니다(4회 조회 → 4회 쿼리, 테스트가 단언). DB 부하를 "없애는" 게 아니라 가벼운 쿼리로 "바꾸는" 것.
  • 옛 버전 키는 지우지 않아 엔트리가 세대마다 쌓입니다(테스트: hasSize(2)). ConcurrentMapCacheManager는 TTL·크기 제한이 없어 장기적으로 메모리 누수가 됩니다.
  • 정밀도: updated_at은 timestamp(6). 같은 값으로 갱신되면 버전이 안 바뀝니다.
코드 확인 rename 계열은 updatedAt을 그대로 둬서 버전 키가 안 바뀐다

StudyBookService.renameDirectly와 BookLookupService.renameBookAndEvictCache는 before.updatedAt()을 그대로 복사해 저장합니다. 테스트는 renameBookWithoutEvictCache(id, name, updatedAt)로 시각을 명시적으로 넘겨서만 버전을 바꿉니다. 실제로는 @UpdateTimestamp/@LastModifiedDate 같은 자동 갱신이 없으면 이 전략이 조용히 깨집니다.

코드 확인 같은 데이터를 담은 여러 캐시가 함께 무효화되지 않는다

updateBook(@CachePut)과 renameBookAndEvictCache(@CacheEvict)는 bookById만 갱신·삭제합니다. 같은 책 이름을 담은 bookName, bookSummary는 그대로 남아 오래된 이름을 돌려줄 수 있습니다(@Caching으로 묶는 예는 없음).

코드 확인 CatalogLookupService는 README·테스트 어디에도 없다

catalog/CatalogLookupService(@Cacheable(cacheNames = "catalogItems", key = "#itemId") + loadCount)와 CatalogItem은 CacheConfig에 이름만 등록돼 있고, 이를 쓰는 테스트나 문서가 없습니다. 이전 실험의 잔재로 보입니다.

코드 확인 TTL·최대 크기·통계가 없는 캐시

ConcurrentMapCacheManager는 만료와 eviction 정책이 없습니다. 이 모듈은 만료로 인한 재조회나 메모리 상한을 다루지 않습니다. 일반 지식 운영 로컬 캐시는 보통 Caffeine(CaffeineCacheManager)으로 TTL·maximumSize를 둡니다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요. 일반 지식은 이 레포 밖의 널리 알려진 내용입니다.

Spring Cache는 내부적으로 어떻게 동작하나?
  • @EnableCaching → 캐시 어노테이션이 붙은 Bean을 프록시로 감쌈.
  • 호출 시 CacheInterceptor가 CacheOperationSource로 메타데이터를 읽고, key를 계산(SpEL 또는 KeyGenerator), CacheResolver→CacheManager.getCache(name)으로 Cache를 찾아 get/put/evict.
  • 저장소가 로컬이든 Redis든 CacheManager 구현만 바뀜 — 이 모듈은 ConcurrentMapCacheManager.
@Cacheable, @CachePut, @CacheEvict의 차이는?
  • @Cacheable: hit면 메서드 생략. miss면 실행 후 저장.
  • @CachePut: 항상 실행 후 결과로 덮어씀 → 반환 타입이 조회 메서드와 맞아야 함.
  • @CacheEvict: 실행 후 삭제(기본 beforeInvocation=false → 메서드가 예외로 끝나면 삭제 안 됨). allEntries=true면 clear().
  • 테스트 근거: CacheAnnotationStudyTest의 Repository 호출 횟수.
같은 클래스 안에서 @Cacheable 메서드를 호출하면 캐시가 동작할까?
  • README의 동작 조건: "호출이 캐시 프록시를 지나야 한다."
  • 일반 지식 기본 프록시 방식에선 this.method() 내부 호출(self-invocation)은 프록시를 거치지 않아 캐시가 적용되지 않음. 별도 Bean으로 분리하거나 자기 프록시를 주입해 호출.
  • 참고: 이 모듈의 #root.target.currentBookTableUpdatedAt()은 SpEL에서 대상 객체 메서드를 직접 호출하는 것이라 캐싱과 무관.
기본 캐시 키는 어떻게 만들어지고, 어떤 실수가 흔한가?
  • SimpleKeyGenerator: 파라미터 0개 SimpleKey.EMPTY, 1개 그 값, 여러 개 SimpleKey.
  • 실수 1: DTO에 equals/hashCode가 없으면 같은 조건도 다른 키 → 매번 miss (테스트: 엔트리 2개). record를 쓰면 해결.
  • 실수 2: key="#id"처럼 일부 파라미터만 쓰면 language가 달라도 같은 값 공유 → 의도인지 확인.
  • 실수 3: 서로 다른 반환 타입을 같은 cacheName에 넣기 → cacheName 분리.
로컬 캐시와 분산(리모트) 캐시는 어떻게 고르나?
  • 로컬: 네트워크 왕복이 없어 빠름. 대신 재시작 시 소멸, 서버별 불일치, JVM 메모리 부담 (README).
  • 적합: 공휴일, 설정값, 코드성 데이터처럼 거의 안 바뀌고 작은 데이터. 부적합: 사용자별 데이터, 서버 간 동기화가 필요한 데이터.
  • 일반 지식 둘을 섞은 2단(L1 로컬 + L2 Redis) 구성도 흔함 — 핫 데이터는 로컬, 공유는 Redis.
WAS 여러 대에서 로컬 캐시를 무효화하려면?
  • 이 레포의 답: 공통 테이블의 max(updatedAt)을 키에 포함해 버전이 바뀌면 모든 서버가 새 키로 miss (evict 불필요).
  • 비용: 매 조회 max 쿼리(인덱스 필수), 옛 엔트리 누적, updatedAt 갱신 누락 시 무력화.
  • 일반 지식 다른 방법: 짧은 TTL로 불일치 시간 제한, Redis Pub/Sub·메시지 브로커로 evict 이벤트 브로드캐스트, 아예 공용 Redis로 전환.
(꼬리) 테이블 버전 키 방식에서 hit인데도 DB 쿼리가 나가는 이유는?
  • key가 {currentBookTableUpdatedAt(), #id}라 key를 계산하려면 먼저 findMaxUpdatedAt()을 실행해야 함. 테스트도 4회 조회에 4회를 단언.
  • 그래서 무거운 원본 쿼리를 가벼운 인덱스 조회로 바꾸는 트레이드오프. 개선하려면 버전 값을 짧게 로컬 캐싱하거나 별도 버전 테이블/Redis 카운터를 둠(설계 아이디어).
테스트에서 캐시 hit/miss를 어떻게 검증했나?
  • MySQL Testcontainers(mysql:8.0.36)에 JPA로 실제 데이터를 넣고, @MockitoSpyBean BookRepository로 실제 호출은 그대로 두면서 횟수만 verify.
  • 매 테스트 전 데이터 reset, 캐시 clear, clearInvocations로 이전 테스트 hit가 섞이지 않게 함.
  • native cache(ConcurrentMap)를 꺼내 엔트리 수(hasSize)로 키 구분을 확인.
