02동시성

같은 자원을 동시에 바꿀 때의 정합성과 처리량

labs/coupon-issue 개선 완료

선착순 쿠폰 재고 차감 — 동시성 제어 9가지를 한 테이블에서 비교

재고 200개짜리 쿠폰 한 장(row 하나)에 요청 200~250개가 동시에 몰리면, "읽고 → 빼고 → 쓰기" 사이에 끼어들기가 생겨 차감이 사라집니다(lost update). 이 모듈은 그 현상을 테스트로 재현한 뒤, JVM 락·DB 락·Redis 락·원자 연산 9가지로 각각 막아 보고 실행 시간을 나란히 찍어 봅니다.

30초 요약 펼치기
문제
두 요청이 같은 quantity = 200을 읽고 둘 다 199를 저장 → 요청은 2번인데 차감은 1번. 테스트는 200번 발급 후 재고가 0이 아님을 단언합니다.
접근
같은 조건(재고 200, 스레드 풀 32)에서 9가지 방식을 구현: 제어 없음 · synchronized · 원자적 UPDATE · 비관적/낙관적 락 · 네임드 락 · Redis SET NX · Redis Lua · Redisson.
결론
"락으로 줄 세우기"보다 확인+차감을 한 번에 원자적으로(UPDATE … WHERE, Lua) 하는 쪽이 단순하고 빨랐고, 경합이 심한 곳에서 낙관적 락은 재시도 폭주로 가장 느렸습니다(README 예시 출력 기준).

콘서트 좌석 예약 — Redis로 선점하고, Kafka로 DB 쓰기를 떼어 낸다

같은 좌석을 여러 명이 동시에 누르면 한 좌석이 두 명에게 팔리고(동시성 문제), 예매 오픈처럼 요청이 한꺼번에 몰리면 DB가 버티지 못합니다(부하 문제). 이 모듈은 두 문제를 4단계로 쌓아 갑니다: 제어 없음 → Redis SADD 선점 → Redis + Kafka 비동기 확정 → 느린 DB에서 직접 쓰기 vs Kafka 경유 비교.

30초 요약 펼치기
문제
지켜야 할 불변식 두 개: 이중 배정 금지(한 좌석 = 한 명), 1인 1좌석(한 명 = 한 좌석). 제어 없이 "있나 확인 → 없으면 INSERT"하면 좌석 50개에 예약이 50건보다 많아집니다(README 실행 예 53건).
접근
Redis Set 두 개(seat:applied-users, seat:held-seats)에 SADD해서 "처음 넣은 요청만 1"을 받는 성질로 선점. 선점 성공분만 DB에 확정하되, 3단계에서는 Kafka에 커맨드만 넣고 즉시 응답, Consumer가 DB에 저장.
결론
정합성은 Redis 원자 연산이, 부하 흡수는 Kafka가 맡는 역할 분리. 풀 2·지연 20ms인 느린 DB에서 직접 쓰기는 100건 중 88건 실패, Kafka 경유는 실패 0건으로 즉시 응답하고 결국 100건 모두 확정(README 예시 출력).

03캐시

읽기/쓰기 패턴, 장애 패턴, Spring Cache 추상화

labs/cache-patterns 개선 완료

캐시 패턴 실험실 — 읽기·쓰기 패턴 5개와 장애 3대장을 순수 Java로

캐시는 "넣으면 빨라진다"로 끝나지 않습니다. 언제 채우고, 언제 지우고, 동시에 몰리면 어떻게 되는지에 따라 오래된 값이 남거나 DB가 터집니다. 이 모듈은 Redis·Spring 없이 InMemoryCache와 InMemoryProductStore만으로 패턴마다 작은 클래스를 만들고, 저장소 read/write 횟수를 세는 단위 테스트로 차이를 확인합니다.

30초 요약 펼치기
문제
캐시를 잘못 채우거나 지우면 DB와 다른 오래된 값이 남고, 인기 키 동시 miss·없는 키 반복 조회·동시 만료가 일어나면 요청이 DB로 몰립니다.
접근
읽기 2개(Cache Aside, Read Through), 쓰기 3개(Write Through/Around/Behind), race 1개, 3대장(Stampede/Penetration/Avalanche) 방어 클래스를 각각 만들고 저장소 호출 횟수로 비교.
결론
일반 조회는 Cache Aside + Write Around(쓰기 후 evict)가 기본값. 문제별로 single-flight / refresh-ahead, negative caching / Bloom filter, TTL jitter, 버전 비교를 덧붙입니다.

Spring Cache 로컬 캐시 — 어노테이션 3종과 캐시 키를 호출 횟수로 확인

Spring Cache는 "DB를 자동으로 캐시"하는 기능이 아니라, Bean 메서드 호출 앞뒤에 프록시를 끼워 캐시 조회·저장·삭제를 대신해 주는 추상화입니다. 이 모듈은 외부 Redis 없이 ConcurrentMapCacheManager(JVM 안 ConcurrentHashMap)로 @Cacheable/@CachePut/@CacheEvict와 캐시 키 규칙을 관찰하고, 로컬 캐시가 왜 여러 서버에서 한계가 있는지 정리합니다.

30초 요약 펼치기
문제
같은 조회마다 DB를 치면 느리고, 캐시 코드를 직접 쓰면 반복됩니다. 게다가 캐시 키를 잘못 잡으면 다른 요청이 같은 값을 공유하거나 매번 miss가 나고, 로컬 캐시는 서버마다 따로 존재합니다.
접근
StudyBookService로 어노테이션 4가지 동작, BookLookupService로 cacheName 분리·key="#id"·DTO equals·테이블 버전 키를 실험. MySQL(Testcontainers)에 데이터를 넣고 @MockitoSpyBean BookRepository 호출 횟수로 검증.
결론
캐시 동작은 프록시 + CacheManager + 키 설계로 결정됩니다. 로컬 캐시는 빠르지만 재시작 시 소멸·서버 간 불일치·JVM 메모리 부담이 있어, 분산 환경이면 Redis 같은 리모트 캐시를 고려합니다.

Spring Cache + Redis — @Cacheable과 RedisTemplate 직접 구현, 그리고 핫키 분산 락

로컬 캐시는 서버마다 따로라서, 여러 서버가 같은 캐시를 보려면 Redis 같은 공용 캐시가 필요합니다. 하지만 Redis로 옮기면 직렬화, 없는 키 반복 조회, 동시 만료, 핫키 동시 miss를 직접 고민해야 합니다. 이 모듈은 MySQL/JPA를 원본으로 두고 @Cacheable(RedisCacheManager)과 StringRedisTemplate 직접 구현을 비교하며, Null caching · TTL Jitter · SET NX + Lua 분산 락을 Testcontainers로 검증합니다.

30초 요약 펼치기
문제
공용 캐시에도 함정이 있습니다. 없는 id는 캐시에 안 남아 매번 DB로 관통, 인기 키가 비어 있는 순간 40개 요청이 동시에 DB 조회, 같은 TTL로 넣으면 동시에 만료.
접근
세 서비스를 비교: SpringCacheBookService(@Cacheable), RedisTemplateBookCacheService(수동 Cache Aside · __NULL__ sentinel · TTL Jitter), RedisHotKeyBookCacheService(락 없음 vs SET NX 락 + double-check). BookOriginService.readCount로 원본 조회 횟수를 셈.
결론
일반 메서드 결과 캐싱은 Spring Cache로 단순하게, SET NX·Lua·sentinel·jitter처럼 Redis 고유 기능이 필요하면 RedisTemplate. 기본 RedisCacheManager는 non-locking이라 @Cacheable이 분산 락을 대신하지 않습니다.

04분산 트랜잭션

같은 실패 시나리오(잔액 50,000으로 2석×30,000 예약)를 네 단계로 비교

labs/distributed-transaction-monolith 개선 완료

Monolith — 하나의 DB, 하나의 @Transactional

분산 트랜잭션 시리즈의 기준선. 워크숍 좌석 예약·크레딧 차감·원장 기록·예약 확정을 하나의 애플리케이션, 하나의 데이터베이스, 하나의 로컬 트랜잭션으로 처리한다. 잔액이 모자라면 좌석까지 함께 롤백된다는 것을 확인하고, 이 보장이 DB를 나누는 순간 사라진다는 것을 다음 단계로 넘긴다.

30초 요약 펼치기
문제
좌석 예약·크레딧 차감·원장 기록·예약 확정 중 일부만 반영되면 "좌석은 잡혔는데 결제가 안 된" 상태가 생긴다.
접근
네 변경을 ReservationTransaction.place() 하나의 @Transactional로 묶고, 예약 행을 SELECT … FOR UPDATE로 잠가 재실행·동시 실행을 한 번만 처리한다.
결론
DB가 하나면 원자성은 DB가 공짜로 준다. 잔액 부족이면 좌석까지 롤백되어 reserved_count 0. 이 "공짜"가 DB를 쪼개는 순간 사라진다는 것이 다음 단계(MSA)의 출발점.

labs/distributed-transaction-msa 개선 완료

MSA — 서비스를 나누자 부분 커밋이 생겼다

모놀리스의 예약·좌석·지갑을 서비스 3개와 DB 3개로 분리한 기준선. 기능 순서(좌석 예약 → 크레딧 차감 → 예약 확정)는 같지만 각 작업이 서로 다른 앱·DB에서 커밋된다. 좌석 커밋 뒤 지갑이 실패하면 좌석만 남는 부분 커밋을 실제 HTTP 통합 테스트로 재현한다.

30초 요약 펼치기
문제
예약·좌석·지갑을 서비스 3개 · DB 3개로 나누자 하나의 로컬 트랜잭션으로 묶을 수 없게 됐다. 좌석이 커밋된 뒤 지갑이 실패하면 좌석만 잡힌 채 남는다.
접근
세 Spring 앱을 실제 HTTP(RestClient)로 연결하고, 각 서비스는 자기 DB에만 @Transactional. 통합 테스트가 세 앱을 랜덤 포트·독립 H2로 띄워 부분 커밋을 재현·고정한다.
결론
Reservation Service의 롤백은 reservation_db에만 적용된다. 잔액 50,000 실패 시 reserved_count 2, 이력 1건이 남는다. 이 부분 커밋이 2PC·TCC가 풀어야 할 문제다.

2PC — 묻고 나서 정한다, 대신 락을 쥐고 기다린다

MSA의 부분 커밋을 2단계 커밋으로 막는다. MySQL의 XA SQL 문을 서로 다른 MySQL 서버 두 대에 직접 실행해 prepare(투표) → commit/rollback(결정)을 눈으로 확인한다. 부분 커밋은 사라지지만, prepare한 참여자가 결정을 기다리며 쥔 락이 다른 요청을 막는 비용을 테스트로 보여 준다.

30초 요약 펼치기
문제

접근
"커밋하기 전에 전원에게 커밋할 수 있는지 묻는다." MySQL XA SQL 문(XA START/END/PREPARE/COMMIT/ROLLBACK)을 서로 다른 MySQL 컨테이너 2대에 직접 실행. 코디네이터는 테스트 메서드의 제어 흐름이다(JTA·코디네이터 클래스 없음).
결론
부분 커밋이 사라진다(좌석 0). 대가: prepare한 참여자는 결정이 올 때까지 락을 쥐고 기다린다. 코디네이터가 죽으면 같은 행 UPDATE·같은 키 INSERT가 Lock wait timeout으로 막히고, 결정을 아는 쪽이 XA COMMIT/ROLLBACK해야 풀린다.

TCC — 일단 커밋하고, 잘못되면 업무 로직으로 되돌린다

2PC가 남긴 블로킹을 없애는 방법. Try에서 자원을 잡아 두고 곧바로 커밋하고, 전원 성공하면 Confirm, 아니면 Cancel로 반대 방향 UPDATE를 한다. 같은 실패 시나리오에서 결과는 2PC와 같지만 락을 쥐지 않는다. 그 대가로 생기는 중간 상태 노출과 멱등·빈 취소·매달림 문제를 참여자 로그로 처리한다.

30초 요약 펼치기
문제

접근
Try에서 자원을 잡아 두고 바로 커밋(held_count·frozen), 이후 Confirm으로 확정하거나 Cancel로 반대 방향 UPDATE. XA 없이 참여자별 로컬 트랜잭션(DataSource·EMF·TxManager 두 벌) + 참여자 소유 로그 *_tcc_log.
결론
결과는 2PC와 같다(reserved_count 0, balance 50,000). Try 직후에도 다른 요청이 막히지 않는다. 대신 중간 상태가 보이고(격리 포기), 멱등·빈 취소·매달림을 참여자 코드가 감당한다.
