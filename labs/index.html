00학습 지도

트랙을 누르면 그 트랙이 무엇을 묻는지 나옵니다.

→ → →

"여러 요청이 같은 데이터를 동시에 바꾸면 어떻게 지키나?"

선착순 쿠폰 재고(coupon-issue)에서 락 9가지를 같은 조건으로 비교하고, 좌석 예약(seat-reservation)에서 Redis 선점과 Kafka 비동기 확정으로 RDB 병목까지 다룹니다.

"DB 부하를 캐시로 줄일 때 무엇이 깨지나?"

순수 Java로 캐시 패턴 5종과 Stampede·Penetration·Avalanche를 보고(cache-patterns), Spring Cache를 로컬(spring-cache-local)과 Redis(spring-cache-redis)로 옮겨 가며 키 설계·Null 캐싱·TTL Jitter·핫키 분산 락을 확인합니다.

"DB가 여러 개로 나뉘면 원자성은 어떻게 되나?"

같은 좌석 예약 시나리오를 Monolith → MSA → 2PC → TCC 순서로 바꿔 가며, 잔액 부족으로 실패할 때 좌석이 어떻게 남는지 비교합니다. MSA에서 좌석 2석이 남는 부분 커밋이 생기고, 2PC는 이를 없애는 대신 블로킹을, TCC는 블로킹을 없애는 대신 격리 포기와 애플리케이션 복잡도를 얻습니다.

"하나의 트랜잭션으로 묶지 않고도 돈이 맞게 하려면?"

Payment·Wallet·Ledger 세 서비스를 Kafka로 잇고, 트랜잭셔널 아웃박스·PSP 재시도·낙관적 락·복식부기 장부로 최종 일관성을 노리는 결제 시스템(payment-system)입니다. 일부 주제(DLQ 처리, Bulkhead, 대사)는 아직 구현되지 않았습니다.

01동시성

같은 자원을 동시에 바꿀 때의 정합성과 처리량

coupon-issue 수치 있음

선착순 쿠폰 200개를 동시에 차감할 때의 Lost Update. 락 없음·synchronized·원자적 UPDATE·비관적/낙관적/네임드 락·Redis 분산락·Lua·Redisson 9가지 비교.

핵심: 한 행에 경합이 몰리면 낙관적 락은 재시도 폭증 → 가장 느림

seat-reservation 수치 있음

좌석 이중 배정·1인 1좌석 불변식을 Redis SADD로 지키고, 버스트 부하에서 DB 직접 쓰기와 Kafka 경유 비동기 확정을 비교.

핵심: 요청 응답성 ↔ 최종 확정 지연의 트레이드오프

02캐시

읽기/쓰기 패턴, 장애 패턴, Spring Cache 추상화

cache-patterns

Cache Aside·Read Through·Write Through·Write Around·Write Behind, 그리고 Stampede·Penetration·Avalanche를 순수 Java 단위 테스트로 관찰.

spring-cache-local

@Cacheable/@CachePut/@CacheEvict 동작과 캐시 키 설계(SimpleKey, equals, 테이블 버전 키). 로컬 캐시의 다중 서버 한계.

spring-cache-redis

Spring Cache와 RedisTemplate 직접 구현 비교. Null sentinel, TTL Jitter, 핫키 분산 락(SET NX + UUID 토큰 + Lua 해제).

03분산 트랜잭션

같은 실패 시나리오(잔액 50,000으로 2석×30,000 예약)를 네 단계로 비교

단계실패 후 좌석(reserved)얻은 것대가
Monolith0로컬 트랜잭션 하나로 원자성DB를 나눌 수 없음
MSA2서비스·DB 분리부분 커밋, 보상·멱등성 없음
2PC (MySQL XA)0원자성 회복prepared 상태 락 유지, 코디네이터 장애 시 블로킹
TCC0락 없이 정합성중간 상태 노출(격리 포기), 멱등·빈 취소·매달림 직접 처리

출처: 각 모듈 README와 테스트(ReservationServiceTest, MsaLocalTransactionTest, TwoPhaseCommitTest, TryConfirmCancelTest). 지연·성능 수치는 측정하지 않았습니다.

04결제 시스템

앞의 트랙을 모두 합친 종합 실험

payment-system 진행 중

Payment(WebFlux·R2DBC) → Kafka → Wallet·Ledger(MVC·JPA). Toss PSP 승인과 에러 분류·재시도, 트랜잭셔널 아웃박스, 지갑 정산 낙관적 락, 복식부기 장부, 결제 완료 집계.

주의 모듈 README는 아직 "스캐폴딩만 있다"고 적혀 있어 실제 코드와 다릅니다. 상세 페이지에서 계획과 실제 구현을 나눠 정리했습니다.

05Spring·운영·JVM

프레임워크 동작과 관측성, 테스트 인프라, 성능 측정

spring

@Async vs ExecutorService, self-invocation 함정, 순차 vs 병렬 실행, @Retryable로 재시도할 예외와 하지 않을 예외 구분.

spring-data-jpa

@Version 낙관적 락 충돌을 결정적으로 재현하고, Hibernate StatementInspector로 요청당 SQL 수를 Micrometer 메트릭으로 발행.

spring-test-infra

@DynamicPropertySource 우선순위, Testcontainers 수명주기, ArchUnit 계층·필드 주입 규칙 검증.

spring-boot-actuator

Health·Info·Counter·Gauge·Timer·Percentile·HTTP Metrics·Custom Endpoint를 13단계로. "언제 무엇을 쓰나" 선택 기준.

java-sandbox 수치 있음

BouncyCastle Provider를 매 호출 등록 vs 1회 등록을 JMH로 측정하고, gc·stack 프로파일러로 원인(할당 비용, getService 경합)을 확인.
