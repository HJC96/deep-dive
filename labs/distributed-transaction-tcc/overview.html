TCC — 일단 커밋하고, 잘못되면 업무 로직으로 되돌린다

2PC가 남긴 블로킹을 없애는 방법. Try에서 자원을 잡아 두고 곧바로 커밋하고, 전원 성공하면 Confirm, 아니면 Cancel로 반대 방향 UPDATE를 한다. 같은 실패 시나리오에서 결과는 2PC와 같지만 락을 쥐지 않는다. 그 대가로 생기는 중간 상태 노출과 멱등·빈 취소·매달림 문제를 참여자 로그로 처리한다.

Java 21Spring Boot 3.4.1Spring Data JPA × 2MySQL 8.0.36 × 2TestcontainersXA 없음

문제

2PC는 부분 커밋을 막았지만 prepare한 참여자가 락을 쥐고 기다리는 블로킹이 남았다. 코디네이터가 늦거나 죽으면 다른 요청까지 멈춘다.

접근

Try에서 자원을 잡아 두고 바로 커밋(held_count·frozen), 이후 Confirm으로 확정하거나 Cancel로 반대 방향 UPDATE. XA 없이 참여자별 로컬 트랜잭션(DataSource·EMF·TxManager 두 벌) + 참여자 소유 로그 *_tcc_log.

결론

결과는 2PC와 같다(reserved_count 0, balance 50,000). Try 직후에도 다른 요청이 막히지 않는다. 대신 중간 상태가 보이고(격리 포기), 멱등·빈 취소·매달림을 참여자 코드가 감당한다.

공통 실패 시나리오 정원 10석 워크숍에서 좌석 2석 × 30,000 = 60,000 크레딧이 필요한데 지갑 잔액은 50,000. 좌석은 잡히지만 지갑이 실패한다. 이미 잡힌 좌석이 되돌아가는가? 네 모듈이 모두 이 질문에 답한다.
README 한 줄 결론 "2PC는 데이터베이스에 맡기고 블로킹을 감수하고, TCC는 블로킹을 없애는 대신 그 몫을 애플리케이션 코드로 가져온다."

02흐름

단계를 클릭하면 상세 설명이 나옵니다. 아래는 실패 시 시퀀스.

→ → → →

SeatParticipant.tryHold(1, 100, 2) (@Transactional("seatTransactionManager")): 로그가 없으면 WorkshopSeat.hold(2) — reservedCount + heldCount + 2 > totalSeats면 false, 아니면 heldCount += 2. seat_tcc_log에 TRIED 기록 후 메서드 종료와 함께 커밋. 락은 이 시점에 모두 풀린다.

WalletParticipant.tryFreeze(1, 1, 60,000): Wallet.freeze()가 balance -= 60,000, frozen += 60,000(잔액 부족이면 false). wallet_tcc_log에 TRIED 후 커밋.

왜 balance를 실제로 깎나? Try 커밋 후 락이 없으니 frozen만 올리면 다음 요청이 같은 돈을 그대로 본다 → 이중 지출.

held 2, frozen 60,000, reserved 0, balance 40,000 — 이미 커밋된 값이라 남에게 보인다.

이 사이 다른 커넥션의 같은 행 UPDATE가 통과하고(2PC에선 Lock wait timeout), 다른 요청의 Try도 나란히 잡힌다.

confirm(1): 로그가 TRIED일 때만 좌석 held → reserved, 지갑 frozen -= 60,000, 로그 CONFIRMED. 수량은 인자가 아니라 로그에 적힌 값을 쓴다.

결과: reserved 2, held 0, balance 40,000, frozen 0.

잔액 50,000 → tryFreeze가 false(변경 없음, 로그도 없음). 코디네이터가 참여자 전원에 cancel(1) → 좌석은 로그가 TRIED이므로 heldCount -= 2, CANCELLED. 지갑은 로그가 없으니 빈 취소로 CANCELLED만 기록(돈은 그대로)하고, 같은 요청의 Try가 재전송돼도 거부한다.

DB 롤백이 아니라 반대 방향 UPDATE를 한 번 더 하는 업무 로직이다.

시퀀스 — 잔액 50,000 실패 시 (2PC와 달리 락 구간이 없다)

TryConfirmCancelTest.지갑이못내면_잡아둔좌석을Cancel로되돌린다 기준. 실제 코드는 findById로 읽고 freeze()가 false를 반환해 UPDATE 자체가 없다. (README 다이어그램이 예전에 "UPDATE 0건 / 빈 커밋"으로 그렸던 것을 코드에 맞게 고쳤다.)

탭을 눌러 봅니다. 코드는 실제 파일에서 발췌(// ... 는 생략).

확정된 것과 잡아 둔 것을 따로 센다 락 대체

락으로 버티지 않으려면 "아직 확정은 아니지만 남이 가져가면 안 되는" 상태를 데이터로 표현해야 한다.

// WorkshopSeat — 정원 검사가 확정+잡아 둔 좌석을 함께 센다
public boolean hold(int seatCount) {
    if (reservedCount + heldCount + seatCount > totalSeats) {
        return false;
    }
    heldCount += seatCount;
    return true;
}
public void confirmHold(int seatCount) {
    heldCount -= seatCount;
    reservedCount += seatCount;
}
public void releaseHold(int seatCount) {
    heldCount -= seatCount;
}

// Wallet — Try에서 balance를 실제로 깎아 frozen으로 옮긴다
public boolean freeze(long amount) {
    if (balance < amount) {
        return false;
    }
    balance -= amount;
    frozen += amount;
    return true;
}
어떻게
잡아 둔 좌석도 이미 커밋돼 남에게 보이므로, 정원에서 함께 빼는 이 뺄셈이 곧 락을 대신한다(README).
지갑
frozen만 올리고 balance를 두면 Try 커밋 직후 다음 요청이 같은 돈을 본다 → 이중 지출. 그래서 balance에서 먼저 뺀다.

@Transactional("seatTransactionManager")
public boolean tryHold(long requestId, long workshopId, int seatCount) {
    SeatTccLog recorded = logs.findById(requestId).orElse(null);
    if (recorded != null) {
        // 취소가 먼저 지나갔다면 여기서 거부해야 아무도 회수하지 않는 좌석이 남지 않는다.
        return !CANCELLED.equals(recorded.getState());
    }
    WorkshopSeat seat = seats.findById(workshopId).orElseThrow();
    if (!seat.hold(seatCount)) {
        return false;
    }
    seats.save(seat);
    logs.save(new SeatTccLog(requestId, workshopId, seatCount, TRIED));
    return true;
}

@Transactional("seatTransactionManager")
public void cancel(long requestId) {
    SeatTccLog log = logs.findById(requestId).orElse(null);
    if (log == null) {
        // 잡아 둔 게 없으니 되돌릴 것도 없다. 워크숍과 수량은 알 수 없어 0으로 남긴다.
        logs.save(new SeatTccLog(requestId, 0L, 0, CANCELLED));
        return;
    }
    if (!TRIED.equals(log.getState())) {
        return;
    }
    // ... seat.releaseHold(log.getSeatCount()); log.changeState(CANCELLED);
}

락이 사라진 자리 — 참여자 로그로 막는 4가지 TccSafetyTest

상황로그가 없으면로그가 있으면 (테스트 결과)
Confirm이 두 번 온다reserved_count 2 → 4, 초과 판매두 번째는 CONFIRMED 보고 무시 → reserved 2, held 0
Cancel이 두 번 온다held_count -2, 재고가 조용히 늘어남두 번째는 CANCELLED 보고 무시 → held 0, reserved 0
Try 없이 Cancel이 온다되돌릴 게 없다고 그냥 넘어감빈 취소: 자원 안 건드리고 CANCELLED 기록
그 뒤 늦은 Try가 온다좌석을 잡지만 아무도 확정·취소 안 함(매달림)CANCELLED 보고 false → held 0
"로그가 없으면" 열은 README 표의 설명, 마지막 열은 TccSafetyTest assert 값. 같은 네 가지를 SeatParticipant와 WalletParticipant에 각각 검증한다(8개).

잡아 둔 자원(held/frozen)이 남는다. 실무에서는 트랜잭션 로그를 두고 재기동 시 미결 요청을 훑어 Confirm/Cancel을 마저 보낸다. 여기서는 코디네이터가 테스트 메서드라 그 장치가 없다. 잡아 둔 자원의 만료(타임아웃 후 자동 Cancel)도 없다.

README 동시 요청 — 갱신 유실

테스트는 순차 실행이고 락을 하나도 걸지 않았다. 두 요청이 같은 좌석을 동시에 잡으면 둘 다 held_count = 0을 읽고 각자 2를 더해 저장 → 4가 아니라 2. 해결: @Version 낙관적 락 + 재시도, 또는 검사를 UPDATE의 WHERE로. README: "TCC의 문제가 아니라 읽고-고쳐-쓰기의 문제". (설계 선택 표에서도 벌크 UPDATE 대신 엔티티 메서드를 택한 이유를 "순차 실행이라 가독성 우선"이라고 밝힘.)

README Cancel이 실패하는 경우

되돌리기도 네트워크를 건너는 이상 실패할 수 있고 재시도가 필요하다. 여기서는 Cancel이 항상 성공한다고 가정한다. 호출도 메시지 큐가 아닌 빈 메서드 직접 호출이라 유실·재시도는 재현하지 않았다.

코드 안전성 테스트는 좌석 참여자만 검증 수정함

TccSafetyTest의 4개 테스트는 모두 seatParticipant만 호출했다. WalletParticipant의 Confirm/Cancel 중복, 빈 취소, 늦은 Try 거부는 코드상 같은 구조지만 테스트로 검증되지 않았다.

어떻게 고쳤나: 같은 네 시나리오를 지갑도_… 테스트 4개로 추가했다. Confirm 두 번 → balance 40,000·frozen 0, Cancel 두 번 → balance 100,000, 빈 취소 → CANCELLED, 그 뒤 늦은 Try → false.

코드 README 표현이 코드와 다른 곳 2군데
  • README 수정함 "지갑이 못 내면" 다이어그램의 UPDATE 0건 (잔액 부족) / 빈 커밋 — 실제 tryFreeze는 findById로 읽고 freeze()가 false면 저장 없이 반환한다. 조건부 UPDATE가 아니다(2PC의 UPDATE … WHERE balance >= … 모양이 남은 것으로 보임).
  • 수정함 "락을 안 쥔다는 게 이런 것" 표의 SELECT 행: 2PC는 reserved_count(옛 값 0)를, TCC 테스트는 held_count(2)를 읽어 같은 칸 비교가 아니었다. 이제 테스트가 reserved_count, held_count를 함께 읽어 0과 2를 검증하고, README 표도 "2PC: reserved 0, prepare된 2석이 안 보임 / TCC: reserved 0, held 2, 잡아 둔 2석이 보임"으로 맞췄다.
코드 실패 시 지갑에는 Cancel을 보내지 않는다 수정함

테스트 코디네이터는 Try가 성공한 좌석에만 cancel을 불렀다(지갑 로그 null로 검증). 실제 코디네이터는 Try 응답이 유실될 수 있으므로 보통 모든 참여자에 Cancel을 보내고, 참여자는 빈 취소로 흡수한다 일반 지식.

어떻게 고쳤나: 지갑이못내면_잡아둔좌석을Cancel로되돌린다가 좌석·지갑 모두에 Cancel을 보낸다. 지갑 로그가 null → CANCELLED(빈 취소)로 바뀌고 balance는 50,000 그대로, 재전송된 지갑 Try는 false임을 검증한다. README "지갑이 못 내면" 다이어그램과 표에도 지갑 빈 취소를 넣었다. 위 SVG 시퀀스에도 지갑 빈 취소 화살표를 더했다.

코드 테스트 전용 애플리케이션

TccApplication에는 main 메서드가 없고 application.yml도 없다. DataSource URL은 테스트의 @DynamicPropertySource만 주입한다. HTTP API·컨트롤러도 없어 참여자는 빈 메서드로만 호출된다. 실행에는 Docker(Testcontainers MySQL 2대)가 필요하다.

06면접 Q&A

질문을 먼저 읽고 스스로 답해 본 뒤 펼쳐 보세요.

TCC를 설명하고 2PC와 가장 큰 차이를 말해 보세요.

Try에서 자원을 잡아 두고 바로 커밋, 전원 성공하면 Confirm, 하나라도 실패하면 Cancel(반대 방향 업무 작업). 2PC는 prepare 후 락을 쥐고 결정을 기다리지만 TCC는 단계 사이에 락이 없다. 대신 되돌리기를 DB가 아니라 참여자 코드가 한다.

지갑 Try에서 frozen만 올리지 않고 balance를 실제로 깎는 이유는?

Try가 커밋되면 락이 없다. balance를 그대로 두면 다음 요청이 같은 돈을 보고 또 쓸 수 있다(이중 지출). balance에서 빼서 frozen으로 옮겨야 한다. 좌석도 같은 이유로 정원 검사에 heldCount를 포함한다.

Confirm이 두 번 오면? 왜 두 번 올 수 있나요?

Confirm 응답이 유실되면 코디네이터는 재전송한다. 로그를 안 보면 held→reserved를 두 번 옮겨 2석이 4석(초과 판매). 참여자는 로그 state가 TRIED일 때만 적용하고 CONFIRMED면 무시한다(Confirm을두번받아도_한번만적용된다).

빈 취소(empty rollback)와 매달림(suspension)을 설명해 보세요.

Try가 유실·지연된 채 코디네이터가 Cancel을 보내면 참여자는 본 적 없는 요청의 Cancel을 받는다 → 자원은 안 건드리고 CANCELLED를 기록(빈 취소). 그 기록이 없으면 뒤늦게 온 Try가 자원을 잡아 두는데 코디네이터는 이미 끝났으니 아무도 회수하지 않는다(매달림). 그래서 Try는 CANCELLED 로그를 보면 거부한다. Seata는 이를 空回滚·悬挂로 부른다(README).

"격리를 포기했다"는 게 실무에서 무슨 의미인가요?

Try만 끝난 held/frozen 값이 커밋되어 다른 트랜잭션에 보인다. 예: 잔여 좌석 화면이 아직 확정 안 된 hold를 반영하고, 그 hold가 Cancel되면 잠깐 매진처럼 보였다가 풀린다. 그래서 조회 화면·정산은 reserved와 held를 구분해서 다뤄야 한다 추론.

코디네이터가 Try 직후 죽으면 어떻게 되나요?

held/frozen이 남는다(README "다루지 않은 것"). 실무에서는 코디네이터가 글로벌 트랜잭션 로그를 두고 재기동 시 미결 건에 Confirm/Cancel을 재전송하며, 타임아웃이 지나면 Cancel하는 것이 일반적이다 일반 지식. 2PC와 달리 그동안 다른 요청은 막히지 않는다.

두 요청이 같은 좌석을 동시에 Try하면 안전한가요?

이 구현은 아니다. 엔티티를 읽고-고쳐-쓰기라 갱신 유실 가능(README 명시). @Version 낙관적 락 + 재시도, 또는 UPDATE … SET held_count = held_count + ? WHERE reserved_count + held_count + ? <= total_seats 같은 조건부 UPDATE로 해결. TCC 프로토콜과는 별개 문제.

TCC와 Saga는 어떻게 다른가요?

일반 지식 Saga는 각 단계를 바로 최종 반영하고 실패 시 보상 트랜잭션을 역순 실행한다(예약 단계 없음 → 중간 상태가 "확정처럼" 보임). TCC는 Try에서 예약(hold) 상태를 따로 두고 Confirm/Cancel로 마무리하므로 비즈니스 모델에 held/frozen 같은 칸이 필요하다. 이 저장소에 Saga 구현은 없다.

Cancel이 계속 실패하면?

README는 다루지 않았다고 명시. Cancel도 멱등하게 만들어 두었으니 재시도가 기본이고, 한계를 넘으면 알림·수동 처리 큐로 보낸다 일반 지식.

실무에서 직접 구현 vs 프레임워크?

Seata TCC 모드는 @TwoPhaseBusinessAction으로 세 메서드만 선언하면 로그 관리·멱등·빈 취소·매달림 판단을 대신한다(README). 이 실험실은 상태 전이를 보이려고 프레임워크 없이 직접 짰다. 참여자마다 세 벌의 로직을 짜야 하는 비용은 어느 쪽이든 남는다.
